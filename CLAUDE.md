# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bdzbridge is unofficial software that talks only, on the LAN, to Sony BDZ Blu-ray recorders and Sony BRAVIA televisions; its app is called RecBridge, while the repository, the server (the `bdzbridge` package) and the PWA keep the name bdzbridge. The iOS app, RecBridge (on the App Store: https://apps.apple.com/jp/app/recbridge/id6812831646), and the Android app over the same model talk to the recorder and the television themselves, with no server, and keep the guide on the device. From 0.5, where a home has no recorder or the reader chooses it, the guide comes from the television, through a helper app installed on it. The server knows the recorder alone: it reads the recorder's own 8-day EPG and its UPnP reservation service, and exposes both as a token-protected JSON API plus a mobile PWA, so a phone can browse the guide and schedule recordings (through a VPN such as Tailscale when away from home).

- `server/` — Python 3.12+ / FastAPI package `bdzbridge` (uv-managed). Serves `web/dist` at `/` when it exists.
- `web/` — Vite + Svelte 5 PWA (plain JS, runes). Uses `/api/v1` on the same origin; the Vite dev server proxies `/api` to port 8000.
- `app/` — the iOS app, RecBridge (Swift/SwiftUI), for iPhone, iOS 17 or later. RecBridge is `CFBundleDisplayName` and what a reader sees; the target, the product, the scheme, the archive and the bundle identifier keep the name it was first published under, BDBridge. Its version is `MARKETING_VERSION` in `app/project.yml`. It is two Swift packages and the app over them; see `app/README.md`.

What is particular to a recorder is in `RecorderDriver`, and to a Sony television in `TVDriver` over `ScalarClient`. A driver holds its link. They keep the television's rules and answer with their sentences (`Reserved`, `Altered`).

## Commands

Server (inside `server/`):

```
uv sync --group dev
uv run pytest -q                       # no recorder needed; the real-file test skips unless BDZBRIDGE_TEST_EPG_FILE is set
uv run pytest -q tests/test_xsrs.py::test_create_elements_match_official_app
uv run ruff check bdzbridge tests
cp .env.example .env                   # set BDZBRIDGE_API_TOKEN; recorder host optional
uv run python -m bdzbridge discover    # list recorders on the LAN
uv run python -m bdzbridge             # serve; OpenAPI at /docs
uv run python -m bdzbridge.tools.apidoc  # regenerate docs/api.md + docs/openapi.json (a test fails while they are stale; `git config core.hooksPath .githooks` makes a pre-commit hook do it)
uv run python -m bdzbridge.tools.portkit # regenerate docs/port/ (conformance vectors for a native port; same freshness test and hook)
```

Every call to the server's API needs `Authorization: Bearer <BDZBRIDGE_API_TOKEN>`.

Web (inside `web/`): `npm install`, `npm run build` (writes `web/dist`; restart the server to pick it up), `npm run dev`, `npm test` (the rules in `src/api.js`, with Node's own test runner).

iOS: inside `app/RecorderKit`, `swift build` and `swift test` (reads the vectors in `docs/port`; the pre-commit hook runs it when `app/` or `docs/port/` is staged); the model's tests are `swift test` inside `app/RecBridgeModel`, which the hook runs too. Live checks, inside `app/RecorderKit`: `RECORDER_HOST=<ip> swift test --filter LiveRecorderTests` reads a real recorder (it writes only with `RECORDER_WRITE=1` as well, and wakes the recorder first with `RECORDER_MAC`); `TV_HOST=<ip> swift test --filter LiveTVTests/<one test>` asks a real television (its header says how the registration is run); `TV_HOST=<ip> swift test --filter LiveTVHelperTests/testWhoAnswers` checks the app's side against the helper on a real television, and `testReadingTheGuide` reads its guide with `TV_HELPER_TOKEN` set as well. For the app, `brew install xcodegen` once, then inside `app/`:

```
xcodegen generate                      # rewrites BDBridge.xcodeproj and BDBridge/Info.plist; commit them
xcodebuild -project BDBridge.xcodeproj -scheme BDBridge -destination 'id=<simulator udid>' build
xcodebuild test -project BDBridge.xcodeproj -scheme BDBridge -destination 'id=<simulator udid>' -only-testing:BDBridgeTests
xcodebuild test -project BDBridge.xcodeproj -scheme BDBridge -destination 'id=<simulator udid>' -only-testing:BDBridgeUITests/DemoModeTests
```

Android (inside `android/`, once what `android/README.md` lists is in place): `./gradlew :app:assembleDebug`; the Swift bridge's tests run on the Mac with `JAVA_HOME=<JDK> swift test --disable-sandbox` inside `android/core` (swift-java builds the Java of Kotlin's listeners with Gradle); the demo's screen tests on an emulator with `ANDROID_SERIAL=<serial> ./gradlew :app:connectedDebugAndroidTest`.

The two packages' tests also run on Android: `app/scripts/android-tests.sh build <arch>`, then `app/scripts/android-tests.sh run <arch>` (aarch64 or x86_64), on the one device or emulator adb sees; on a Mac, with `SWIFT="swiftly run swift +6.4.2"`. GitHub Actions (`.github/workflows/android.yml`) runs the same on an emulator for every pull request and every push to main. On a pull request that changes nothing under `app/RecorderKit`, `app/RecBridgeModel`, `docs/port`, the script or the workflow, it passes without building.

Helper (inside `helper/`, with JDK 17 and the Android SDK's platform 34 and build-tools 34): `./gradlew assembleDebug` gives `recbridge-helper-debug.apk`, and `./gradlew assembleRelease` gives `recbridge-helper.apk`. A release build is signed only with the key that the file named by `RECBRIDGE_HELPER_KEYS`, or `~/.config/recbridge-helper/key.properties`, describes, and comes out unsigned otherwise; the key never goes in the repository. The helper has no tests of its own; the app's side is checked against it on a real television by `LiveTVHelperTests` (above).

The repository is public. The pre-commit hook (`git config core.hooksPath .githooks`, once) also refuses staged signing material, parses a staged privacy manifest strictly (Apple refuses one that `plutil -lint` accepts, ITMS-91056), and, with XcodeGen installed, fails a commit whose `app/BDBridge.xcodeproj` or `app/BDBridge/Info.plist` no longer matches `app/project.yml`.

## Architecture

- `bdzbridge/config.py` — `Settings`, read from the environment variables prefixed `BDZBRIDGE_` and from `.env` (see `.env.example`). `bdzbridge/__main__.py` serves, or with `discover` lists the recorders it finds.
- `bdzbridge/recorder/epg.py` — decodes `EPG_*_FILE.dat` (XOR 0x9D, concatenated zlib, "@SRV/@DAY/@EVT" container; see docs/epg-format.md). Has an encoder used only by tests to build fixtures. `bdzbridge/recorder/logo.py` decodes the station-logo files served next to them, in the same wrapping, and has a test encoder too.
- `bdzbridge/recorder/xsrs.py` — SOAP client for `X_ScheduledRecording` / `X_PvrControl`. `build_create_elements` must stay byte-identical to the captured request in `tests/fixtures/create-request.xml`; the recorder answers UPnP error 402 to any deviation (e.g. `+0900` instead of `+09:00`). Updates send the same item with `id` set.
- `bdzbridge/recorder/codes.py` — quality / repeat / broadcasting code tables.
- `bdzbridge/recorder/series.py` — groups recorded titles into programmes by their names (the recorder exposes no series id). Keyword auto-reservation (`bdzbridge/services/autorec.py`) runs after each EPG refresh and reports through `bdzbridge/services/notify.py` (SMTP / webhook).
- `bdzbridge/recorder/discovery.py` — SSDP M-SEARCH, then a TCP scan of the local /24 for port 64220; candidates are confirmed via `description.xml`.
- `bdzbridge/recorder/client.py` — one recorder: discovery, EPG download from port 60151, and an `asyncio.Lock` serializing every request (the recorder returns 503 to concurrent requests).
- `bdzbridge/recorder/wol.py` — Wake-on-LAN, the MAC taken from the host's ARP/neighbour table right after a talk with the recorder (`BDZBRIDGE_RECORDER_MAC` overrides it).
- `bdzbridge/store/` — SQLite, one mixin per area assembled into `Store`: `base.py` (connection, schema, meta; `SCHEMA_VERSION` rebuilds the cache tables, user data survives), `guide.py` (channels, programs with NFKC/case-folded search text and reference resolution in SQL, logos, channel preferences; a TV day is 04:00–04:00 JST), `rules.py` (auto-reservation rules and their log), `titles.py` (cached programme summaries).
- `bdzbridge/api/app.py` — assembles the FastAPI app: lifespan (creates `Bridge`, starts the refresh loop), the routers under `api/routers/` (recorder, guide, reservations, rules, titles, jobs), and the static web app. `api/deps.py` has the bearer-token dependency; `api/schemas.py` holds the API's models, and `api/serializers.py` turns recorder/store objects into them.
- `bdzbridge/state.py` — `Bridge`, the state shared by everything: settings, the selected recorder or None, store, notifier, job registry, the cached full title list, and what is kept of the USB disk between readings (the disk the list's USB rows came from, those rows, when the slot first said none). It has no behaviour beyond `require_recorder`.
- `bdzbridge/services/` — what the app does with a recorder, as functions taking the `Bridge`: `usb.py` (the disk in the USB slot: what the recorder says of it and the disk kept between readings), `session.py` (discovery, selection order `BDZBRIDGE_RECORDER_HOST` → host saved in SQLite `meta`, re-discovered by UDN if it moved → unconfigured; reachability; Wake-on-LAN), `epg.py` (refresh + loop, then rules and monitor), `titles.py` (full-list cache, programme groups, duplicate scan, bulk delete/protect as job bodies), `autorec.py`, `monitor.py`, `notify.py`. `bdzbridge/jobs.py` runs the bulk bodies as cancellable background jobs: POST starts one (202 + job), `GET /jobs/{id}` polls, `POST /jobs/{id}/cancel` stops after the current item (`Job.step()` is the checkpoint); the web app follows them with `src/jobs.svelte.js`, which also keeps the running ones for the job bar on the recordings screen (`GET /jobs` lets a reopened page pick them up). Tests inject a fake recorder through `create_app(settings, bridge)`; the fakes and the `client` fixture live in `tests/conftest.py`, API tests are split by area (`tests/test_api_*.py`).
- Web: `src/api.js` (fetch wrapper, reservation index, formatters), `src/store.svelte.js` (shared state), `src/prefs.js` (per-device preferences in localStorage), `src/jobs.svelte.js` (start / follow / cancel bulk jobs; shared list of running ones), `src/lib/*.svelte` (Setup, Guide with ProgramList or GuideGrid and ChannelPrefs, Search, Reservations, Settings, ProgramSheet). The recordings screen is `src/lib/Titles.svelte` as the shell (filters, list, groups) with `src/lib/titles/` components: TitleRow / PickRow, TitleSheet (detail, play, protect, delete), GroupSheet (episodes, bulk delete / protect), DuplicatesView, PlaybackBar, JobBar (running jobs with 中止, independent of any sheet), JobModal (confirm + progress + 中止). Children report changes through `onchanged({ deleted, protected })` and the shell keeps every list in step.

## Device facts that shape the code

- Creating a reservation with `event_id` makes the recorder follow schedule changes and replaces any title we send with its own EPG title. Time-only reservations never get an event id back-filled.
- The recorder answers in network standby; `X_PowerControl` with `on` works, `PowerOn`/`On` do not. It also leaves the LAN after a quarter of an hour or so in standby, and is then woken with a magic packet to its MAC: by the app before it asks anything (`Waking.swift`, `WakeOnLan.swift`), and by the server before a refresh, playback or power-on (`bdzbridge/recorder/wol.py`).
- Just after a wake, the recorder can say that no USB disk is in the slot, the same answer it gives for a disk taken out. One such answer is not believed while a disk is known: the app keeps the disk and reads the slot again 30 seconds later (`RecorderDriver.learnTheSlot`), and the server keeps it until a reading 30 seconds later says none as well (`services/usb.py`). See `docs/xsrs-api.md`, USB HDD.
- Writes to the recorder (create/update/delete) are real. The ordinary tests never touch a device; the live ones touch one only when an address is given, and write only with `RECORDER_WRITE=1` or with `TV_WRITE` naming the test. Manual checks should use a clearly named reservation and delete it afterwards. So are writes to a television: a reservation made, changed or deleted, or a recording on its USB disk protected or deleted, from the screens, and a waiting row sent from the screens, the overnight run or the Shortcuts action. The same care applies.
- The recorder's own keyword conditions (おまかせ・まる録, `X_*PrefRecSetting`) are created and deleted, never updated: the list omits the channel narrowing the recorder's screen can set, and writing a condition back erases it (verified). `Filter` must be `*` there or the quality and the recording destination are dropped. See `docs/xsrs-api.md`.
- The television is never woken: `TVDriver` answers `canWake` with false, and there is no packet to send. A PIN goes on its screen only when the reader asks to register.
- The first ask of a connect needs no registration (`getSystemSupportedFunction`, which a television answers in standby). Nothing that carries the registration's cookie is sent until the saved television has said by its MAC that it is the one, at a connect and at the check before an operation (`TVDriver.check`); one that gives no MAC is taken for the one saved. A television with another MAC is refused before the registration request is sent (`ScalarClient.enrol(expecting:)`). See `docs/porting.md`.
