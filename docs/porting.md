# ネイティブアプリへの移植ガイド

bdzbridge はサーバー（Python）とブラウザ（PWA）、それに iOS アプリ（`app/`）の 3 つで動いています。サーバーも
VPN 前提の構成も要らずアプリがレコーダーと直接話す形が iOS アプリで、**これは実機で動いています**。このドキュメントは
「何をそのまま持っていき、何を作り直し、何で検証するか」と、実機で分かったレコーダーの癖をまとめたものです。
プロトコルそのものの説明は [`xsrs-api.md`](xsrs-api.md) と [`epg-format.md`](epg-format.md) にあり、ここでは
繰り返しません。

読者は 2 通りです。

- **iOS アプリに手を入れる人**: 下の「Swift での対応」「レコーダーの振る舞いチェックリスト」「端末側の設計メモ」が
  実装の背景です。アプリの構成そのものは `app/README.md`。
- **他のプラットフォームに移植する人**: Android ネイティブは作者の予定にありません。必要と思った人が作れるように、
  機種依存の知識と検証ベクタは言語に依存しない形にしてあります。Android 利用者向けの現状の道は、サーバーを自分で
  動かして PWA を使うことです。

## 前提と方針

- レコーダーの API は LAN 内で無認証です。アプリはレコーダーと同じネットワークにいるとき（VPN で自宅の
  ネットワークに入っている場合を含む）に動作します。届かないときはキャッシュ済みの番組表を見て、予約は
  「送信待ち」として端末に溜め、**次にレコーダーに接続できたとき**に送ります（帰宅を待つ必要はありません。
  VPN 越しにレコーダーを起こして送れることも実機で確認しています）。
- Python のサーバーは移植中も動かし続け、**正解（oracle）**として使います。同じレコーダーに対して両方から
  同じ操作をして結果を突き合わせるのがいちばん確実な検証です（書き込みは予約の作成→削除で行い、録画の削除は
  テストに使わないこと）。
- 機種依存の知識はすべて `server/bdzbridge/recorder/` に閉じ込めてあります。移植の中心はこのディレクトリです。

## 何を持っていくか

| Python 側 | 役割 | 移植先での扱い | 検証ベクタ |
|---|---|---|---|
| `recorder/discovery.py` | SSDP M-SEARCH → 見つからなければ /24 を TCP 64220 でスキャン → `description.xml` で確認 | 必須。SSDP はマルチキャストの権限が要る（後述）。スキャンだけでも成立する | `port/description.json` |
| `recorder/client.py` | 1 台分の状態、EPG/ロゴのダウンロード、DLNA ツリーから配信ポートの検出、**全リクエストを直列化するロック** | 必須。ロックは絶対に省かない（並行リクエストに 503 を返す）。配信ポートの検出は**番組表ファイルが必要になった時点で 1 回だけ**行う（後述） | — |
| `recorder/xsrs.py` | SOAP の組み立て、予約/録画 item の解析、`build_create_elements` | 必須。生成する XML は Python とバイト単位で一致させる | `port/xsrs.json` |
| `recorder/codes.py` | 放送種別・画質・毎回録画・ジャンルのコード表、EPG/ロゴのファイル名 | そのまま定数に | `port/codes.json` |
| `recorder/epg.py` | EPG ファイルの復号（XOR 0x9D → 連結 zlib → @SRV/@DAY/@EVT）、ARIB 記号の置換 | 必須 | `port/epg-sample.{dat,json}` |
| `recorder/logo.py` | 局ロゴファイルの復号、PLTE/tRNS の挿入 | 任意（見た目） | `port/logo-sample.{dat,json}` |
| `recorder/series.py` | 録画タイトルからの番組名抽出（まとめ表示）、重複検出のキー | 必須（まとめ・重複を出すなら）。正規表現をそのまま移す。結果はタイトルごとに覚えておく（まとめは描画のたびに全録画を通すので、毎回求めると 1,300 本で数十 ms かかる） | `port/series.json` |
| `recorder/wol.py` | Wake-on-LAN | **必須に近い**。レコーダーは時間の 4 分の 3 を寝て過ごすので例外処理ではなく通常の経路。**MAC はレコーダー自身が教えてくれる**（`X_GetPrivateIp`、または `description.xml` の UDN 末尾）ので、利用者に入力させる必要はない | — |
| `store/guide.py` | SQLite の番組表キャッシュ（検索用正規化、サブチャンネルの参照解決、放送日 04:00 区切り） | 端末内 DB に作り直す。仕様は下記「番組表の扱い」 | — |
| `store/rules.py` + `services/autorec.py` | 番組表からのキーワード自動予約（サーバー側の機能） | 任意。**iOS アプリでは作っていません**: レコーダー本体の「おまかせ・まる録」を読み書きできるので、アプリを閉じていても本体が録ってくれる方を採りました | — |
| `services/titles.py` | 全録画リストのキャッシュ、まとめ、重複検出、一括削除/保護 | ロジックはそのまま。一括処理は端末内で逐次実行し、中止できるようにする | — |
| `jobs.py`, `api/`, `services/notify.py`, `services/monitor.py` | サーバーならではの部分（HTTP API、ジョブ、SMTP/webhook 通知、残容量監視） | 不要。通知は端末のローカル通知で代替 | — |

## Swift での対応

すべて OS 標準の機能で足ります。外部ライブラリは要りません。

| やること | 使うもの |
|---|---|
| LAN への HTTP と SOAP | `URLSession`。1 台につき 1 本に直列化するため、`actor` で包むか `OperationQueue` の同時実行数を 1 にする |
| /24 の TCP スキャン | 各アドレスの `description.xml` を `URLSession` で取りに行く（48 本並列、1 本 1.2 秒で打ち切り）。答えの中身でレコーダーかどうか決まるので、ポートだけを見る走査は別に要らない。その前にローカルネットワークの許可を待つ（下の「ローカルネットワークの許可」） |
| SSDP | `NWConnection` のマルチキャスト。エンタイトルメント申請が必要なので後回しにする |
| Wake-on-LAN | BSD ソケット（`socket`、`setsockopt(SO_BROADCAST)`、`sendto`）の UDP。Network framework にはブロードキャストを送る手段がない。宛先は 3 つ（`255.255.255.255`、レコーダーのサブネットのブロードキャスト、**レコーダーのアドレス宛のユニキャスト**）。VPN 越しに届くのはユニキャストだけ。iPhone で実際に出ていくのはこのうち 2 つの見込み（下の「Wake-on-LAN」） |
| 連結 zlib の展開 | `libz` を直接使い、`z_stream` の未消費バイト数から次のストリームの開始位置を求める。`import zlib` がそのまま通り、iOS SDK でも解決します。Compression framework でも消費量は追えるが、境界の判定を自分で書くことになる |
| XML の解析 | `XMLParser`。SOAP 応答と DIDL-Lite の両方に使う |
| XML の生成 | 文字列連結で十分。要素の順序を固定したいので、汎用のシリアライザは使わない方が確実 |
| 番組表の保存 | SQLite。検索用に NFKC + casefold 済みの列を持たせる。ファイルは Application Support の下のフォルダ（`Guide/`）に置き、**フォルダごと**バックアップから外す（-wal と -shm は作り直されるので、ファイルに付けた印は消える）。画面と深夜の処理はそれぞれ接続を開くので、`sqlite3_busy_timeout` で 5 秒待たせる（無いと、重なった書き込みがすぐ「database is locked」で失敗する） |
| 定期更新 | `BGProcessingTask`（`requiresNetworkConnectivity`、深夜 2 時を `earliestBeginDate` に）。呼ばれる保証がないので手動更新も必ず置く。**この中でもレコーダーを起こすこと**: 深夜はまず寝ている。期限切れのハンドラでは**その場で**完了を伝え（処理の終わりと重なっても 1 回だけ）、処理のほうは種別の切り替わりで取り消しを見て止める。取り消しても送信中の要求は最後まで待つので、処理の終わりを待って完了すると、番組表ファイル 1 本で 2 分待たせることになる |
| 通知 | `UNUserNotificationCenter`。自動予約の結果と残容量の警告に使う。許可の取り方は下の「通知の許可」 |

UI で唯一手間がかかるのは番組表の表形式です。時間軸とチャンネル軸の 2 方向スクロール、両方向に残るヘッダー、
ピンチでの時間軸の拡大縮小は SwiftUI でも自前で組む必要があります。PWA 側の `GuideGrid.svelte` が仕様書代わりになります。

## レコーダーの振る舞いチェックリスト

実機（BDZ-FBT4100）で分かったこと。どれもコードにコメントとして残っていますが、移植時に踏みやすい順に並べます。

**通信**
- 同時リクエストは 503。1 台につき 1 本のキューで直列化する（アプリではクライアントが 1 本ずつ持つ）。それでも
  ほかのクライアント（公式アプリ、別の端末、同じアプリの深夜の処理）とはぶつかるので、503 は**キューの中で**
  0.5〜1 秒（ランダム）おいて 2 回まで送り直し、それでも 503 なら「ほかの要求を処理中」として返す。
  どの呼び出し元も 503 を独自に読み違えていた
  （`description.xml` では「ソニー製レコーダーではない」、番組表ファイルでは「まだ作られていない」）。
- XSRS の制御 URL は `/XSRS`、X_PvrControl は `/X_PvrControl`、ContentDirectory は `/DMSContentDirectory`。ポートは 64220。
- SOAP ヘッダは `Content-Type: text/xml; charset="utf-8"`、`SOAPACTION: "<serviceType>#<action>"`、`Accept-Language: ja`。
  本文の形は `port/xsrs.json` の `soap.example`。
- エラーは HTTP 500 + SOAP Fault の `errorCode`。402 は引数の形式違反（例: 時刻のオフセットが `+0900`）、
  804 は存在しない予約 ID、820 は存在しないタイトル ID、831 は受信できないチャンネルの番組を追従予約しようとした、
  880 はレコーダーがネットワークスタンバイ中で再生できない。**errorCode の無い素の HTTP 500 もあります**
  （録画中のタイトルの削除。後述）。
- EPG/ロゴのファイルは別ポート（既定 60151）から `//EPG_TRDEPG_FILE.dat` のように**スラッシュ 2 つ**で取る。ポートは
  DLNA ツリーの最初の `<res>` URL から確認できる。そのチャンネル種別を持っていない場合は 416 が返る。
- **`description.xml` の取得に余計な処理を足さないこと。** 上の配信ポート検出（Browse を最大 8 回）を
  `describe` の中でやっていたため、「2 秒で諦めるはずの生存確認」が数分かかりました。起動待ちのプローブは
  `description.xml` 1 本だけにして、ポート検出は番組表ファイルを取る直前に 1 回だけ行います。
- ネットワークスタンバイ中でも API は答える。電源を入れるのは `X_PowerControl` の `on`（`PowerOn` や `On` は不可）。
- レコーダーが完全に落ちている（電源オフ後しばらく）と何も答えない。Wake-on-LAN で起きる。本体の「ネットワーク待機」が
  切だと、しばらく操作がないだけで LAN から消えるので、これは例外ではなく普通に起きる。
- **レコーダーは自分から起きます。** 12 時間つないだまま 1 分ごとに 64220 を見た記録（2026-09-17、誰も操作していない
  時間帯を含む）:

  | | 回数 | 中央値 | 最短 | 最長 |
  |---|---|---|---|---|
  | 寝ている時間 | 13 | 27 分 | 2 分 | 136 分 |
  | 起きている時間 | 12 | 10 分 | 2 分 | 81 分 |

  応答していたのは全体の **25%**。周期は一定ではなく、2 分で起きることも 2 時間寝ていることもあります。設計上の
  意味は 2 つです。**(1) 「寝ている」は恒久的な状態ではない**ので、溜めた予約を送る機会は放っておいても来ます
  （中央値 27 分待ち）。**(2) 逆に、起きているのは 4 分の 1 の時間だけ**なので、アプリを開いた瞬間につながっている
  ことは期待できず、Wake-on-LAN は例外処理ではなく通常の経路として要ります。
  何のために起きているのかは LAN 側からは見えません（外部サービスとの通信を覗く手段がない）。
- **Wake-on-LAN はレコーダー自身が申告しています。** `description.xml` の `X_WakeupOnLAN` が `1`（取説には記載なし、
  公式クライアントもこの値を読む）。
  宛先の MAC は 2 通りで取れるので、ユーザーに入力させる必要はありません。`X_PvrControl` の `X_GetPrivateIp` が
  `macAddress` と `wirelessMacAddress` を返すのが正攻法で、`description.xml` の `<UDN>` の末尾 12 桁も同じ有線 MAC です
  （`uuid:XXXXXXXX-XXXX-XXXX-XXXX-<MAC>`、実機で ARP と一致）。iOS は ARP を読めないので、起きているうちに控えておくのが
  唯一の手です。有線と無線で MAC が違うので、繋いでいる側を使うこと。
- **Wake-on-LAN は同じサブネットにいるときだけ確実です。** `255.255.255.255` はルーターを越えず、VPN 越しの端末は
  自分のインターフェースから自宅のサブネットを知ることができません。レコーダーのアドレスからそのサブネットの
  ブロードキャストを組み立てて送る手はありますが、ゲートウェイがディレクテッドブロードキャストを転送する設定で
  なければ届きません（UniFi は既定で転送しません）。**レコーダーのアドレス宛のユニキャストでも起きます**（実測:
  ブロードキャストを一切使わず、同じセグメントからアドレス宛にポート 9 と 7 へ送って 6 秒で応答）。
  どちらの実装も、リミテッドブロードキャスト・サブネットのブロードキャスト・レコーダーのアドレスの 3 つへ送ります。
- **VPN 越しにも起きました。** 外出先から VPN でつないだ iPhone のアプリが、寝ていたレコーダーを起こして接続
  できています（寝てから 2 分後、起きるまで 2 分ほど）。届いたのはアドレス宛のユニキャストで、
  ブロードキャストは VPN を越えません。ただし**ゲートウェイがそのアドレスの MAC を覚えている間だけ**のはずで、
  何時間も寝たあとに同じことができるかは未確認です。キャッシュが切れた後は LAN の内側にいる何かに送ってもらう
  しかありません。自宅にサーバーを置いているなら `POST /api/v1/recorder/wake` がその役目を果たします。
- **この機種は ICMP に答えません。** 起きていても ping は通らないので、死活監視には使えません（UPnP のポート
  64220 に繋がるかで見ます）。「ping に答えない＝ネットワークにいない」とは言えない、ということでもあります。
- `X_GetPrivateIp` は `useDhcp` も返します。アドレスが DHCP で動く機体なら、保存した IP に繋ぐだけの実装は取りこぼします。
  サーバー側は UDN で再探索していますが、移植先でも同じ手当てが必要です。
- サービスは 5 つに見えて実質 4 つ。`/XSRSExt`（`X_ScheduledRecordingExt:1`）は `/XSRS` と SCPD が完全に同一で、同じ答えを
  返します。詳細は `upnp/service-sweep.md`。

**予約**
- `X_CreateRecordSchedule` の `<Elements>` は公式アプリの送信内容と同一にする（`port/xsrs.json` の `create_elements[0]`
  は実キャプチャ由来）。要素の順序、`channelType="2"`、`scheduledChannelID` の `0x0428` 形式、時刻の `+09:00`。
- `desiredMatchingID` に `,,0x<service>,0x<event>` を入れると番組追従になり、タイトルはレコーダーが EPG から上書きする。
  時間指定（event なし）の予約は後から event_id が補完されることはない。
- 更新は同じ item に `id` を付けて `X_UpdateRecordSchedule`。画質・毎回録画をその場で変えられる。
- 毎週の毎回録画（`w1`〜`w7`）は番組の曜日と一致させる。
- 一覧は `X_GetRecordScheduleList`、1 回 200 件まで。ソートは `-scheduledStartDateTime`。
- **予約 ID は振り直されます。** レコーダーが自分のおまかせ・まる録で入れた予約は、番組表を読み直したときに
  ブロックごと番号が変わります（実測: 19 件が一斉に変わり、番組自体は同じまま）。数時間前に読んだ ID で削除や
  更新をすると 804 になります。**削除・更新の前に一覧を読み直し、チャンネルと開始時刻で同じ予約を探すこと**
  （この 2 つが同じ予約は 2 つ存在しません）。本当に無くなっているのは、探して見つからないときだけです。
- `X_GetConflictList` に作成と同じ Elements を渡すと重なる予約が返る。作成と同じ本文を投げるので、**実際に
  作らずに本文の妥当性まで確かめられます**。

**録画タイトル**
- `X_GetTitleList` は `recordDestinationID=HDD` で検索し、1 回 200 件まで。`TotalMatches` を見て繰り返す。
- `lastPlaybackTime` は未再生だと本文が `notplayed`。`resumePoint` 属性が再生位置（秒）。
- `genreID` は ARIB のレベル1×16＋レベル2。
- `X_UpdateTitle` は `<item id>` と変える要素だけを送る（`titleProtectFlag`、`titleNewFlag`、`title`）。
- `X_DeleteTitle` は保護中なら失敗、**存在しない ID には成功を返す**。削除前に `X_GetTitleDetail` で存在を確かめる。
  1 件 3 秒ほどかかる。
- **録画中のタイトルも一覧に出ます。** item の `recordingFlag` が `1`。これを消そうとすると
  **errorCode の無い HTTP 500** が返るので（820 のような手がかりが無い）、削除の前にフラグを見て、画面にも
  「録画中」と出すこと。完了したタイトルが `0` であることは実機で確認済み、`1` の観測は未了（予約一覧の
  同名フラグと同じ意味と解釈）。
- 再生は `X_PlayControlTitle`（`play` / `stop` / `pause`、小文字。`pause` はトグルで再開も同じ）。テレビ側で再生される。
  `Position` を付けても先頭から始まるので、途中まで見た録画のボタンは「最初から再生」にしてある。
- ネットワークスタンバイ中の `play` は 880。アプリはそのときだけ `X_PowerControl` の `on` を送り、`X_GetPlayStatus` の
  `powerstatus` が `PowerOn` になるまで 1 秒ごとに見て（最長 30 秒、経過秒数を画面に出す）、もう一度 `play` を送る
  （`RecorderClient.play`）。先に電源状態は確かめない: 電源が入っているときに毎回 1 往復増えるうえ、サンプルデータの
  レコーダーは `powerstatus` を返さない。待っても入らなければ 880 のまま返り、手で電源を入れるボタンが出る。
- 残容量は ContentDirectory の `X_HDLnkGetRecordDestinationInfo`（バイト単位）。`RecordDestinationInfo` 要素の中に
  エスケープされた XML があり、その `totalCapacity` / `availableCapacity` 属性が値。
- サムネイルは全タイトル共通のダミー画像なので出さない。番組内容は `X_GetTitleDetail`（summary と detail 群）。
- DLNA ツリーにはシリーズ ID がない。「まとめ」はタイトル文字列から `series.py` の規則で作る。公式クライアントも
  同じくクライアント側でタイトル文字列から鍵を作っている。
- レコーダー本体の「おまかせ・まる録」（キーワード自動録画）は `X_GetPrefRecSettingList` で読め、
  `X_CreatePrefRecSetting` / `X_DeletePrefRecSetting` で作成・削除できる。**変更は実装しない**: 一覧には本体で設定した
  対象チャンネルが含まれず、書き戻すとそれが消える（実測）。`Filter` は `*` を渡すこと。録画モードは放送波ごとに
  2 つあり、`ALL`（と知らない放送波）の条件では `desiredQualityMode` と `desiredQualityModeForAdvanced` の両方に
  入れる。片方だけだと 4K 側が DR になる（実測）。形と語彙は `xsrs-api.md`、ベクタは `port/xsrs.json` の `recorder_rules`。

**番組表**
- 時刻は 1970-01-01 00:00 **JST** 起点の秒（unix 時刻 + 32400）。
- サブチャンネル（例: 総合 2）の「参照」イベントは開始・終了と親の service/event しか持たない。表示時に親の番組を引く。
- ジャンルは 3 スロット（内容ニブル + ユーザーニブル）。
- テキストは UTF-8 だが NUL 詰めと C0 制御文字が混ざる。ARIB の私用領域文字は `codes.json` の `arib_symbols` で
  `[字]` 等に置き換え（ほか と © は文の一部なので括弧なし）、それ以外の私用領域は捨てる。BS4K の一部外字は
  この表で変換する（U+1F19B〜U+1F1AC）。
- 放送日は 04:00〜翌 04:00。0 時〜4 時はまだ前日の放送日なので、番組表の最初の日は「今 − 4 時間」の日付にする
  （PWA の `tvDays()`、アプリの `GuideStore.broadcastDays`）。暦の日付で始めると、深夜に放送中の番組が
  どの日にも入らない。
- ロゴファイルは毎日深夜に作り直される。受信していない局は 1152 バイトのゼロ。PNG が IHDR の終わり（33 バイト）
  より短いものは、その局だけ飛ばす（パレットを差し込む位置が無い）。

## 端末側の設計メモ

- **番組表の扱い**: 放送種別ごと（`codes` にあるのは地デジ・BS・CS・BS4K・CS4K の 5 つ。アプリは CS4K を除く 4 つを
  取ります）に 8 日分をまとめて取り、端末内 DB に置く。受信していない種別はファイルが 416 で返るので、無いものは
  飛ばすだけでよい。全文検索は NFKC + casefold した列で。アプリはこの列に番組名・番組内容・詳細（出演者は
  詳細にしか無いことが多い）を制御文字で区切って入れ、どの欄で見つかったかで「番組名 → 番組内容 → 詳細」、
  その中は放送順に SQL で並べてから件数で切る（時刻順で切ると、番組名に語を含む数日先の番組が落ちる）。
  空白で区切った語はすべてを含むものだけ。LIKE の `%` と `_` はエスケープする。詳細だけで見つかった番組には
  語の前後を 1 行添える。列の作り方を変えたときはスキーマ番号を上げず、`meta` の印を見てその場で作り直す
  （上げるとキャッシュが消え、宅外で番組表が空になる）。サーバーの検索は番組名と番組内容のままにしてある
  （キーワード自動予約が同じ列を使うので、出演者名で予約が増えないように）。
  更新はアプリ起動時（キャッシュが古いときだけ）と手動、
  それに OS のバックグラウンド更新（iOS の `BGProcessingTask` は不定期、Android の `WorkManager` は最短 15 分）に
  頼りすぎない。古いかどうかは**種別ごと**に、レコーダーがその種別に最後に答えた時刻（ファイルが無いという答えも
  含む。`meta` の `epg_checked:<種別>`）で決め、最後の作り直しより前の種別だけを取る。いちばん新しい種別で
  決めると、1 種別だけ失敗しても新しいと見なされて翌晩まで欠けたままになり、いちばん古い種別で決めると、その
  レコーダーに無い種別のせいで接続のたびに全種別を取り直すことになる。取得は 1 種別の失敗（作り直し前の 500、
  読めないファイル）では止めずに次の種別へ進み、失敗した種別には印を付けないので次の接続でもう一度取る。
  無応答だけはそこで止める（次の種別も答えず、ファイル 1 本ごとに長いタイムアウトが掛かる）。どの種別で失敗
  したかは種別ごとに 1 行で出し、終わったら結果にかかわらずキャッシュを読み直す。
  初回の取得は全種別とロゴで時間が掛かるので、チュートリアルは番組表を取り終えるのを待たず、
  レコーダーが応答した時点で閉じる（接続の処理は分けず、応答したことを知らせるだけにする。分けると同時接続の
  ガードが外れて、クライアントが 2 つになる）。番組表は種別を 1 つ保存するたびに画面に出す（最初に取る地デジが、
  アプリが最初に開く種別）。取得中の空の番組表には、取得中であることを出す。
  空の番組表は理由を言い分ける（すべての局を非表示にしている、絞り込んだ局にその日の番組が無い、サンプルデータに
  無い種別や日、番組表に対応していない機種、その種別のファイルが無かった、まだ取得していない）。「更新ボタンで
  取得できます」で済ませると、更新しても埋まらない場合に嘘になる。
- **局の非表示と並び順**: 放送種別ごとに端末に持つ（`channel_prefs`。キャッシュとは別の表なので、スキーマ番号を
  上げても消えない）。レコーダーには送らない。番組表・表形式の列・番組の検索が従い、予約と録画の一覧は従わない。
  リストを局で絞っているときにその局を非表示にしたら、または放送種別を変えたら、絞り込みを外す（残すと空の
  一覧になり、メニューにもその局が出ないので戻し方が無い）。
- **予約の重複**: 一覧の `conflictID` が 0 でない予約は、レコーダーが重複と見ているもの。相手は教えてくれない
  ので、予約の画面には時間帯が重なるほかの予約を「時間が重なる予約」として並べる。`X_GetConflictList` の答えも
  同じ言い方にする。チューナーは複数あるので、時間が重なるだけでは録れない理由にならず、「重複」と呼ぶと言い過ぎになる。
- **送信待ちキュー**: 届かなかった予約は端末に保存し、**レコーダーに接続できたときに毎回**順に
  `X_CreateRecordSchedule` する（アプリを前面に戻したとき、深夜の更新のとき、手動の再接続のとき、ショートカットの
  アクションから呼ばれたとき）。送る先は、送信待ちを溜めたときのレコーダー（端末内 DB に控えた UDN の機体）
  だけ。別のレコーダーに切り替わったら理由を付けて止め、利用者が「もう一度送る」を選ぶまで送らない。画面の
  無い処理は、別のレコーダーが答えたら何も送らずに通知する（下の「答えたレコーダーが誰かで決める」）。捨てるのは
  **番組が終わったとき**で、始まっただけのものは送る（レコーダーは残りを録る）。レコーダーが errorCode 付きの
  SOAP fault で断ったもの（未契約の局の 831 など）は理由を付けて残し、**利用者が「もう一度送る」を選ぶまで
  送らない**（同じ答えが返るだけで、以前は接続のたびと毎晩送り直し、毎朝「受け付けませんでした」と通知して
  いた）。503（ほかの要求の処理中。クライアントが 2 回送り直したあとのもの）や errorCode の無い失敗は要求の
  中身とは関係がないので、何も書かずに残して次の機会に送り直す。途中でレコーダーが消えたら残りはそのまま次の機会へ。結果は、深夜の処理ではローカル通知
  （新しく断られたものだけを伝える）、アプリが前面で送ったときは画面上部に 1 行で知らせる（前面では通知が表示
  されない）。結果の文は規則と同じ場所にあり（`PendingQueue.Outcome` の `summary` と `says(naming:)`）、
  画面上部の行、通知、ショートカットのアクションの答えが同じ文を使う。レコーダーだけの家では、文に機器の
  名前は入らない。テレビを登録してある家では、どの機器に送ったかを入れる（「送信待ちだった「…」をレコーダーに
  登録しました」）。入れるかどうかはアプリが決め、機器の呼び名を渡す。
  実装は `app/RecorderKit/Sources/RecorderKit/PendingQueue.swift` の 1 か所だけで、画面と深夜の
  処理が同じ規則を使います。ここにあるのは、送る順番、送らない行の扱い（終わった番組は捨て、理由の付いた
  行は残す）、1 件ごとの結果に応じて行をどうするか（消す、理由を書く、そのまま残す、その回を打ち切る）
  だけです。1 件をどう送るかは機器の側にあります（`QueueTarget`。
  `DeviceEndpoint.swift`）。送信待ちは機器に 1 件ずつ送らせ、返ってきた結果（作った、すでにあった、理由を
  付けて断った、見送った、この回はここまで）を読みます。上に書いたレコーダーの送り方（作成を 1 回送り、
  無応答ならその回を打ち切り、理由の付いた断りは行に書き、それ以外は見送る）は、作成の要求だけを持つ機器
  （`ReservationTarget`）の既定の送り方です。送る前に読んでおくものがある機器のために、その回で最初に送る
  行の直前に 1 回だけ機器を読む口（`openRound`）もありますが、レコーダーは何も読みません。
  送信は端末の中で**一度に 1 つだけ**にし、2 つ目は 1 つ目が終わってから送信待ちを
  読み直す（画面と深夜の処理はクライアントも接続も別なので、同時に読むと同じ予約を 2 回作る）。
  送信待ちの各行は、**どの機器宛か**を持つ（`PendingReservation.target`。いまはレコーダーだけ）。レコーダーへの
  送信は、レコーダー宛の行だけを送る。別の機器宛の行には触らず、別のレコーダーに切り替わったときに止めるのも
  レコーダー宛の行だけ。どの機器宛の行を送るかは、呼ぶ側ではなく送る先の機器の型が言う（`QueueTarget.slot`。
  レコーダーのクライアントは `.recorder`）。
  宛先の列は、あとから足した（`ALTER TABLE`）。画面と画面の無い処理は同じファイルを
  別々に開くので、列があるかは鍵を取らずに見て、無いときだけ書き込みの鍵を取り、中でもう一度見てから足す。
  送信待ちの予約は番組表（リストと表形式）、検索結果、番組の画面にも「送信待ち」と出し、番組の画面は予約の
  入力をもう一度出さない。端末への保存に失敗したときは予約できたように閉じず、エラーを出す。
  帰宅しただけでは送られない（iOS はネットワークが来たことでアプリを起こさない）。そのためショートカットの
  アクション「送信待ちの予約を送る」を用意し、自宅の Wi-Fi に接続したときのオートメーション（iOS 17 以降は
  確認なしで実行できる）から呼べるようにする。バックグラウンドで動き、送るものがないときはレコーダーに
  何も送らない（帰宅のたびに起こさないため）。送るものがあれば起こして `PendingQueue` で送り、結果を通知する。
- **LAN の判定**: 保存した UDN の `description.xml` が保存ホストで取れるか、駄目なら探索し直す（`services/session.py`
  の `resolve_recorder` と同じ順序）。iOS アプリも、つながったレコーダーの UDN を端末内 DB の `meta`
  （`recorder_udn`）に控えますが、使うのは「答えたのがどのレコーダーか」を見分けるためです（下の「答えた
  レコーダーが誰かで決める」）。移ったレコーダーの探し直しは、起こすために控えている有線 MAC で照合します。
  UDN の末尾 12 桁と同じなので、UDN を控える前のインストールでも移行なしで探せます。
  - 探すのは、保存アドレスがマジックパケットの起動待ちのあとも黙っていたときに、**同じ接続の中で 1 回だけ**です
    （接続の途中でネットワークが変わってやり直したときは、そのやり直しでもう 1 回）。
    UDN の末尾がその MAC の機体が見つかった時点で残りのアドレスは打ち切り、そのアドレスに移って接続します。
    見つからなければ下の「諦めたら諦めたままにする」のとおり諦め、繰り返しません。走査は /24 で数秒、起動待ちの
    30 秒のあとに足されます。
  - 走査するのは、保存アドレスが属する Wi-Fi のサブネットだけです。DHCP が動かすのはそのサブネットの中なので、
    保存アドレスが今の Wi-Fi のサブネットに無いとき（外出先、よその Wi-Fi、VPN 越し）は走査しません。
  - MAC を読んだときのアドレスも控えておきます。利用者が別の機体のアドレスを入れた直後は、MAC はまだ前の機体の
    もので、そのマジックパケットで起きた前の機体を見つけて黙って元に戻ってしまうからです。控えたアドレスが
    保存アドレスと違う間は照合しません（控えが無いときは照合します。以前の版は控えていないためです）。
    別のレコーダーが説明を返し、その UDN の末尾が控えている MAC でなければ、MAC も忘れます（新しい機体の MAC は
    同じ接続の中で読みます）。それまでは前の機体の MAC が残るので、新しいアドレスが黙っている間のマジック
    パケットは前の機体に届きます。
  - ローカルネットワークの許可は、起こす前に保存アドレス（同じサブネット）で確かめ済みです。拒否されていれば
    そこで許可を待つので、走査が確認ダイアログの裏で空振りすることはありません。バックグラウンドとサンプル
    データのモードでは走査しません。
  - 接続できないときの画面（番組表・予約・録画）には、再接続の下に控えめな「レコーダーを探す」を置き、
    チュートリアルの検索に戻れるようにしています。照合できないとき（一度もつながっていない、1 桁違いの
    アドレスを入れた）や、見つからなかったときの逃げ道です。
- **別のアドレスを選んだら、前のレコーダーのことは忘れる**: 利用者がレコーダーを選び直したとき（探して選ぶ、
  アドレスを入力する。`AppModel.adopt`）、今のアドレスと違うアドレスなら、**接続を試す前に**、前のレコーダーが
  言ったことを端末のメモリから消します。機種・ファームウェア・残容量・電源が要るという印
  （`SessionState.forgotTheDevice`）、予約、録画、おまかせ・まる録の一覧、重複の組とそのチェック、
  読んだ番組内容、終わった一括処理の結果、画面に出ていたエラーと送信待ちの結果の行です。一覧の絞り込み
  （ジャンル、視聴状態、予約の種類）も元に戻します。
  接続は試みのたびに、そのときのアドレスで新しいクライアントを作るので、消さないと、前の機体の一覧が、新しい
  アドレスに向いたクライアントの上に残ります。録画一覧は「読み込み済み」のままで読み直されず、そこから削除や保護を
  押すと、前の機体の ID が新しいアドレスに送られていました。新しいアドレスが説明を返さなかったとき（ほかの要求の
  処理中で 503、レコーダーではない機器）は前の機体の説明も残り、前の機体に接続中と見えたまま、要求だけが
  新しいアドレスに行っていました。
  - 同じアドレスを選び直したときは何も消さず、再接続と同じ動きをします。入力を整えたうえで、大文字と小文字を
    区別せずに比べます（`RecorderAddress.same`）。比べるのはアドレスだけです。同じ機体が別のアドレスに移った
    だけのときも、消して読み直します。探して見つけた行は、UDN が同じなら「使用中」と出ますが、選ぶときには
    見ていません。消さないのは、アプリが自分で探し直して移ったとき（上の「LAN の判定」）だけです。
  - 消えるのは一覧だけではありません。重複の組と、利用者が付け外ししたチェック、終わった一括処理の結果、
    絞り込みも消えます。アドレスを打ち間違えて直したときも同じで、重複の検出はやり直しになります（番組内容は
    端末に残っているのでレコーダーには聞き直しませんが、チェックは付け直しです）。別の機体の録画が画面に
    残るよりは軽い、という判断です。
  - 選んだ時点で消すのはメモリの中だけです。端末内のデータベース（番組表、録画の番組内容、送信待ち、
    チャンネルの設定）、MAC、並び順と放送波の選択は、新しいアドレスで何かが説明を返すまで残します。アドレスを
    打ち間違えても、黙っているかレコーダーでない機器が答えるだけなら、端末の中は何も変わりません。説明が
    返ったあとは、答えたのがどのレコーダーかで決めます（下の「答えたレコーダーが誰かで決める」）。サンプル
    データのモードの出入りでも同じものを消しますが、こちらはデータベースごと切り替わります。
  - 送信待ちは利用者のものなので残します。次に説明を返したレコーダーが、送信待ちを溜めたときのレコーダー
    （UDN が同じ）なら、その接続が送ります。別のレコーダーなら理由を付けて止め、利用者が「もう一度送る」を
    選ぶまで送りません（下の「答えたレコーダーが誰かで決める」）。503 だけを返した機器や、レコーダーではない
    機器は、応答はしているので画面は無応答として扱いませんが、どの機体かを言っていないので送りません。この
    状態は、選び直さなくても起きます（接続のときに、レコーダーがほかのアプリの相手をしていて 503 を返した）。
    そこで、予約一覧の引き下げ更新と、送信待ちの「もう一度送る」は、**接続していなければ接続し直します**
    （`AppModel.refreshReservations`、`resend`）。説明が返れば、その接続が送信待ちを送ります。以前の引き下げ
    更新は、無応答でなければ一覧を読んでから送信待ちを送っていたので、説明を返していない機器にも届いていました。
  - 操作の前の確認（下の「操作の前に起こす」）の最中は、選び直しも、サンプルデータの開始・終了も受け付けません。
    確認は始めたときのクライアントで続くので、起きた前の機体が、新しいアドレスの機体として接続されてしまう
    からです。
  - 選び直したときに、前の機体への要求がまだ返っていないことがあります。帯に行を出さない要求（録画の番組内容、
    予約の重複の確認）は、選び直しを止めないからです。あとから届いた無応答やエラーは前の機体のものなので、
    今の機体の無応答としては扱わず、画面にも出しません（要求を出したクライアントが今のものかで見分けます）。
    以前は、選んだばかりの機体が「接続していません」になっていました。接続し直しただけのときも同じです。
- **答えたレコーダーが誰かで決める**: アドレスは叩く場所にすぎません。どのレコーダーかは、`description.xml` が
  返した UDN で決めます（`Recognition`: 初めて・同じ・別。大文字と小文字は区別しません）。控えは 2 つです。
  メモリの一覧をどの機体から読んだか（`SessionState.device`。無応答の間も残り、選び直しの `forgotTheDevice` で
  消える）と、端末内 DB がどの機体のものか（`meta` の `recorder_udn`。`GuideStore.owner`）。説明が返るたび
  （`RecorderDriver.attach`）に、一覧を読んだり送信待ちを送ったりする前に、この 2 つと比べます。
  - 同じ UDN なら、どのアドレスで答えても端末のものは何も消しません。番組内容、番組表とその取得の印、残容量の
    通知の印、MAC はそのままで、送信待ちもそのまま送ります。DB には何も書きません（読むだけで分かるので、
    深夜の更新などほかの書き込みを待たされません）。
  - 別の UDN なら、前の機体のものは渡しません。メモリでは、説明が届いたのと同じターンで一覧を消し
    （`forgetWhatTheRecorderSaid`。選び直しのときに消すものから、説明とクライアント、画面に出ていたエラーを
    除いたもの。エラーは、その接続が最後まで進んだときに消えます）、接続済みの
    ままだったときは、読んであった録画とおまかせ・まる録の一覧をその接続の中で読み直します
    （`readAgainWhatWasUp`。画面は「接続済みになった」ことをきっかけに読むので、接続済みのままだと誰も
    読み直さない）。端末内 DB では 1 つのトランザクションで（`GuideStore.claim`）、録画の番組内容、番組表（局・
    番組・ロゴ）と `epg_refreshed:` / `epg_checked:` の印を消し、レコーダー宛の送信待ちの各行に理由を書いて止め、持ち主の
    UDN を書き換えます。`UserDefaults` の残容量の通知の印と最終自動更新の時刻も消します。番組表は空になり、
    同じ接続の `refreshGuideIfStale` が全種別を取り直します（その機体に無い種別は、前の機体の番組を残さず
    空のまま）。MAC は、新しい UDN の末尾がそれでなければ忘れ、同じ接続の中で新しい機体のものを読みます。
  - DB を書き換えられなかったとき（ほかの書き込みが長く続いている、空き容量が無い）は、その機体には接続
    しません。接続すると、前の機体の番組表や番組内容の上で動いてしまうからです。理由を画面に出し、次の接続で
    やり直します。クライアントも手放します（選び直しの直後と同じ、誰にも聞けない状態）。残すと「応答は
    あるが接続していない」機器として扱われ、画面に残っている前の機体の番組表から予約すると、その機体に
    送られていました。手放したあとの予約は送信待ちに入り、持ち主が替わった時点でほかの行と同じく止まります。
  - 止めた送信待ちは、各行に理由を出し、帯に「別のレコーダーに切り替わったため、送信待ちの予約 N 件は送らずに
    残しています」と出します。止まっている行がある間は、送信待ちを送るたびに出します（止めた接続が最後まで
    進まなかったときも次の接続で伝わるように、行から数えます）。「もう一度送る」でいまの機体に送れます。黙って
    別の機体に入れるのも黙って捨てるのも違う、という判断です。以前に別の理由で断られていた行も、同じ理由に
    書き換わります。
  - 操作の前の確認（下の「操作の前に起こす」）でも比べます。プローブに別の機体が答えたら、その操作は行わず
    （画面には「別のレコーダーが応答したため、この操作は行っていません」）、一覧を消して、新しい機体は別の
    接続で取り込みます。起動待ちの末に別の機体につながったときも同じです。予約の登録も、このときは送信待ちに
    入れません（入れると、前の機体のための予約として止まるか、新しい機体に送られます）。実行中の一括処理や
    重複の検出は次の 1 件に進む前に止め、接続はそれが終わってから始めます。前面で動いている一括処理も、
    確認が出ている間は次の 1 件を始めずに結果を待ちます（`readyForNextStep`）。確認の問い合わせは実行中の
    1 件の後ろに並ぶので、待たないと、結果が届く前に次の 1 件が別の機体に届きます。すでに送った 1 件は
    止められません。
  - メモリの一覧を消したことは、画面にも伝えます（`AppModel.timesForgotten`）。開いたままの録画や予約の画面、
    削除の確認に選んだ行は前の機体のものなので、閉じます。閉じないと、空になった一覧の上に残った画面の
    ボタンが、前の機体の ID を新しい機体に送ります。機体の行を持つ画面（録画 1 件、番組ごとの録画、予約
    1 件）は、どこから開かれたかに依らないように、自分で閉じます。番組の画面は放送のものなので残しますが、
    削除の確認に選んだ予約と、前の機体が答えた「時間が重なる予約」は捨て、次の機体につながったら聞き直します。
    検索の画面は、予約と録画の一覧を「接続済みになった」ときにも読みます（一覧を消された画面が前面に
    あると、ほかに読み直すきっかけがありません）。
  - 利用者が選んでいないのに別の機体が答えたとき（一覧を持ったままの接続、操作の前の確認）は、帯にも出します
    （`AppModel.anotherTookOver`。「別のレコーダーが応答したため、一覧を読み直しました。操作の途中だった場合は、
    確かめてからやり直してください」）。操作を行わなかったことはエラーの行でも伝えますが、その行は続く接続で
    消え、操作を始めた画面が上のとおり閉じると、その中のアラートも一緒に閉じます。帯はどの画面でも読めるので、
    利用者が閉じるか、アプリを離れるか、レコーダーを選び直すまで残します。出すのは接続している間だけです
    （新しい機体がすぐ黙ったときは、読み直していないので、再接続の帯を先に出します）。
  - 画面の無い処理（深夜の更新、ショートカットのアクション）は、端末内 DB の持ち主と違う機体が答えたら、何も
    送らず、取らず、消しません（`RecorderDriver.isTheOneKnown`）。持ち主を読めなかったときも同じです。送るものが
    待っていたときだけ、別のレコーダーが応答したので送っていないと通知します。取り込むのは画面のある接続
    だけです。
  - UDN を返さない機器は見分けようがないので、控えている機体と同じとみなします（答えるたびに忘れる方が害が
    大きい）。
  - 持ち主の UDN を控える前のキャッシュ（以前の版）は、誰のものかを言いません。推測はせず、最初に説明を
    返した機体を持ち主として控え、中身はそのままにします。起こすために控えている MAC を UDN の末尾と比べれば
    見分けられる場合もありますが、末尾が MAC だと確かめたのは 1 機種だけで、MAC は利用者が手で入れることも
    あります。外れると、レコーダーが 1 台しかない家で、更新した日に番組内容が消え、送信待ちが止まります。
    ただし、メモリの一覧を別の機体から読んでいたと分かっているとき（`SessionState.device`）は、持ち主が
    書かれていなくても別の機体のものとして引き継ぎます（`claim` の `knownToBeAnother`。最初の機体の UDN を
    書き込めないまま、次に別の機体が答えた場合です）。
  - サンプルデータのモードでは比べません（キャッシュが別で、終了時に消える）。実機のキャッシュの持ち主、
    番組内容、通知の印は、サンプルの出入りで変わりません。
  - 残っていること。同じアドレスで別の機体が答えたら、利用者が選んでいなくても取り込みます（機体の入れ替え、
    DHCP の割り当て直しのほか、よその家の同じアドレスのレコーダーでも同じです）。2 台を行き来すると、その
    たびに番組内容と番組表を消して取り直し、送信待ちは止まったままになります（どの機体のための行かは控えて
    いません）。同じ機体がディスクの初期化などで録画の ID を振り直すと、古い番組内容が残ります。新しい
    アドレスを選んでから最初の説明が返るまでに溜めた送信待ちも、新しい機体のための予約なのに止まります。
    同じアドレスの機体が入れ替わったあと、画面の無い処理は、アプリが開かれるまで送信待ちを送りません（通知で
    知らせます）。深夜の更新の最中に画面で別の機体を取り込むと、深夜の更新が前の機体の番組表を新しい
    キャッシュに書くことがあります（次の夜に直ります）。接続の途中、説明が返るまでの一瞬に確定した操作は、
    照合の前に送られます。確認や接続の問い合わせに、機器が説明ではなく 503 などで答えたときは、誰が答えたか
    分からないまま、それまでの機体として扱います（以前からの動作で、直後の操作は照合なしで送られます）。
    以前の版で 2 台を使い分けていた端末は、更新した時点のキャッシュに別の機体の番組内容が混ざっていても、
    最初に答えた機体のものになります（次に機体を切り替えたときに消えます）。
- **諦めたら諦めたままにする**: レコーダーが沈黙したときの再試行は、**この端末が持っているアドレスが変わったとき**
  （別の Wi-Fi、VPN の上がり下がり、セルラーへの切り替え）と、利用者が明示的に頼んだとき（再接続・レコーダーを
  探す・引き下げ更新）だけにします。同じネットワークでは答えは同じで、1 回の試行にタイムアウト（マジックパケット →
  5 秒の確認 → 無応答なら最大 30 秒の起動待ち。待つ間は、2 秒で打ち切る確認を 1 秒おいて繰り返す）が掛かるうえ、
  クライアントは要求を直列化するので、画面ごとに読み込みを始めると数分間スピナーが回り続けます。
  `NWPathMonitor` はもっと細かい理由でも発火するので、
  判断はインターフェースのアドレス一覧で行います。セルラー（`pdp_ip`）のアドレスは一覧に入れません。キャリアは
  自宅の Wi-Fi にいる間も勝手に付け替えるので、数えるとそのたびに 35 秒の起動待ちが走ります。Wi-Fi が
  切れれば Wi-Fi の側が変わるので、セルラーへの切り替えはそれで分かります。接続していないことは画面に出し、
  再試行の入口を添えます。諦めるのは無応答のときだけで、503 や SOAP の Fault のように答えがあったときは
  諦めません（レコーダーはそこにいて、何が悪いかはもう画面に出ています）。接続の途中でネットワークが変わった
  とき（家に着いて Wi-Fi につながった、VPN が上がった）は、接続の最後にアドレス一覧を比べ、変わっていれば
  **同じ接続の中で 1 回だけ**やり直します。接続中は変化の通知を受けても何もしないので、やり直さないと、来た
  ばかりのネットワークで諦めたままになります。
  変化の通知は、アドレスが揃う前に来ます。IPv6 もあるネットワークでは IPv4 のアドレスが付く前に経路が
  使えるようになって通知が来て、アドレスが付いたときには何も来ません。通知の瞬間だけ比べると変化が見えず、
  Wi-Fi に戻っても諦めたままでした。そこで通知のあと 30 秒ほど何度か見直し、試行を 1 回始めたらやめます。
  処理中に来た通知も捨てず、「前回の試行のあとに別のネットワークにいた」ことを通知の時点で覚えておきます。
  要求の途中で Wi-Fi が切れて戻ると、前後のアドレスは同じでも、無応答は家の外で受けたものだからです。
  無応答で諦めるときに、試したネットワークを終わった時点のものに書き換えないのも同じ理由です。
  アプリに戻ったときの再接続は、実際にバックグラウンドに回ったあとだけにします。コントロールセンター、通知センター、アプリスイッチャー、
  システムのアラートでもアプリは非アクティブになりますが、どこにも行っていないので数えません。
  接続していて、最後の応答から 1 分以内なら、戻っても接続し直しません（少し別のアプリを見て戻るたびにマジック
  パケットを送らないため）。処理の途中や、操作の前の確認の最中は、2 つめのクライアントを作らないよう、接続は
  せずにネットワークを見直すだけにします（`LinkRules.onReturn`）。
- **表示するだけの値で接続の成否を決めない**: 接続できたかどうかは `description.xml` だけで決めます。
  続けて読むファームウェア（`X_GetFirmwareVersion`）、MAC（`X_GetPrivateIp`）、残容量は、BDZ-FBT4100 は答えますが
  シリーズのほかの機種が同じように答えるとは限りません。断られたり形の違う答えが返ったりしたら値を「不明」にして
  接続を続け（設定の行を出さない）、無応答のときだけ接続の失敗にします（`RecorderError.silenceOnly`）。以前は
  これで接続全体が失敗し、レコーダーが答えているのにエラーが出て、送信待ちも予約一覧も番組表も取りませんでした。
  残容量は、数値が 2 つとも読めなければ 0 とせずエラーにします（0 と読むと「残り 0.0 GB」と出て、容量不足の
  通知まで出ていました）。合計が 0 のときも不明として扱い、通知は出しません。削除のあとに読み直す残容量が
  読めなくても、削除は成功として扱います。
  接続済みになるのは `description.xml` が読めた時点ですが、それまでの無応答の印は、続き（ファームウェア・MAC・
  残容量）を読み終えるまで残します。そこで、画面が一覧を読み込むきっかけは「接続済みで、無応答の印も無い」に
  します。接続済みだけをきっかけにすると、起こした直後に読みに行って空振りし、そのあと読み直すきっかけが
  ありません（起動待ちの間に録画の画面を開いていると、起きたあとも一覧が空のままでした）。予約の画面も同じ
  きっかけにしています。予約一覧は接続そのものも読むので空にはなりませんが、操作の前の確認で起こしたあとは、
  送信待ちを送ったときと、操作そのものが読むとき（予約の変更・削除）を除いて、誰も読み直さず、眠る前の一覧が
  出たままでした。
- **使っている最中に眠る**: レコーダーは何もしないと 15 分ほどで LAN から消えるので、アプリを開いたままでも
  眠ります。そのままにすると、番組を開けば重複の確認で 30 秒、予約で 30 秒待たされ、家にいるのに送信待ちに
  なります。
  - **無応答は 1 か所で受ける。** どの要求（一覧の読み込み、重複の確認、予約の作成・変更・削除、録画の操作、
    一括処理、重複の検出、送信待ちの送信）でも、無応答を受けたら接続に失敗したときと同じ状態（未接続・諦めた）
    にします。そうしないと、アプリはつながっているつもりのまま画面ごとに同じタイムアウトを待ち、再接続の入口も
    出ません。一括処理と重複の検出は最初の無応答で止めます。
  - **書き込みは送り直さない。** 無応答でも、要求はレコーダーに届いていることがあります。予約を送ったあとに
    無応答になったものは送信待ちにも入れず、再接続してから一覧で確かめるよう伝えます（送信待ちに入れると、次に
    つながったときに同じ予約をもう一度作ることになります）。送信待ちに入るのは、何も送らないうちに無応答が
    分かったものだけです。例外は送信待ちを送っている途中の無応答で、そのとき送っていた 1 件は `PendingQueue`
    の規則どおり送信待ちに残り、次の機会にもう一度送られます（深夜の処理も同じです）。
  - **操作の前に起こす。** クライアントは最後に応答を受けた時刻を持ちます（SOAP の Fault も応答に数えます）。
    利用者の操作の前に 90 秒以上空いていたら、**今のクライアントのまま**マジックパケットと 5 秒のプローブを
    送り、黙っていれば接続時と同じ起動待ちに入ります。起きていればミリ秒で終わります。ここで接続し直すと
    クライアントが 2 つになり、2 本のキューがレコーダーに同時に話しかけて 503 になるので使いません。接続中に
    端末のネットワークが変わったときも、最後の応答はもう当てにならないので、同じ確認をします。
- **一括処理**: 削除・保護はキューで 1 件ずつ、進捗と「中止」を出す（中止は次の 1 件から止める）。アプリが
  バックグラウンドに回ると OS がまもなく止めるので、その旨（離れると一時停止し、戻ると再開する）を表示する。
  止められた途中の要求は失敗として返り、削除が届いたかどうか分からないまま処理が止まるので、処理中の 1 件だけは
  バックグラウンドタスク（iOS の `beginBackgroundTask`）で終わらせ、次の 1 件の前で待ちます。前面に戻ったら、
  離れていた間に眠ったかもしれないレコーダーを確かめてから続けます。処理中は接続し直しません（クライアントが
  2 つになり、2 本目への 503 を「レコーダーではない」と読んで諦めていた）。
- **重複の削除**: チェックを付けたものが消え、チェックの無いものが残る。「残す」の札は提案した 1 本ではなく
  チェックの無い行に付け、全部にチェックが付いた組があれば、その組の名前を出して削除しない。自動で
  チェックを付けるのは番組内容まで一致した組（`high`）だけ。毎回同じ説明文を載せる番組（毎朝の短い番組、
  ミニアニメ）は別の回でも説明文が一致するので、説明文が 20 字未満（`summary_key` で数える）か、番組表の
  キャッシュに同じタイトル・同じ説明文が別々の放送日（4 時区切り）に 2 回以上あれば `boilerplate` とし、
  チェックを付けない（`fixed_blurbs`）。同じ日の 2 回は数えない。1 週間以内の同じ回の再放送も定型文と
  見なされるが、チェックが付かない側に倒れるだけなので許す。番組表は重複の検出のたびに読み直す。
  組を作り直したとき（1 件ずつの削除・保護、一括処理、一覧の再読み込みのあと）は、前と同じ録画でできていて
  確度も同じ組だけ利用者のチェックをそのまま残し、処理中はチェックを変えさせない。番組内容は**読めたものだけ**を
  保存する（空の本文も答えのうち）。820 はレコーダーから消えたものなので一覧から外し、それ以外の失敗は保存せず、
  組にも入れない。`port/titles.json` のベクタは要約の無いものを空として扱う（サーバーと同じ）ので、この絞り込みは
  その手前で行う（RecorderKit では `Duplicates.readSets`。削除を持ちかける画面は `Duplicates.sets` を直接呼ばず、
  これを使う）。一括削除で 820 が返った録画は「すでに削除されています」として飛ばし、一覧からも外す
  （`ItemOutcome.gone`。理由の文言の比較で見分けない）。サーバーの `services/titles.py` は今も失敗を空として保存します。iOS アプリは、以前の版が
  失敗を空として保存した行を一度だけ消します（`meta` の `blank_summaries_cleared`）。
- **iOS の権限**: LAN への平文 HTTP は `NSAppTransportSecurity` の `NSAllowsLocalNetworking` で許可する。LAN
  アクセスの説明文 `NSLocalNetworkUsageDescription` も必須。SSDP のマルチキャスト送信には
  `com.apple.developer.networking.multicast` エンタイトルメントが要り、Apple への申請が必要。**TCP スキャンだけなら
  不要**なので、まずはスキャンで作る。
- **ローカルネットワークの許可**: iOS は、アプリが初めて LAN に触れたときに利用者へ確認を出します。URLSession は
  確認が出ている最中にも、拒否されたあとにも、圏外と同じ -1009 ですぐに失敗するので、そのまま走査すると確認の裏で
  空振りし、「見つかりません」と出て、許可したあとにもう一度押させることになります。Network framework なら区別が
  つきます。同じサブネットの宛先へ `NWConnection` を張り、経路が `.satisfied` になったら許可済み、
  `unsatisfiedReason` が `.localNetworkDenied` の間は許可されていない、と読めます（TN3179）。許可されると
  システムがその接続をやり直すので、答えを待ってから走査を始めれば 1 回のタップで見つかります。
  - 確認が出ている最中に経路が何を返すかは文書になく、拒否されたあとと区別できる保証もありません。表示は
    どちらにも正しい文言にし（「許可されていません。許可されると、そのまま検索が始まります」）、設定アプリの
    アプリ自身のページ（`UIApplication.openSettingsURLString`）を開くボタンを添えます。一度拒否されると、
    アプリからは二度と確認を出せません。
  - 確認はボタンを押したときに出し、起動時には出しません。手順の説明を読む前にダイアログが重なり、サンプル
    データで試す人と審査担当にも見せることになります。サンプルデータのモードでは LAN に一切触れないこと。
  - 保存済みのアドレスが黙ったときも、起こす前に同じ確認をします。拒否されていればマジックパケットも出ていかない
    ので、起動待ちには入らず、許可を待って接続し直します。許可の変更はネットワークの変化として見えないため、
    「諦めたら諦めたままにする」の唯一の例外になります（利用者自身の操作がきっかけなので矛盾しません）。
  - バックグラウンドの処理（深夜の更新）ではこの確認をしません。未決定のまま通信すると黙って拒否され、その
    ことはどこにも残りません。
- **通知の許可**: 通知はどれも深夜の処理から出ます（送信待ちの結果と残容量の警告）。許可を送信待ちのときにしか
  求めないと、家でしか使わない人には一度も確認が出ず、残容量の警告が届きません。iOS アプリは、初めて実機に
  つながったあとに provisional の許可（`.provisional`）を取ります。ダイアログが出ないので、最初の接続の前後に出る
  ローカルネットワークの確認と重なりません。通知は通知センターに目立たない形で届き、利用者はそこで残すか止めるかを
  選べます。正式な確認のダイアログは、予約を送信待ちに**保存したあとで**出します。先に聞くと、答えを待つ間に予約が
  保存されないままになるためです。設定画面には許可の状態と、通知の設定
  （`UIApplication.openNotificationSettingsURLString`）を開くボタンを置きます。サンプルデータのモードでは許可を
  取りません。
  - 残容量の警告は閾値を切るたびに 1 回だけ出しますが、出したと記録するのは通知が許可されているときだけです。
    許可が無いまま記録すると、あとで許可しても、容量が戻ってまた切るまで届きません。
  - 深夜に出すので音は鳴らさず、`interruptionLevel` を `.passive` にして画面も点けません。
- **Android に移植する場合の権限**: `android:usesCleartextTraffic="true"` またはネットワークセキュリティ設定で LAN を
  許可し、SSDP には `WifiManager.MulticastLock` を取る。
- **Wake-on-LAN**: Android はブロードキャスト UDP をそのまま送れます。iOS は、マルチキャストのエンタイトルメントが
  無いアプリのブロードキャストを止めると文書にありますが、止めている箇所（xnu の `bsd/net/necp.c`、
  `necp_check_restricted_multicast_drop`）を読むと、落とすのは 224.0.0.0/4 と `255.255.255.255` だけで、
  サブネットのブロードキャスト（x.x.x.255）とユニキャストは通します。つまり iPhone では `255.255.255.255` 宛てだけが
  毎回 `EHOSTUNREACH` で失敗する見込みです。実機ではまだ確かめていないので、アプリは宛先ごとの結果と errno を
  デバッグログ（サブシステム `RecorderKit`、カテゴリ `wake`）に出しています。ローカルネットワークの許可が無ければ、
  どの宛先にも送れません。MAC は端末から ARP を読めませんが、
  **レコーダーに聞けます**（`X_GetPrivateIp` の `macAddress` / `wirelessMacAddress`、あるいは `description.xml` の
  UDN 末尾 12 桁）。つながっているうちに控えて保存し、次からはそれで起こします。入力欄は「一度もつながって
  いない機体」のための逃げ道として残す程度で十分です。送り先はリミテッドブロードキャスト・レコーダーの
  サブネットのブロードキャスト・**レコーダーのアドレス宛のユニキャスト**の 3 つ（VPN 越しに届くのは最後の 1 つ）。
- **待っていることを画面に出す**: 起こしてから応答までは実測 6〜11 秒、VPN 越しではもっと掛かります。何も出さない
  と故障に見え、「失敗 → 再試行」に見せるのも同じくらい悪いので、マジックパケットは最初のプローブより前に送り、
  待っている間は経過秒数を出し続けます（ボタンを 1 秒ごとに有効／無効させないこと）。マジックパケットは待って
  いる間も 5 秒ごとに送り直します。届いたかどうかは誰も答えず、1 通落ちると、起きないレコーダーを 30 秒
  待って諦めることになります。待つ処理は `app/RecorderKit/Sources/RecorderKit/Waking.swift` の 1 か所だけで、
  画面、深夜の処理、ショートカットのアクションが同じものを使います（待つ長さは、画面が 30 秒、見ている人の
  いない深夜の処理とショートカットが 60 秒）。深夜の処理とショートカットも、パケットを最初のプローブより前に
  送り、次のパケットはそこから数えて送ります。1 回の試みの順番（パケット → 短い確認 → 無応答ならローカル
  ネットワークの許可を確かめる → 起こして待つ → それでも無応答なら別のアドレスを 1 回だけ探す）も
  `app/RecorderKit/Sources/RecorderKit/Reach.swift` の 1 か所で、接続、操作の前の確認、深夜の処理、ショートカットが
  同じ順番を使います（許可を確かめるのは画面のある 2 つだけ、別のアドレスを探すのは接続だけ）。エラーで答えた
  機器は「いる」ので起こしも探しもしませんが、画面のない 2 つ（深夜の処理とショートカット）は、最初の確認に
  エラーで答えたときも起こして待ちます（アドレスがアドレスになっていないときを除く）。起動の途中の機器は何を
  返すか分からず、待ちを見ている人もいないからです。
  画面のある側の接続、操作の前の確認、無応答と諦め、許可を待つかどうかの判断は、機器に共通の
  `app/RecorderKit/Sources/RecorderKit/DeviceLink.swift` にあり、レコーダーに固有の手順（答えた機体の照合、
  起こして待つ、移った機体の探し直し）は `RecorderDriver.swift` にあります。アプリが受け持つのは、画面の行と
  一覧、端末に保存するもの、許可が下りるのを待つ見張り、LAN に出る口（サンプルデータのモードでは何も出さず、
  背景では走査しない）です。LAN が要る規則は、偽の外界を渡す `DeviceLinkTests` が確かめます。画面のない 2 つの
  試みも `RecorderDriver.reachWithNoScreen` にあり、マジックパケットの送り方だけをアプリから受け取ります
  （`NoScreenReachTests` は偽のパケットで確かめます）。テレビ（ソニーの BRAVIA）は同じ `DeviceLink` に
  `TVDriver.swift` を載せ、レコーダーのリンクとは別に動きます。テレビとの通信（Scalar の JSON-RPC、PIN での登録と
  cookie）は `ScalarClient.swift` にあります。テレビは起こさず、待機中も答える `getPowerStatus` で確かめます。
  どのテレビかは保存した Wake-on-LAN の MAC で見分け（起動して最初の応答から）、cookie の更新はアプリが前面に
  あるときだけ行います。テレビの録画予約の一覧と削除も `TVDriver.swift` の手順で、結果ごとの文もそこにあります。
  一覧の 1 行の読みと、消す前に同じ予約かを確かめる規則（番号と番組の両方が合うこと）は `TVSchedule.swift` です。
  テレビに予約を入れるための要求は 3 つで、どれも `ScalarClient.swift` にあります。局の一覧
  （`avContent.getContentList` 1.0、50 局ずつ）、その予約を入れると録れなくなる予約の問い合わせ
  （`recording.getConflictScheduleList` 1.0）、作成（`recording.addSchedule` 1.1）です。送る中身のテレビ側の綴りは
  `TVReservation.swift` にあり、測って分かった規則もそこに書いてあります。局の uri は一覧で返ったものをそのまま送り、
  組み立て直しません。番組の局（放送の種別とサービス ID）と違う局には、本文を作りません（番組 ID はその局の中でしか
  意味を持たないため）。開始の時刻はレコーダーの `+09:00` ではなく `+0900`、番組 ID は 10 進の文字列、長さは数で、
  録画モードは送りません。番組名での繰り返しは `title` です。毎週の繰り返しは番組の曜日（日本時間）のものだけを送り、
  月−金は土日の番組に、月−土は日曜の番組に送りません。午前 4 時より前に始まる番組には、曜日の入る繰り返しを
  どれも送りません（放送の 1 日と暦の 1 日がずれる時間帯で、測っていないため）。局の一覧は、どの頁で失敗しても
  読めなかったことにします（途中までを返すと、その先の局が「テレビに無い」ことになるため）。問い合わせの答えが
  読めないときも、「何も録れなくならない」とは読みません。作成の応答が言うのは `annotation` という数だけで
  （測った限りは 0）、そのまま返します。テレビへ送る本文は、鍵を並べて書きます（`.sortedKeys`）。
  辞書には順序が無く、そのままでは同じ要求のバイト列が起動のたびに変わり、実機で確かめたものと出荷するものが
  同じになりません。この 3 つの要求を使うのは、下に書く「送信待ちの 1 件をテレビに送る手順」だけで、アプリは
  まだその手順を呼びません。
  アプリ自身のクライアントから実機に送って分かったこと: 局の一覧は、終わりの先の頁を聞くと空の頁が返ります。
  作成は受け付けられると `annotation` 0 を返し、一覧には送った項目がそのまま（録画モードは DR で）載りますが、
  題名はテレビが番組表から付け直します。同じ番組の 2 回目は 41222 で、何も作られません。契約していない局への
  作成と、番組の曜日と合わない毎週の作成は、どちらもエラー 7 で断られます。毎日・月−金・月−土は、テレビの
  予約一覧にそのとおりの言い方で出ます。同じ時刻に 3 件目を入れると、問い合わせはいちばん先に作った 1 件を名指しし、
  作成は通って、その 1 件が録れない状態（`fullyOverlapped`）になります。視聴予約は名指しされませんが、作成のあと
  一部重なり（`partlyOverlapped`）に変わることがあります。受け付けられない cookie での作成は 403 で、何も
  作られません。
  送信待ちの 1 件をテレビに送る手順も `ScalarClient.swift` にあり、送信待ちが機器に頼む形（`QueueTarget` の
  `openRound` と `send`）で書いてあります。レコーダーは作成の要求 1 つで済みますが、テレビは作成に、何を
  作ったかも、何を録れなくしたかも答えません。そこで前後に読みます。規則は次のとおりで、実機の答えで確かめた
  ものに（測）、確かめていないものに（未測）と書きます。
  回の初めに、録画用のディスクと予約の一覧を読みます。ディスクが無ければ、何も送らずにその回をやめ、行には何も
  書きません（ディスクが戻れば、そのまま送られます）。一覧に、行と同じ局で同じ番組 ID の録画予約があれば、その行は
  送らずに「すでにある」として送信待ちから外します。題名でも開始の時刻でも探しません。題名はテレビが付け直し
  （測）、番組を追う予約は開始が動いてもその番組のものだからです。視聴予約は録画しないので数えません。ただし、
  毎回録画を頼んだ行に対して、テレビにある予約がそれに足りないときは、外しません。外すと、残りの回の番組が
  予約されないまま、何も言わずに送信待ちから消えるからです。足りないのは、テレビにあるのが 1 回だけの予約
  （`repeatType` が `1` か、書かれていない）のときと、テレビにある毎回録画の曜日が、頼んだ毎回録画の曜日の
  一部でしかないときです。毎日を頼んだ行には、毎週・月−金・月−土のどれも足りません。月−土を頼んだ行には、
  月−金と、月曜から土曜までの毎週が足りません。月−金を頼んだ行には、月曜から金曜までの毎週が足りません
  （毎日・月−金・月−土は、テレビ自身の予約一覧がそう言い表します。毎週は、月曜・木曜・日曜の符号を番組の
  曜日で確かめました。測）。その行は、何も聞かずに、テレビの予約を削除してから「もう一度送る」を選ぶよう
  書いた理由を付けて、保留にします（テレビにある予約を書き換える操作は、まだ無いため）。理由の文は、1 回だけの
  予約のときと、曜日の少ない毎回録画のときとで別です。ほかの組み合わせは「すでにある」のままです。1 回を
  頼んだ行にテレビの毎回録画があるとき、同じ毎回録画があるとき、頼んだ曜日をすべて含む毎回録画があるときは、
  失うものがありません。番組名での毎回録画（`title`）は、頼んだ側でもテレビにある側でも、1 回だけの予約としか
  比べません。名前で追うもので、曜日で決まる毎回録画と比べてどちらが広いかは分かりません（未測）。曜日が
  1 日も重ならない毎回録画どうしも比べません（片方は番組の曜日に合わないもので、毎週ならテレビが断り、
  月−金と月−土は送っていません）。頼んだ毎回録画は行の符号そのもので比べるので、テレビに送らない繰り返しを
  頼んだ行も同じに比べます。足りなければ外さず、その行は「送らない繰り返し」の理由で保留になります
  （送る手順では、その確認のほうが先のため）。番組 ID の無い予約と、テレビに送らない繰り返しの予約も、
  何も聞かずに、理由を書いて保留にします。
  局の一覧は、放送の種別ごとに、その回で 1 度だけ読みます。読めた一覧にその局が無ければ、理由を書いて
  保留にします。読めなければ、行に何も書かずに見送ります（次の機会に送り、下の「何も言わない答え」には
  数えません）。最初の頁がその要求自身のエラーで答えられたら、「その種別の局は無い」と読み（未測）、局が無いときと
  同じに保留にします。ただし、テレビの状態を言う符号は「局が無い」とは読まず、読めなかったときと同じに見送ります
  （行に何も書かず、数えず、その回ではその種別をもう聞きません）。保留にすると、いずれ変わる状態のために、
  その種別の行がどれも自分からは送られなくなるからです。その符号は 40005 と 7 です。40005 は、
  このクライアントがどの要求でも「電源が入っていない」と読む符号で、待機中のテレビがほかの要求に返しました（測）。
  7 は「いまの状態では受けられない」の符号で、局の一覧に返ったことはありません（作成に返る 7 とは別の意味です）。
  待機にして何時間も経ったテレビに局の一覧を聞いたことも、テレビが持たない種別を聞いたこともまだ無く、2 つの
  読みはどちらも未測です。
  その予約を入れると録れなくなる予約は、毎回問い合わせます。1 件でも名指しされたら、録画でも視聴予約でも、
  それぞれを題名と局の名前と開始の月日・時刻で書いた理由を付けて保留にし、作成は送りません。局の名前は、その行の
  uri の `&srvName=` から後ろを、テレビの書いたまま使います（問い合わせが名指しする行には `channelName` が
  無いため）。利用者が「もう一度送る」を選んだ行（録れなくなる予約があっても入れる、という同意）でも
  問い合わせ直し、行に書いてある理由が、今の答えから作った理由と一字も違わないときだけ作成を送ります。同意は、
  その文が名指しした予約に対するもので、一覧はそのあと変わっているかもしれないからです。局の名前まで
  書くのもそのためです。同じ題名で同じ時刻の予約が 2 つの局にあるとき（同時に放送される番組）、片方を失うことへの
  同意が、もう片方を失うことへの同意にならないようにします。答えが読めないときは、何も
  名指しされなかったことにしません。理由の頭の文（「この予約を入れると、次の予約は録画されません」）は、保留の
  行をそれで見分けるので変えません。視聴予約が名指しされると「録画されません」は合わない言い方になりますが、
  テレビが視聴予約を名指ししたことはありません。
  作成を送ったら、一覧を読みます。一覧に（局と番組 ID で）あって初めて「作った」です。受け付けたと答えて一覧に
  無ければ、理由を書いて保留にします。41222 は何も作らないので（測）、一覧にあれば「すでにある」、無ければ
  保留です。41222 は繰り返しが違っても返るので（測）、一覧にある予約が、行の頼んだ毎回録画に足りないときは、
  「すでにある」にせず、回の初めと同じ規則で、同じ理由を書いて保留にします。エラー 7 は、その予約そのものが
  断られた符号なので（契約していない局、番組の曜日と合わない毎週。どちらも測）、理由を書いて保留にし、同じものは
  送り直しません。作成の前と後の一覧を比べ、作った行が重なりの印を持つとき、名指しされなかった行が新しく印を
  持ったとき（視聴予約が `partlyOverlapped` になる。測）は、その文を「作った」に添えます
  （`RowSent.made(saying:)`）。新しく印を持った行は、録画予約と視聴予約を別の文で言います。録画予約には
  「録画されないことがあります」と言い（`fullyOverlapped` は、録れない側になった録画予約に付いた印です。測）、
  視聴予約には「重なりました」とだけ言います。視聴予約は録画しないので、印の付いた視聴予約を「録画されない」
  とは言いません。送信待ちはそれを結果の `remarks` に入れ、「登録しました」の文のすぐ後ろで言います。
  レコーダーは何も添えず、文は前と一字も変わりません。
  どの段でも、無応答と、受け付けられない cookie（403。作成でも何も作られない。測）は、その回を止めます。作成が
  無応答なら、一覧も読みません。作られているかもしれないので、次の回の初めの一覧が教えます（あれば「すでにある」、
  無ければ送る）。問い合わせや作成への答えが、行について何も言わないとき（知らない符号、読めない答え）は、行に何も
  書かずに見送り、そういう行が 2 件続いたらその回を止めます。おかしいのは行ではなくテレビのほう、と読むためです。
  41222 のあとの一覧が読めないときも、同じに数えます（何も作られていないので、回の持っている一覧はそのまま
  使えます）。受け付けられた作成のあとの一覧が読めないときは、数に関係なく、そこで回を止めます。回が拠っている
  一覧が無くなり、続ければ、次の行が「作ったことで何を変えたか」を、この作成より前の一覧と比べて言うことに
  なるからです。その行には何も書かず、見送った行としても伝えません（その一覧が無応答だったときと同じです）。
  見送った行は「送れなかったため、次の機会にもう一度送ります」と伝えられますが、テレビは作成を受け付けたと
  答えていて、次の回は送り直さず、初めの一覧で見つけて「すでにある」と伝えるからです。「2 件続いたら」の数を
  初めから数え直すのは、テレビがその行について何か答えたときだけです。問い合わせで名指しされて保留、符号で
  断られて保留、一覧に無くて保留、41222 のあとの一覧にあった予約が頼んだ毎回録画に足りなくて保留、作った、
  すでにあった、の 6 つです。何も聞かずに保留にした行（番組 ID が無い、送らない繰り返し、回の一覧にある予約が
  頼んだ毎回録画に足りない、局が一覧に無い）と、局の一覧が読めずに見送った行は、数えもせず、数え直しも
  しません。テレビが答えるかどうかを、何も示さないからです。
  残してあること: 作成が無応答だった行と、受け付けられた作成のあとの一覧が読めなかった行は、次の回の初めの一覧で
  見つかり、「すでにある」と伝えられます。その作成がほかの予約に重なりの印を付けていても、それはどこでも
  言われません（回の初めに返るのは、どの行がすでにあるかだけです）。
  この規則は `TVRoundTests` が偽のテレビ（`DemoTV`）で確かめます。偽のテレビは、実機が答えたとおりに答えます。
  題名を付け直す、3 件目の問い合わせには先に作った 1 件を名指しして作成は通す、視聴予約を一部重なりにする、
  契約していない局と曜日の合わない毎週はエラー 7、同じ番組の 2 回目は 41222、受け付けない cookie は 403 です。
  実機で見ていないことを答える箇所には、そう書いてあります。
  ドライバーは自分のリンクを持つので、アプリは操作のたびにリンクを渡しません。アプリの側では、テレビのホスト
  （`TVHost`）が読んだ一覧を持ち、テレビを外せば一覧もホストごと無くなります。予約の変更と削除は、行を持っている
  機器へ最初に振り分けます。レコーダーの予約の探し直し（`current`）も、ほかの機器の行は見つけません。
  1 つの操作を作る部品も、機器に共通のものをリンクが持ちます（`LinkOperation.swift`）。操作の前の確認
  （`DeviceLink.check`）は、機器に送れないときに、なぜかを返します。未接続、許可待ち、別の機器が答えた、
  起こしたが接続を断られた、無応答の 5 つです（`ensureUp` は同じ確認を真偽で返します）。送ったものがどう
  失敗したかは `OperationFailure` が種類と文をまとめて持ちます。何も送っていない、機器が断った、書き込みの
  あとの無応答、読み込みの無応答の 4 つです。`DeviceLink.say` がそれを画面の行に書き、無応答なら上の
  「無応答は 1 か所で受ける」の状態にします。断られただけなら機器は「いる」ので文を出すだけ、何も送って
  いないときは何も書きません（確認がもう伝えています）。書き込みのあとの無応答に出す文は、操作ごとに渡します
  （あとで何を確かめるかが操作によって違うため）。読み込みの無応答を受けるかどうかだけは機器によって違い、
  ドライバーが答えます（`takesSilenceOnARead`）。レコーダーはいつでも受けます。テレビは接続済みの間だけで、
  無応答になった要求の後ろで順番を待っていた読み込みが、先の要求の文（削除が届いているかもしれない）を
  上書きしないためです。`DeviceLink.run` は、要求が 1 つの操作の順番（進行中の行を出す、確認する、送る、
  うまくいけば前の失敗の行を消し、失敗なら伝える）をまとめたもので、レコーダーの操作の入口（`AppModel.run`）と
  テレビの予約一覧の読み込みがこれを通ります。失敗の行を消すのはうまくいったときだけで、入口では消しません
  （前の要求の失敗が、読まれる前に次の要求で消えるため）。部品は、偽の外界を渡す `LinkPartsTests` が
  確かめます。レコーダーの個々の操作はまだアプリにあります。要求がいくつもある操作（テレビの予約の削除）は
  `run` を通りません。同じ確認（`ensureUp`）を使い、途中の一覧の読み込みは `run` を通りますが、進行中の行と、
  送信の無応答や「その予約は無い」と答えられたときの文は、まだ自分で書いています。
  HTTP のクライアントは、1 つの要求を 1 回だけ送ること。`URLSession` は、401 に Basic の認証の問いが付いていると、
  同じ要求を別の接続でもう 1 回送ってから 401 を返します（デリゲートが何と答えても、問いを取り消さない限り）。
  テレビの登録の要求（`actRegister`）は、未登録なら必ずこの 401 で答えられます。アプリから登録したとき、テレビの
  画面の PIN は出てすぐ消えました（同じ要求を 1 回だけ送ると、読める間は残ります）。`Http.swift` は問いを取り消して
  401 の答えをそのまま返し、`URLSessionTransportTests` がループバックのサーバーで、送ったのが 1 回であることを
  確かめます。差し替えの通信では見えない規則なので、移植先でも本物の HTTP クライアントで確かめてください。
  テレビの挙動を測るときも、別の道具ではなく、アプリが送るのと同じクライアントと通信で送ります
  （`TV_HOST=<アドレス> swift test --filter LiveTVTests/<テスト名>`。変数は毎回コマンドの行に書き、テストは 1 つずつ名指しします。
  登録の手順はファイルの先頭にあります）。
  予約を入れる 3 つの要求を実機に初めて送る確認も同じファイルにあり、持ち主がテレビの前にいる席で、1 つずつ
  走らせます（順番と、そのつど見るものはファイルの先頭）。テレビに書き込む確認の決まりは `TVSitting` に
  書いてあります。書き込みを名指しで許されたとき（`TV_WRITE` が、走らせるそのテストの名前のとき）だけ、テレビの
  電源が入っているときだけ作る。作成の前には毎回、録れなくなる予約をテレビに問い合わせ、自分の作った行のほかが
  挙がれば作らない。作成の前と後に一覧を読み、送った局に新しく増えた番号の録画だけを自分のものとして消す（番組や
  時刻や番組名では消さない）。作る前に台帳のファイルに書き、削除に応答があり、消えたのを一覧で見てから線を引く。
  線の引かれていない記入が残っていれば、その後の確認は何も作らずに失敗する。作成が無応答でも送り直さない。前後
  3 時間に予約の無い、20 時間以上先の番組にだけ作る。確認に使う視聴予約は、持ち主が開始の時刻で名指しする
  （`TV_REMINDER`）。番組名・局名・テレビの付けた番号は表示しない。同じ確認を、その前に偽のテレビ（`DemoTV`）で
  通します（`TVSittingTests`）。持ち主の予約を、確認の使う枠のすぐ外と、確認が予約する番組そのものに置いておき、
  行が残る、作っていない行を消す、作成を 2 回送る、問い合わせずに作成を送る、番組名を表示する、のどれかがあれば、
  実機に送る前にそこで落ちます。
  テレビを待機にして一晩置いた席の確認が 1 つあります（`testAWaitingRowSentInStandby`。手順はファイルの先頭）。
  この確認だけは、ほかと逆に、テレビが待機と答えたときにだけ作ります。送信待ちの 1 件を、確認だけのために
  メモリ上に作ったデータベースに入れ（ディスクには何も置かない）、出荷するのと同じ手順（`PendingQueue.flush` と、
  上のテレビの回）で送ります。続けて同じ 1 件をもう一度入れて送り（一覧で見つかるので、作成は送られない）、
  行を消します。0 時から 5 時までに始まる番組は選びません。局が放送を休んでいることのある時間帯で、その枠への
  作成にテレビが何と答えるかは見ていないためです。作成を送るのが確認ではなく回なので、台帳は送信待ちを送る前に
  書き、送る前と後に一覧を読みます。台帳にいつ線を引くかは、ほかの確認と同じ 1 か所の規則を通ります。自分の行と
  するものは、ほかの確認より狭くしてあります。送った局に新しく増えた録画のうち、入れた番組の番組 ID を持つもの
  だけです。回が作成を送っていないと分かるとき（すでにあった、作成の前に保留した、作成の前に回が止まった）は、
  1 行も自分のものとしません。それ以外に増えた録画は持ち主のものとして触らず、台帳に線を引かずに失敗します。
  作成の前の問い合わせは回が行い、1 件でも名指しされれば作成を送りません。回が「受け付けられたが一覧に無い」
  「見送った」と言ったとき、作成が無応答だったときは、一覧に何も増えていなくても台帳に線を引きません。
  回が何を送ったかは、送信待ちの結果からは分かりません（一覧で見つかった行は、作成を送ったあとで見つかっても
  同じ結果になる）。そこで確認のクライアントは、要求ごとにメソッド名と応答の種類（応答あり、エラーの符号、
  HTTP の状態、無応答）だけを控える通信（`TVLine`）の上に作り、送るたびに何を送ったかを表示します。2 回目に
  作成が含まれていれば失敗します。終わりに、テレビが自分の状態を何と答えるかをもう一度聞いて表示します
  （何と答えても失敗にはせず、無応答のあとは聞かない）。ほかに表示するのは、送信待ちの結果の件数と、回が
  止まった理由の種類だけです（行に書かれた理由の文には、持ち主の予約の題名が入るため）。夜のあいだは、この
  確認のコマンドのほかにも、レコーダーやテレビに問い合わせるもの（番組表を取りに行くサーバー、スマホのアプリ）を
  止めておきます。
- **サンプルデータのモード**: レコーダーの応答を偽のものに差し替えるだけで、画面は本物のパーサを通ります。
  審査にも、レコーダーを持っていない人の下見にも、ストア用のスクリーンショットにも同じものが使えます。
  キャッシュは**別のデータベースに書く**こと（終了時にファイルごと消せる）。実装は `app/BDBridge/DemoData.swift`。
  サンプル中に実機を選んだとき（探して選ぶ・アドレスを入力する）は、**サンプルを終了してから**そのレコーダーに
  つなぐこと。サンプルのままつなぐと偽の応答で「つながった」ように見え、あとで終了すると元の設定に戻って、選んだ
  レコーダーが消えます。元の設定に戻すのは「終了」だけで、選んだときは戻しません（`AppModel.adopt`）。サンプルの
  開始・終了と切り替えは、接続・読み込み・一括処理・操作の前の確認の最中は受け付けないこと。途中の応答が
  切り替えたあとの画面に入ります。答えたレコーダーの照合（上の「答えたレコーダーが誰かで決める」）は、
  サンプルでは行わないこと。サンプルのキャッシュは自分のもので終了時に消え、実機のキャッシュ（持ち主の UDN、
  録画の番組内容、残容量の通知の印）はサンプルの出入りで変えません。

## App Store 申請の要点

- **審査担当者はレコーダーを持っていません。** 起動しても何も見つからず、機能を評価できないという理由で返される
  可能性があります。これが最大のリスクです。**対策として、チュートリアルの最後と設定画面から入れるサンプル
  データのモードを入れました**（`app/BDBridge/DemoData.swift`）。架空の番組表・録画一覧・予約一覧で、予約の作成・
  変更・削除まで実際に動きます。審査メモには入り方を書き、機種要件とデモ動画のリンクも添えます。
- **アプリ名は独自の名前にします。** 他社の商標は名前にもサブタイトルにも入れず（Apple のガイドライン）、
  対応機種は**説明文の本文**で伝えます。ロゴ、製品写真、本家アプリに似た配色やアイコンは使いません。
- **Info.plist** には `NSLocalNetworkUsageDescription` と `NSAllowsLocalNetworking` を入れます。用途は正直に書きます。
- **プライバシー**: ポリシーの URL は全アプリ必須なので、何も収集しない旨のページを用意します（`privacy.md`）。
  App Privacy の質問票は収集項目なしで答えられます。外部ライブラリは使っていませんが、`UserDefaults` は
  「理由の宣言が必要な API」なので、理由コード（`CA92.1`）を書いたプライバシーマニフェストが要ります（無いと
  ITMS-91053 で止められます）。iOS アプリでは `app/BDBridge/PrivacyInfo.xcprivacy` がそれで、収集も追跡も
  しないことと、この 1 つの理由を宣言しています。マニフェストにはコメントを書かないこと。`--` を含むコメントは
  整形式の XML にならず、ITMS-91056 でビルドが差し戻されます（`plutil -lint` はそれを通してしまいます）。
- **費用と手続き**: 個人登録で足ります。無料アプリなら銀行口座と税務情報の登録は不要です。iPhone のみにすると
  iPad 用のスクリーンショットと動作保証が不要になり、面倒が減ります。
- スクリーンショットの要求サイズは変わります。申請時に App Store Connect の最新の要件を確認してください。
  撮り方（サンプルデータで撮る手順、寸法とシミュレータの対応、はまりどころ）は
  `app/scripts/screenshots/README.md`。

Android を配布する人向けの注意も一つ書いておきます。Play ストアを使わず APK を直接配る形は、Play Protect の警告、
自動更新の欠如、そして認証済み端末へのサイドロードに開発者の本人確認を求める動きがあるため、一般利用者向けには
向きません。配布前に最新の要件を確認してください。

## 検証ベクタ（`docs/port/`）

`uv run python -m bdzbridge.tools.portkit` が Python 実装から生成します（テストが鮮度を確認するので、手で直さないこと）。
移植側では次のようなテストを書きます。

- `codes.json` — 定数の一致（コード表、ファイル名、ARIB 記号表、ロゴの共通カラーテーブル、名前空間、制御 URL）。
- `xsrs.json` —
  - `create_elements[*].input` から Elements 文字列を組み立て、`elements` と**完全一致**させる。
  - `update_elements` / `title_update_elements` も同様。
  - `parse_reservation.item` / `parse_title[*].item` を解析して `expected` と一致させる（`notplayed` の扱いを含む）。
  - `soap.example.body` と同じ本文を作れること。
- `description.json` — `description_xml` を解析して `expected` の各値（機種名、UDN、EPG 対応）を得ること。他社機や
  レコーダー以外のソニー機を弾くこと（製造者が Sony Corporation かつ XSRS サービスを持つもの）。
- `epg-sample.dat` → `epg-sample.json` — 復号結果が一致すること（時刻は ISO 8601 の `+09:00`、参照イベント、ジャンル、
  コピー制御、視聴年齢、記号置換）。実機ファイルでの検証は `server/tests/test_epg.py` の要領で自分のレコーダーから取る。
- `logo-sample.dat` → `logo-sample.json` — チャンネル番号と service_id の対応、ロゴのない局のスキップ、PLTE/tRNS 挿入後の
  PNG が `png_base64` と一致すること。
- `series.json` — `series_name` / `series_key` / `same_title_key` / `summary_key` の各値の一致。
- `titles.json` — 視聴状態（未視聴／途中／視聴済み）、番組ごとの「まとめ」（件数・容量・未視聴数・保護数）、
  重複の検出（候補の作り方、内容による分割、残す 1 本とその理由、`guide` から求める `fixed_blurbs` と定型文の組
  `boilerplate`）。**録画中のものは残す側に固定**され、削除候補には入りません。

| 宅外 | 完了。送信待ちキュー、VPN 越しの起こし、番組終了で破棄。断られた送信待ちは理由を付けて残し、利用者が選ぶまで送り直さない。帰宅時に送るショートカットのアクション（送るものがなければ何もしない） |
| 深夜の番組表更新 | 完了（`BGProcessingTask`。レコーダーを起こしてから取る）。1 種別の失敗では止めず、古いかどうかは種別ごとに決める。期限が来たらその場で完了を伝える |
| 通知 | 完了。送信待ちが送れたとき、残容量が閾値を切ったとき。許可は初めての接続のあとに provisional で取り、設定画面に状態を出す |
| 文字サイズと VoiceOver | 完了。アクセシビリティの文字サイズまで各行が折り返す。予約・送信待ち・重複の橙は、ライトモードでは白地で読める濃さにする。表形式のブロック、アイコンだけのボタン、重複のチェックに読み上げ用の説明。ただし VoiceOver で実際に読み上げさせての確認はまだ |
| サンプルデータのモード | 完了。チュートリアルと設定から。スクリーンショットにも使う。サンプル中に実機を選ぶと、サンプルを終了してからつなぐ |
| テスト | RecorderKit は `swift test`（`docs/port` のベクタを含む）。接続の規則のうち LAN が要るもの（パケットの順、許可待ち、移った機体の探し直し）は `DeviceLinkTests` が偽の外界で。`AppModel` は `BDBridgeTests` で、レコーダーもネットワークも使わない。サンプルデータの画面は UI テスト（`DemoModeTests`）。Xcode Cloud はアーカイブの前に `swift test` を走らせる |
| SSDP | 未実装。マルチキャストのエンタイトルメント申請が要るので、TCP スキャンのままにしてある |
| 番組表からの自動予約（キーワード） | 未実装。レコーダー本体のおまかせ・まる録で代替できるため後回し |
| 持ち出し（`portableRecordFile`）・ディスクへのダビング | 未実装。読み取り以外は手を付けていない |

`RECORDER_HOST=<ip> swift test --filter LiveRecorderTests`（読み取りのみ）が実機との突き合わせを走らせます。
各段階で、Python サーバーの `docs/api.md` にある同じ操作の結果と比べると差分が見つけやすいです。

## 他のプラットフォームに移植するときの順番

上の表と同じ順序で積むのがいちばん楽でした。

1. プロトコル層: `description.xml` の解析 → SOAP → 予約一覧の取得（読み取りだけ）。`xsrs.json` と `description.json` を通す。
2. EPG: ファイル取得と復号、端末内 DB、日別・チャンネル別の表示。`epg-sample` を通し、実機ファイルで Python と突き合わせる。
3. **サンプルデータのモード**: ここで作っておくと、実機がなくても UI を進められて、申請にもスクリーンショットにも
   そのまま使えます。
4. 予約: 作成・更新・削除と番組追従。テスト用の予約名を決めて作成→削除で確認する（録画の削除はテストに使わない）。
5. 録画: 一覧、詳細、保護、削除、テレビ再生、まとめ、重複。`series.json` と `titles.json` を通す。
6. 宅外: 送信待ちキュー、Wake-on-LAN、諦め方。
7. 仕上げ: おまかせ・まる録、ロゴ、残容量の警告、定期更新、通知。
