# ネイティブアプリへの移植ガイド

bdzbridge はサーバー（Python）とブラウザ（PWA）、それに iOS アプリ（`app/`）の 3 つで動いています。サーバーも
VPN 前提の構成も要らずアプリがレコーダーと直接話す形が iOS アプリで、**これは実機で動いています**。このドキュメントは
「何をそのまま持っていき、何を作り直し、何で検証するか」と、実機で分かったレコーダーの癖をまとめたものです。
プロトコルそのものの説明は [`xsrs-api.md`](xsrs-api.md) と [`epg-format.md`](epg-format.md) にあり、ここでは
繰り返しません。

読者は 2 通りです。

- **iOS アプリに手を入れる人**: 下の「Swift での対応」「レコーダーの振る舞いチェックリスト」「端末側の設計メモ」が
  実装の背景です。アプリの構成そのものは `app/README.md`。
- **他のプラットフォームに移植する人**: Android ネイティブは作者の予定にありません。必要と思った人が作れるように、
  機種依存の知識と検証ベクタは言語に依存しない形にしてあります。Android 利用者向けの現状の道は、サーバーを自分で
  動かして PWA を使うことです。

## 前提と方針

- レコーダーの API は LAN 内で無認証です。アプリはレコーダーと同じネットワークにいるとき（VPN で自宅の
  ネットワークに入っている場合を含む）に動作します。届かないときはキャッシュ済みの番組表を見て、予約は
  「送信待ち」として端末に溜め、**次にレコーダーが応答したとき**に送ります（帰宅を待つ必要はありません。
  VPN 越しにレコーダーを起こして送れることも実機で確認しています）。
- Python のサーバーは移植中も動かし続け、**正解（oracle）**として使います。同じレコーダーに対して両方から
  同じ操作をして結果を突き合わせるのがいちばん確実な検証です（書き込みは予約の作成→削除で行い、録画の削除は
  テストに使わないこと）。
- 機種依存の知識はすべて `server/bdzbridge/recorder/` に閉じ込めてあります。移植の中心はこのディレクトリです。

## 何を持っていくか

| Python 側 | 役割 | 移植先での扱い | 検証ベクタ |
|---|---|---|---|
| `recorder/discovery.py` | SSDP M-SEARCH → 見つからなければ /24 を TCP 64220 でスキャン → `description.xml` で確認 | 必須。SSDP はマルチキャストの権限が要る（後述）。スキャンだけでも成立する | `port/description.json` |
| `recorder/client.py` | 1 台分の状態、EPG/ロゴのダウンロード、DLNA ツリーから配信ポートの検出、**全リクエストを直列化するロック** | 必須。ロックは絶対に省かない（並行リクエストに 503 を返す）。配信ポートの検出は**番組表ファイルが必要になった時点で 1 回だけ**行う（後述） | — |
| `recorder/xsrs.py` | SOAP の組み立て、予約/録画 item の解析、`build_create_elements` | 必須。生成する XML は Python とバイト単位で一致させる | `port/xsrs.json` |
| `recorder/codes.py` | 放送種別・画質・毎回録画・ジャンルのコード表、EPG/ロゴのファイル名 | そのまま定数に | `port/codes.json` |
| `recorder/epg.py` | EPG ファイルの復号（XOR 0x9D → 連結 zlib → @SRV/@DAY/@EVT）、ARIB 記号の置換 | 必須 | `port/epg-sample.{dat,json}` |
| `recorder/logo.py` | 局ロゴファイルの復号、PLTE/tRNS の挿入 | 任意（見た目） | `port/logo-sample.{dat,json}` |
| `recorder/series.py` | 録画タイトルからの番組名抽出（まとめ表示）、重複検出のキー | 必須（まとめ・重複を出すなら）。正規表現をそのまま移す | `port/series.json` |
| `recorder/wol.py` | Wake-on-LAN | **必須に近い**。レコーダーは時間の 4 分の 3 を寝て過ごすので例外処理ではなく通常の経路。**MAC はレコーダー自身が教えてくれる**（`X_GetPrivateIp`、または `description.xml` の UDN 末尾）ので、利用者に入力させる必要はない | — |
| `store/guide.py` | SQLite の番組表キャッシュ（検索用正規化、サブチャンネルの参照解決、放送日 04:00 区切り） | 端末内 DB に作り直す。仕様は下記「番組表の扱い」 | — |
| `store/rules.py` + `services/autorec.py` | 番組表からのキーワード自動予約（サーバー側の機能） | 任意。**iOS アプリでは作っていません**: レコーダー本体の「おまかせ・まる録」を読み書きできるので、アプリを閉じていても本体が録ってくれる方を採りました | — |
| `services/titles.py` | 全録画リストのキャッシュ、まとめ、重複検出、一括削除/保護 | ロジックはそのまま。一括処理は端末内で逐次実行し、中止できるようにする | — |
| `jobs.py`, `api/`, `services/notify.py`, `services/monitor.py` | サーバーならではの部分（HTTP API、ジョブ、SMTP/webhook 通知、残容量監視） | 不要。通知は端末のローカル通知で代替 | — |

## Swift での対応

すべて OS 標準の機能で足ります。外部ライブラリは要りません。

| やること | 使うもの |
|---|---|
| LAN への HTTP と SOAP | `URLSession`。1 台につき 1 本に直列化するため、`actor` で包むか `OperationQueue` の同時実行数を 1 にする |
| /24 の TCP スキャン | 各アドレスの `description.xml` を `URLSession` で取りに行く（48 本並列、1 本 1.2 秒で打ち切り）。答えの中身でレコーダーかどうか決まるので、ポートだけを見る走査は別に要らない。その前にローカルネットワークの許可を待つ（下の「ローカルネットワークの許可」） |
| SSDP | `NWConnection` のマルチキャスト。エンタイトルメント申請が必要なので後回しにする |
| Wake-on-LAN | BSD ソケット（`socket`、`setsockopt(SO_BROADCAST)`、`sendto`）の UDP。Network framework にはブロードキャストを送る手段がない。宛先は 3 つ（`255.255.255.255`、レコーダーのサブネットのブロードキャスト、**レコーダーのアドレス宛のユニキャスト**）。VPN 越しに届くのはユニキャストだけ。iPhone で実際に出ていくのはこのうち 2 つの見込み（下の「Wake-on-LAN」） |
| 連結 zlib の展開 | `libz` を直接使い、`z_stream` の未消費バイト数から次のストリームの開始位置を求める。`import zlib` がそのまま通り、iOS SDK でも解決します。Compression framework でも消費量は追えるが、境界の判定を自分で書くことになる |
| XML の解析 | `XMLParser`。SOAP 応答と DIDL-Lite の両方に使う |
| XML の生成 | 文字列連結で十分。要素の順序を固定したいので、汎用のシリアライザは使わない方が確実 |
| 番組表の保存 | SQLite。検索用に NFKC + casefold 済みの列を持たせる |
| 定期更新 | `BGProcessingTask`（`requiresNetworkConnectivity`、深夜 2 時を `earliestBeginDate` に）。呼ばれる保証がないので手動更新も必ず置く。**この中でもレコーダーを起こすこと**: 深夜はまず寝ている |
| 通知 | `UNUserNotificationCenter`。自動予約の結果と残容量の警告に使う |

UI で唯一手間がかかるのは番組表の表形式です。時間軸とチャンネル軸の 2 方向スクロール、両方向に残るヘッダー、
ピンチでの時間軸の拡大縮小は SwiftUI でも自前で組む必要があります。PWA 側の `GuideGrid.svelte` が仕様書代わりになります。

## レコーダーの振る舞いチェックリスト

実機（BDZ-FBT4100）で分かったこと。どれもコードにコメントとして残っていますが、移植時に踏みやすい順に並べます。

**通信**
- 同時リクエストは 503。1 台につき 1 本のキューで直列化する。
- XSRS の制御 URL は `/XSRS`、X_PvrControl は `/X_PvrControl`、ContentDirectory は `/DMSContentDirectory`。ポートは 64220。
- SOAP ヘッダは `Content-Type: text/xml; charset="utf-8"`、`SOAPACTION: "<serviceType>#<action>"`、`Accept-Language: ja`。
  本文の形は `port/xsrs.json` の `soap.example`。
- エラーは HTTP 500 + SOAP Fault の `errorCode`。402 は引数の形式違反（例: 時刻のオフセットが `+0900`）、
  804 は存在しない予約 ID、820 は存在しないタイトル ID、831 は受信できないチャンネルの番組を追従予約しようとした、
  880 はレコーダーがネットワークスタンバイ中で再生できない。**errorCode の無い素の HTTP 500 もあります**
  （録画中のタイトルの削除。後述）。
- EPG/ロゴのファイルは別ポート（既定 60151）から `//EPG_TRDEPG_FILE.dat` のように**スラッシュ 2 つ**で取る。ポートは
  DLNA ツリーの最初の `<res>` URL から確認できる。そのチャンネル種別を持っていない場合は 416 が返る。
- **`description.xml` の取得に余計な処理を足さないこと。** 上の配信ポート検出（Browse を最大 8 回）を
  `describe` の中でやっていたため、「2 秒で諦めるはずの生存確認」が数分かかりました。起動待ちのプローブは
  `description.xml` 1 本だけにして、ポート検出は番組表ファイルを取る直前に 1 回だけ行います。
- ネットワークスタンバイ中でも API は答える。電源を入れるのは `X_PowerControl` の `on`（`PowerOn` や `On` は不可）。
- レコーダーが完全に落ちている（電源オフ後しばらく）と何も答えない。Wake-on-LAN で起きる。本体の「ネットワーク待機」が
  切だと、しばらく操作がないだけで LAN から消えるので、これは例外ではなく普通に起きる。
- **レコーダーは自分から起きます。** 12 時間つないだまま 1 分ごとに 64220 を見た記録（2026-09-17、誰も操作していない
  時間帯を含む）:

  | | 回数 | 中央値 | 最短 | 最長 |
  |---|---|---|---|---|
  | 寝ている時間 | 13 | 27 分 | 2 分 | 136 分 |
  | 起きている時間 | 12 | 10 分 | 2 分 | 81 分 |

  応答していたのは全体の **25%**。周期は一定ではなく、2 分で起きることも 2 時間寝ていることもあります。設計上の
  意味は 2 つです。**(1) 「寝ている」は恒久的な状態ではない**ので、溜めた予約を送る機会は放っておいても来ます
  （中央値 27 分待ち）。**(2) 逆に、起きているのは 4 分の 1 の時間だけ**なので、アプリを開いた瞬間につながっている
  ことは期待できず、Wake-on-LAN は例外処理ではなく通常の経路として要ります。
  何のために起きているのかは LAN 側からは見えません（外部サービスとの通信を覗く手段がない）。
- **Wake-on-LAN はレコーダー自身が申告しています。** `description.xml` の `X_WakeupOnLAN` が `1`（取説には記載なし、
  公式クライアントもこの値を読む）。
  宛先の MAC は 2 通りで取れるので、ユーザーに入力させる必要はありません。`X_PvrControl` の `X_GetPrivateIp` が
  `macAddress` と `wirelessMacAddress` を返すのが正攻法で、`description.xml` の `<UDN>` の末尾 12 桁も同じ有線 MAC です
  （`uuid:XXXXXXXX-XXXX-XXXX-XXXX-<MAC>`、実機で ARP と一致）。iOS は ARP を読めないので、起きているうちに控えておくのが
  唯一の手です。有線と無線で MAC が違うので、繋いでいる側を使うこと。
- **Wake-on-LAN は同じサブネットにいるときだけ確実です。** `255.255.255.255` はルーターを越えず、VPN 越しの端末は
  自分のインターフェースから自宅のサブネットを知ることができません。レコーダーのアドレスからそのサブネットの
  ブロードキャストを組み立てて送る手はありますが、ゲートウェイがディレクテッドブロードキャストを転送する設定で
  なければ届きません（UniFi は既定で転送しません）。**レコーダーのアドレス宛のユニキャストでも起きます**（実測:
  ブロードキャストを一切使わず、同じセグメントからアドレス宛にポート 9 と 7 へ送って 6 秒で応答）。
  どちらの実装も、リミテッドブロードキャスト・サブネットのブロードキャスト・レコーダーのアドレスの 3 つへ送ります。
- **VPN 越しにも起きました。** 外出先から VPN でつないだ iPhone のアプリが、寝ていたレコーダーを起こして接続
  できています（寝てから 2 分後、起きるまで 2 分ほど）。届いたのはアドレス宛のユニキャストで、
  ブロードキャストは VPN を越えません。ただし**ゲートウェイがそのアドレスの MAC を覚えている間だけ**のはずで、
  何時間も寝たあとに同じことができるかは未確認です。キャッシュが切れた後は LAN の内側にいる何かに送ってもらう
  しかありません。自宅にサーバーを置いているなら `POST /api/v1/recorder/wake` がその役目を果たします。
- **この機種は ICMP に答えません。** 起きていても ping は通らないので、死活監視には使えません（UPnP のポート
  64220 に繋がるかで見ます）。「ping に答えない＝ネットワークにいない」とは言えない、ということでもあります。
- `X_GetPrivateIp` は `useDhcp` も返します。アドレスが DHCP で動く機体なら、保存した IP に繋ぐだけの実装は取りこぼします。
  サーバー側は UDN で再探索していますが、移植先でも同じ手当てが必要です。
- サービスは 5 つに見えて実質 4 つ。`/XSRSExt`（`X_ScheduledRecordingExt:1`）は `/XSRS` と SCPD が完全に同一で、同じ答えを
  返します。詳細は `upnp/service-sweep.md`。

**予約**
- `X_CreateRecordSchedule` の `<Elements>` は公式アプリの送信内容と同一にする（`port/xsrs.json` の `create_elements[0]`
  は実キャプチャ由来）。要素の順序、`channelType="2"`、`scheduledChannelID` の `0x0428` 形式、時刻の `+09:00`。
- `desiredMatchingID` に `,,0x<service>,0x<event>` を入れると番組追従になり、タイトルはレコーダーが EPG から上書きする。
  時間指定（event なし）の予約は後から event_id が補完されることはない。
- 更新は同じ item に `id` を付けて `X_UpdateRecordSchedule`。画質・毎回録画をその場で変えられる。
- 毎週の毎回録画（`w1`〜`w7`）は番組の曜日と一致させる。
- 一覧は `X_GetRecordScheduleList`、1 回 200 件まで。ソートは `-scheduledStartDateTime`。
- **予約 ID は振り直されます。** レコーダーが自分のおまかせ・まる録で入れた予約は、番組表を読み直したときに
  ブロックごと番号が変わります（実測: 19 件が一斉に変わり、番組自体は同じまま）。数時間前に読んだ ID で削除や
  更新をすると 804 になります。**削除・更新の前に一覧を読み直し、チャンネルと開始時刻で同じ予約を探すこと**
  （この 2 つが同じ予約は 2 つ存在しません）。本当に無くなっているのは、探して見つからないときだけです。
- `X_GetConflictList` に作成と同じ Elements を渡すと重なる予約が返る。作成と同じ本文を投げるので、**実際に
  作らずに本文の妥当性まで確かめられます**。

**録画タイトル**
- `X_GetTitleList` は `recordDestinationID=HDD` で検索し、1 回 200 件まで。`TotalMatches` を見て繰り返す。
- `lastPlaybackTime` は未再生だと本文が `notplayed`。`resumePoint` 属性が再生位置（秒）。
- `genreID` は ARIB のレベル1×16＋レベル2。
- `X_UpdateTitle` は `<item id>` と変える要素だけを送る（`titleProtectFlag`、`titleNewFlag`、`title`）。
- `X_DeleteTitle` は保護中なら失敗、**存在しない ID には成功を返す**。削除前に `X_GetTitleDetail` で存在を確かめる。
  1 件 3 秒ほどかかる。
- **録画中のタイトルも一覧に出ます。** item の `recordingFlag` が `1`。これを消そうとすると
  **errorCode の無い HTTP 500** が返るので（820 のような手がかりが無い）、削除の前にフラグを見て、画面にも
  「録画中」と出すこと。完了したタイトルが `0` であることは実機で確認済み、`1` の観測は未了（予約一覧の
  同名フラグと同じ意味と解釈）。
- 再生は `X_PlayControlTitle`（`play` / `stop` / `pause`、小文字。`pause` はトグルで再開も同じ）。テレビ側で再生される。
- 残容量は ContentDirectory の `X_HDLnkGetRecordDestinationInfo`（バイト単位）。
- サムネイルは全タイトル共通のダミー画像なので出さない。番組内容は `X_GetTitleDetail`（summary と detail 群）。
- DLNA ツリーにはシリーズ ID がない。「まとめ」はタイトル文字列から `series.py` の規則で作る。公式クライアントも
  同じくクライアント側でタイトル文字列から鍵を作っている。
- レコーダー本体の「おまかせ・まる録」（キーワード自動録画）は `X_GetPrefRecSettingList` で読め、
  `X_CreatePrefRecSetting` / `X_DeletePrefRecSetting` で作成・削除できる。**変更は実装しない**: 一覧には本体で設定した
  対象チャンネルが含まれず、書き戻すとそれが消える（実測）。`Filter` は `*` を渡すこと。形と語彙は `xsrs-api.md`、
  ベクタは `port/xsrs.json` の `recorder_rules`。

**番組表**
- 時刻は 1970-01-01 00:00 **JST** 起点の秒（unix 時刻 + 32400）。
- サブチャンネル（例: 総合 2）の「参照」イベントは開始・終了と親の service/event しか持たない。表示時に親の番組を引く。
- ジャンルは 3 スロット（内容ニブル + ユーザーニブル）。
- テキストは UTF-8 だが NUL 詰めと C0 制御文字が混ざる。ARIB の私用領域文字は `codes.json` の `arib_symbols` で
  `[字]` 等に置き換え、それ以外の私用領域は捨てる。BS4K の一部外字はこの表で変換する（U+1F19B〜U+1F1AC）。
- 放送日は 04:00〜翌 04:00。0 時〜4 時はまだ前日の放送日なので、番組表の最初の日は「今 − 4 時間」の日付にする
  （PWA の `tvDays()`、アプリの `GuideStore.broadcastDays`）。暦の日付で始めると、深夜に放送中の番組が
  どの日にも入らない。
- ロゴファイルは毎日深夜に作り直される。受信していない局は 1152 バイトのゼロ。

## 端末側の設計メモ

- **番組表の扱い**: 放送種別ごと（`codes` にあるのは地デジ・BS・CS・BS4K・CS4K の 5 つ。アプリは CS4K を除く 4 つを
  取ります）に 8 日分をまとめて取り、端末内 DB に置く。受信していない種別はファイルが 416 で返るので、無いものは
  飛ばすだけでよい。全文検索は NFKC + casefold した列で。更新はアプリ起動時（キャッシュが古いときだけ）と手動、
  それに OS のバックグラウンド更新（iOS の `BGProcessingTask` は不定期、Android の `WorkManager` は最短 15 分）に
  頼りすぎない。
- **送信待ちキュー**: 届かなかった予約は端末に保存し、**レコーダーが応答したときに毎回**順に
  `X_CreateRecordSchedule` する（アプリを前面に戻したとき、深夜の更新のとき、手動の再接続のとき）。捨てるのは
  **番組が終わったとき**で、始まっただけのものは送る（レコーダーは残りを録る）。レコーダーがエラーを返した
  ものは理由を付けて残し、黙って再送し続けない。途中でレコーダーが消えたら残りはそのまま次の機会へ。結果は
  ローカル通知で知らせる。実装は `app/RecorderKit/Sources/RecorderKit/PendingQueue.swift` の 1 か所だけで、
  画面と深夜の処理が同じ規則を使います。
- **LAN の判定**: 保存した UDN の `description.xml` が保存ホストで取れるか、駄目なら探索し直す（`services/session.py`
  の `resolve_recorder` と同じ順序）。**iOS アプリはまだ保存アドレスに繋ぐだけ**で、UDN による再探索は入れて
  いません（DHCP でアドレスが変わったら設定から探し直す）。DHCP の機体を相手にするなら手当てした方がよい部分です。
- **諦めたら諦めたままにする**: レコーダーが沈黙したときの再試行は、**この端末が持っているアドレスが変わったとき**
  （別の Wi-Fi、VPN の上がり下がり、セルラーへの切り替え）と、利用者が明示的に頼んだとき（再接続・レコーダーを
  探す・引き下げ更新）だけにします。同じネットワークでは答えは同じで、1 回の試行にタイムアウト（プローブ 5 秒 →
  マジックパケット → 2 秒間隔で最大 30 秒）が掛かるうえ、クライアントは要求を直列化するので、画面ごとに
  読み込みを始めると数分間スピナーが回り続けます。`NWPathMonitor` はもっと細かい理由でも発火するので、
  判断はインターフェースのアドレス一覧で行います。セルラー（`pdp_ip`）のアドレスは一覧に入れません。キャリアは
  自宅の Wi-Fi にいる間も勝手に付け替えるので、数えるとそのたびに 35 秒の起動待ちが走ります。Wi-Fi が
  切れれば Wi-Fi の側が変わるので、セルラーへの切り替えはそれで分かります。接続していないことは画面に出し、
  再試行の入口を添えます。諦めるのは無応答のときだけで、503 や SOAP の Fault のように答えがあったときは
  諦めません（レコーダーはそこにいて、何が悪いかはもう画面に出ています）。アプリに戻ったときの再接続は、
  実際にバックグラウンドに回ったあとだけにします。コントロールセンター、通知センター、アプリスイッチャー、
  システムのアラートでもアプリは非アクティブになりますが、どこにも行っていないので数えません。
- **使っている最中に眠る**: レコーダーは何もしないと 15 分ほどで LAN から消えるので、アプリを開いたままでも
  眠ります。そのままにすると、番組を開けば重複の確認で 30 秒、予約で 30 秒待たされ、家にいるのに送信待ちに
  なります。
  - **無応答は 1 か所で受ける。** どの要求（一覧の読み込み、重複の確認、予約の作成・変更・削除、録画の操作、
    一括処理、重複の検出、送信待ちの送信）でも、無応答を受けたら接続に失敗したときと同じ状態（未接続・諦めた）
    にします。そうしないと、アプリはつながっているつもりのまま画面ごとに同じタイムアウトを待ち、再接続の入口も
    出ません。一括処理と重複の検出は最初の無応答で止めます。
  - **書き込みは送り直さない。** 無応答でも、要求はレコーダーに届いていることがあります。予約を送ったあとに
    無応答になったものは送信待ちにも入れず、再接続してから一覧で確かめるよう伝えます（送信待ちに入れると、次に
    つながったときに同じ予約をもう一度作ることになります）。送信待ちに入るのは、何も送らないうちに無応答が
    分かったものだけです。例外は送信待ちを送っている途中の無応答で、そのとき送っていた 1 件は `PendingQueue`
    の規則どおり送信待ちに残り、次の機会にもう一度送られます（深夜の処理も同じです）。
  - **操作の前に起こす。** クライアントは最後に応答を受けた時刻を持ちます（SOAP の Fault も応答に数えます）。
    利用者の操作の前に 90 秒以上空いていたら、**今のクライアントのまま**マジックパケットと 5 秒のプローブを
    送り、黙っていれば接続時と同じ起動待ちに入ります。起きていればミリ秒で終わります。ここで接続し直すと
    クライアントが 2 つになり、2 本のキューがレコーダーに同時に話しかけて 503 になるので使いません。接続中に
    端末のネットワークが変わったときも、最後の応答はもう当てにならないので、同じ確認をします。
- **一括処理**: 削除・保護はキューで 1 件ずつ、進捗と「中止」を出す（中止は次の 1 件から止める）。アプリが
  バックグラウンドに回ると OS がまもなく止めるので、その旨（離れると一時停止し、戻ると再開する）を表示する。
  止められた途中の要求は失敗として返り、削除が届いたかどうか分からないまま処理が止まるので、処理中の 1 件だけは
  バックグラウンドタスク（iOS の `beginBackgroundTask`）で終わらせ、次の 1 件の前で待ちます。前面に戻ったら、
  離れていた間に眠ったかもしれないレコーダーを確かめてから続けます。処理中は接続し直しません（クライアントが
  2 つになり、2 本目への 503 を「レコーダーではない」と読んで諦めていた）。
- **重複の削除**: チェックを付けたものが消え、チェックの無いものが残る。「残す」の札は提案した 1 本ではなく
  チェックの無い行に付け、全部にチェックが付いた組があれば、その組の名前を出して削除しない。自動で
  チェックを付けるのは番組内容まで一致した組（`high`）だけ。組を作り直したとき（1 件ずつの削除・保護、一括処理、
  一覧の再読み込みのあと）は、前と同じ録画でできた組だけ利用者のチェックをそのまま残し、処理中はチェックを
  変えさせない。番組内容は**読めたものだけ**を保存する（空の本文も答えのうち）。820 はレコーダーから消えたもの
  なので一覧から外し、それ以外の失敗は保存せず、組にも入れない。`port/titles.json` のベクタは要約の無いものを
  空として扱う（サーバーと同じ）ので、この絞り込みはその手前で行う。サーバーの `services/titles.py` は今も
  失敗を空として保存します。iOS アプリは、以前の版が失敗を空として保存した行を一度だけ消します（`meta` の
  `blank_summaries_cleared`）。
- **iOS の権限**: LAN への平文 HTTP は `NSAppTransportSecurity` の `NSAllowsLocalNetworking` で許可する。LAN
  アクセスの説明文 `NSLocalNetworkUsageDescription` も必須。SSDP のマルチキャスト送信には
  `com.apple.developer.networking.multicast` エンタイトルメントが要り、Apple への申請が必要。**TCP スキャンだけなら
  不要**なので、まずはスキャンで作る。
- **ローカルネットワークの許可**: iOS は、アプリが初めて LAN に触れたときに利用者へ確認を出します。URLSession は
  確認が出ている最中にも、拒否されたあとにも、圏外と同じ -1009 ですぐに失敗するので、そのまま走査すると確認の裏で
  空振りし、「見つかりません」と出て、許可したあとにもう一度押させることになります。Network framework なら区別が
  つきます。同じサブネットの宛先へ `NWConnection` を張り、経路が `.satisfied` になったら許可済み、
  `unsatisfiedReason` が `.localNetworkDenied` の間は許可されていない、と読めます（TN3179）。許可されると
  システムがその接続をやり直すので、答えを待ってから走査を始めれば 1 回のタップで見つかります。
  - 確認が出ている最中に経路が何を返すかは文書になく、拒否されたあとと区別できる保証もありません。表示は
    どちらにも正しい文言にし（「許可されていません。許可されると、そのまま検索が始まります」）、設定アプリの
    アプリ自身のページ（`UIApplication.openSettingsURLString`）を開くボタンを添えます。一度拒否されると、
    アプリからは二度と確認を出せません。
  - 確認はボタンを押したときに出し、起動時には出しません。手順の説明を読む前にダイアログが重なり、サンプル
    データで試す人と審査担当にも見せることになります。サンプルデータのモードでは LAN に一切触れないこと。
  - 保存済みのアドレスが黙ったときも、起こす前に同じ確認をします。拒否されていればマジックパケットも出ていかない
    ので、起動待ちには入らず、許可を待って接続し直します。許可の変更はネットワークの変化として見えないため、
    「諦めたら諦めたままにする」の唯一の例外になります（利用者自身の操作がきっかけなので矛盾しません）。
  - バックグラウンドの処理（深夜の更新）ではこの確認をしません。未決定のまま通信すると黙って拒否され、その
    ことはどこにも残りません。
- **Android に移植する場合の権限**: `android:usesCleartextTraffic="true"` またはネットワークセキュリティ設定で LAN を
  許可し、SSDP には `WifiManager.MulticastLock` を取る。
- **Wake-on-LAN**: Android はブロードキャスト UDP をそのまま送れます。iOS は、マルチキャストのエンタイトルメントが
  無いアプリのブロードキャストを止めると文書にありますが、止めている箇所（xnu の `bsd/net/necp.c`、
  `necp_check_restricted_multicast_drop`）を読むと、落とすのは 224.0.0.0/4 と `255.255.255.255` だけで、
  サブネットのブロードキャスト（x.x.x.255）とユニキャストは通します。つまり iPhone では `255.255.255.255` 宛てだけが
  毎回 `EHOSTUNREACH` で失敗する見込みです。実機ではまだ確かめていないので、アプリは宛先ごとの結果と errno を
  デバッグログ（サブシステム `RecorderKit`、カテゴリ `wake`）に出しています。ローカルネットワークの許可が無ければ、
  どの宛先にも送れません。MAC は端末から ARP を読めませんが、
  **レコーダーに聞けます**（`X_GetPrivateIp` の `macAddress` / `wirelessMacAddress`、あるいは `description.xml` の
  UDN 末尾 12 桁）。つながっているうちに控えて保存し、次からはそれで起こします。入力欄は「一度もつながって
  いない機体」のための逃げ道として残す程度で十分です。送り先はリミテッドブロードキャスト・レコーダーの
  サブネットのブロードキャスト・**レコーダーのアドレス宛のユニキャスト**の 3 つ（VPN 越しに届くのは最後の 1 つ）。
- **待っていることを画面に出す**: 起こしてから応答までは実測 6〜11 秒、VPN 越しではもっと掛かります。何も出さない
  と故障に見え、「失敗 → 再試行」に見せるのも同じくらい悪いので、マジックパケットは最初のプローブより前に送り、
  待っている間は経過秒数を出し続けます（ボタンを 1 秒ごとに有効／無効させないこと）。
- **サンプルデータのモード**: レコーダーの応答を偽のものに差し替えるだけで、画面は本物のパーサを通ります。
  審査にも、レコーダーを持っていない人の下見にも、ストア用のスクリーンショットにも同じものが使えます。
  キャッシュは**別のデータベースに書く**こと（終了時にファイルごと消せる）。実装は `app/BDBridge/DemoData.swift`。

## App Store 申請の要点

- **審査担当者はレコーダーを持っていません。** 起動しても何も見つからず、機能を評価できないという理由で返される
  可能性があります。これが最大のリスクです。**対策として、チュートリアルの最後と設定画面から入れるサンプル
  データのモードを入れました**（`app/BDBridge/DemoData.swift`）。架空の番組表・録画一覧・予約一覧で、予約の作成・
  変更・削除まで実際に動きます。審査メモには入り方を書き、機種要件とデモ動画のリンクも添えます。
- **アプリ名は独自の名前にします。** 他社の商標は名前にもサブタイトルにも入れず（Apple のガイドライン）、
  対応機種は**説明文の本文**で伝えます。ロゴ、製品写真、本家アプリに似た配色やアイコンは使いません。
- **Info.plist** には `NSLocalNetworkUsageDescription` と `NSAllowsLocalNetworking` を入れます。用途は正直に書きます。
- **プライバシー**: ポリシーの URL は全アプリ必須なので、何も収集しない旨のページを用意します（`privacy.md`）。
  App Privacy の質問票は収集項目なしで答えられます。**`PrivacyInfo.xcprivacy` はまだ入っていません。**
  外部ライブラリは使っていませんが、`UserDefaults` は「理由の宣言が必要な API」なので、提出前に理由コード
  （`CA92.1`）を書いたマニフェストを入れること。TestFlight へのアップロードは通っていますが、審査提出時に
  ITMS-91053 で止まる可能性があります。
- **費用と手続き**: 個人登録で足ります。無料アプリなら銀行口座と税務情報の登録は不要です。iPhone のみにすると
  iPad 用のスクリーンショットと動作保証が不要になり、面倒が減ります。
- スクリーンショットの要求サイズは変わります。申請時に App Store Connect の最新の要件を確認してください。
  撮り方（サンプルデータで撮る手順、寸法とシミュレータの対応、はまりどころ）は
  `app/scripts/screenshots/README.md`。

Android を配布する人向けの注意も一つ書いておきます。Play ストアを使わず APK を直接配る形は、Play Protect の警告、
自動更新の欠如、そして認証済み端末へのサイドロードに開発者の本人確認を求める動きがあるため、一般利用者向けには
向きません。配布前に最新の要件を確認してください。

## 検証ベクタ（`docs/port/`）

`uv run python -m bdzbridge.tools.portkit` が Python 実装から生成します（テストが鮮度を確認するので、手で直さないこと）。
移植側では次のようなテストを書きます。

- `codes.json` — 定数の一致（コード表、ファイル名、ARIB 記号表、ロゴの共通カラーテーブル、名前空間、制御 URL）。
- `xsrs.json` —
  - `create_elements[*].input` から Elements 文字列を組み立て、`elements` と**完全一致**させる。
  - `update_elements` / `title_update_elements` も同様。
  - `parse_reservation.item` / `parse_title[*].item` を解析して `expected` と一致させる（`notplayed` の扱いを含む）。
  - `soap.example.body` と同じ本文を作れること。
- `description.json` — `description_xml` を解析して `expected` の各値（機種名、UDN、EPG 対応）を得ること。他社機や
  レコーダー以外のソニー機を弾くこと（製造者が Sony Corporation かつ XSRS サービスを持つもの）。
- `epg-sample.dat` → `epg-sample.json` — 復号結果が一致すること（時刻は ISO 8601 の `+09:00`、参照イベント、ジャンル、
  コピー制御、視聴年齢、記号置換）。実機ファイルでの検証は `server/tests/test_epg.py` の要領で自分のレコーダーから取る。
- `logo-sample.dat` → `logo-sample.json` — チャンネル番号と service_id の対応、ロゴのない局のスキップ、PLTE/tRNS 挿入後の
  PNG が `png_base64` と一致すること。
- `series.json` — `series_name` / `series_key` / `same_title_key` / `summary_key` の各値の一致。
- `titles.json` — 視聴状態（未視聴／途中／視聴済み）、番組ごとの「まとめ」（件数・容量・未視聴数・保護数）、
  重複の検出（候補の作り方、内容による分割、残す 1 本とその理由）。**録画中のものは残す側に固定**され、削除候補には
  入りません。

## 他のプラットフォームに移植するときの順番

上の表と同じ順序で積むのがいちばん楽でした。

1. プロトコル層: `description.xml` の解析 → SOAP → 予約一覧の取得（読み取りだけ）。`xsrs.json` と `description.json` を通す。
2. EPG: ファイル取得と復号、端末内 DB、日別・チャンネル別の表示。`epg-sample` を通し、実機ファイルで Python と突き合わせる。
3. **サンプルデータのモード**: ここで作っておくと、実機がなくても UI を進められて、申請にもスクリーンショットにも
   そのまま使えます。
4. 予約: 作成・更新・削除と番組追従。テスト用の予約名を決めて作成→削除で確認する（録画の削除はテストに使わない）。
5. 録画: 一覧、詳細、保護、削除、テレビ再生、まとめ、重複。`series.json` と `titles.json` を通す。
6. 宅外: 送信待ちキュー、Wake-on-LAN、諦め方。
7. 仕上げ: おまかせ・まる録、ロゴ、残容量の警告、定期更新、通知。
