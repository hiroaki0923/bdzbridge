# ネイティブアプリへの移植ガイド

bdzbridge はサーバー（Python）とブラウザ（PWA）、それに iOS アプリ（`app/`）の 3 つで動いています。サーバーも
VPN 前提の構成も要らずアプリがレコーダーと直接話す形が iOS アプリで、**これは実機で動いています**。このドキュメントは
「何をそのまま持っていき、何を作り直し、何で検証するか」と、実機で分かったレコーダーの癖をまとめたものです。
プロトコルそのものの説明は [`xsrs-api.md`](xsrs-api.md) と [`epg-format.md`](epg-format.md) にあり、ここでは
繰り返しません。

読者は 2 通りです。

- **iOS アプリに手を入れる人**: 下の「Swift での対応」「レコーダーの振る舞いチェックリスト」「端末側の設計メモ」が
  実装の背景です。アプリの構成そのものは `app/README.md`。
- **他のプラットフォームに移植する人**: Android ネイティブは作者の予定にありません。必要と思った人が作れるように、
  機種依存の知識と検証ベクタは言語に依存しない形にしてあります。Android 利用者向けの現状の道は、サーバーを自分で
  動かして PWA を使うことです。

## 前提と方針

- レコーダーの API は LAN 内で無認証です。アプリはレコーダーと同じネットワークにいるとき（VPN で自宅の
  ネットワークに入っている場合を含む）に動作します。届かないときはキャッシュ済みの番組表を見て、予約は
  「送信待ち」として端末に溜め、**次にレコーダーに接続できたとき**に送ります（帰宅を待つ必要はありません。
  VPN 越しにレコーダーを起こして送れることも実機で確認しています）。
- Python のサーバーは移植中も動かし続け、**正解（oracle）**として使います。同じレコーダーに対して両方から
  同じ操作をして結果を突き合わせるのがいちばん確実な検証です（書き込みは予約の作成→削除で行い、録画の削除は
  テストに使わないこと）。
- 機種依存の知識はすべて `server/bdzbridge/recorder/` に閉じ込めてあります。移植の中心はこのディレクトリです。

## 何を持っていくか

| Python 側 | 役割 | 移植先での扱い | 検証ベクタ |
|---|---|---|---|
| `recorder/discovery.py` | SSDP M-SEARCH → 見つからなければ /24 を TCP 64220 でスキャン → `description.xml` で確認 | 必須。SSDP はマルチキャストの権限が要る（後述）。スキャンだけでも成立する | `port/description.json` |
| `recorder/client.py` | 1 台分の状態、EPG/ロゴのダウンロード、DLNA ツリーから配信ポートの検出、**全リクエストを直列化するロック** | 必須。ロックは絶対に省かない（並行リクエストに 503 を返す）。配信ポートの検出は**番組表ファイルが必要になった時点で 1 回だけ**行う（後述） | — |
| `recorder/xsrs.py` | SOAP の組み立て、予約/録画 item の解析、`build_create_elements` | 必須。生成する XML は Python とバイト単位で一致させる | `port/xsrs.json` |
| `recorder/codes.py` | 放送種別・画質・毎回録画・ジャンルのコード表、EPG/ロゴのファイル名 | そのまま定数に | `port/codes.json` |
| `recorder/epg.py` | EPG ファイルの復号（XOR 0x9D → 連結 zlib → @SRV/@DAY/@EVT）、ARIB 記号の置換 | 必須 | `port/epg-sample.{dat,json}` |
| `recorder/logo.py` | 局ロゴファイルの復号、PLTE/tRNS の挿入 | 任意（見た目） | `port/logo-sample.{dat,json}` |
| `recorder/series.py` | 録画タイトルからの番組名抽出（まとめ表示）、重複検出のキー | 必須（まとめ・重複を出すなら）。正規表現をそのまま移す。結果はタイトルごとに覚えておく（まとめは描画のたびに全録画を通すので、毎回求めると 1,300 本で数十 ms かかる） | `port/series.json` |
| `recorder/wol.py` | Wake-on-LAN | **必須に近い**。レコーダーは時間の 4 分の 3 を寝て過ごすので例外処理ではなく通常の経路。**MAC はレコーダー自身が教えてくれる**（`X_GetPrivateIp`、または `description.xml` の UDN 末尾）ので、利用者に入力させる必要はない | — |
| `store/guide.py` | SQLite の番組表キャッシュ（検索用正規化、サブチャンネルの参照解決、放送日 04:00 区切り） | 端末内 DB に作り直す。仕様は下記「番組表の扱い」 | — |
| `store/rules.py` + `services/autorec.py` | 番組表からのキーワード自動予約（サーバー側の機能） | 任意。**iOS アプリでは作っていません**: レコーダー本体の「おまかせ・まる録」を読み書きできるので、アプリを閉じていても本体が録ってくれる方を採りました | — |
| `services/titles.py` | 全録画リストのキャッシュ、まとめ、重複検出、一括削除/保護 | ロジックはそのまま。一括処理は端末内で逐次実行し、中止できるようにする | — |
| `jobs.py`, `api/`, `services/notify.py`, `services/monitor.py` | サーバーならではの部分（HTTP API、ジョブ、SMTP/webhook 通知、残容量監視） | 不要。通知は端末のローカル通知で代替 | — |

## Swift での対応

すべて OS 標準の機能で足ります。外部ライブラリは要りません。

| やること | 使うもの |
|---|---|
| LAN への HTTP と SOAP | `URLSession`。1 台につき 1 本に直列化するため、`actor` で包むか `OperationQueue` の同時実行数を 1 にする |
| /24 の TCP スキャン | 各アドレスに、レコーダーの `description.xml`（64220 番）とテレビの `getInterfaceInformation`（80 番。登録が要らず、cookie を付けない）を `URLSession` で同時に尋ねる（`DeviceSearch.scan`。48 アドレス並列なので 96 本、1 本 1.2 秒で打ち切り）。答えの中身でレコーダーかテレビかが決まるので、ポートだけを見る走査は別に要らない。許可を待たず、押すとすぐに 1 回走査し、結果はすぐに言う。確認の裏で拒否されたときは、拒否されたアドレスに 1 秒ごとに尋ね直し、外へ出たら走査し直す（下の「ローカルネットワークの許可」） |
| SSDP | `NWConnection` のマルチキャスト。エンタイトルメント申請が必要なので後回しにする |
| Wake-on-LAN | BSD ソケット（`socket`、`setsockopt(SO_BROADCAST)`、`sendto`）の UDP。Network framework にはブロードキャストを送る手段がない。宛先は 3 つ（`255.255.255.255`、レコーダーのサブネットのブロードキャスト、**レコーダーのアドレス宛のユニキャスト**）。VPN 越しに届くのはユニキャストだけ。iPhone で実際に出ていくのはこのうち 2 つの見込み（下の「Wake-on-LAN」） |
| 連結 zlib の展開 | `libz` を直接使い、`z_stream` の未消費バイト数から次のストリームの開始位置を求める。`import zlib` がそのまま通り、iOS SDK でも解決します。Compression framework でも消費量は追えるが、境界の判定を自分で書くことになる |
| XML の解析 | `XMLParser`。SOAP 応答と DIDL-Lite の両方に使う |
| XML の生成 | 文字列連結で十分。要素の順序を固定したいので、汎用のシリアライザは使わない方が確実 |
| 番組表の保存 | SQLite。検索用に NFKC + casefold 済みの列を持たせる。ファイルは Application Support の下のフォルダ（`Guide/`）に置き、**フォルダごと**バックアップから外す（-wal と -shm は作り直されるので、ファイルに付けた印は消える）。画面と深夜の処理はそれぞれ接続を開くので、`sqlite3_busy_timeout` で 5 秒待たせる（無いと、重なった書き込みがすぐ「database is locked」で失敗する） |
| テレビの登録の保存 | キーチェーンの 1 項目（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: 再起動のあと最初のロック解除からは、ロック中の深夜の処理とショートカットも読めて、ほかの端末には移らない）。中身はクライアント ID と cookie の JSON を CryptoKit の AES-GCM で封じたもの。鍵は 32 バイトのファイル（`Application Support/television.key`。`.atomic` と `completeUntilFirstUserAuthentication` で書く）で、`Guide/` の外に置いてバックアップに入れる（同じ端末への復元で項目と一緒に戻る）。アプリを消すと鍵が消えるので、キーチェーンに残るかもしれない項目はだれにも開けない（アプリを消したときの項目の扱いを Apple の文書はどちらとも言っていない）。**読むときは書かず、消さない**: 鍵が無い、鍵で開かない（封じる前の版が書いた平文の JSON も）なら「登録なし」で、項目はそのまま。鍵のファイルが読めない（最初のロック解除の前、権限）のは鍵が無いのとは別で、保存もしない。長さが 32 バイトでないファイルは鍵なし。保存は、鍵が無ければ鍵を先に書き、書けたときだけ項目を書く。外すときは項目と鍵の両方を消す（`KeychainTVCredentials`） |
| 定期更新 | `BGProcessingTask`（`requiresNetworkConnectivity`、深夜 2 時を `earliestBeginDate` に）。呼ばれる保証がないので手動更新も必ず置く。**この中でもレコーダーを起こすこと**: 深夜はまず寝ている。期限切れのハンドラでは**その場で**完了を伝え（処理の終わりと重なっても 1 回だけ）、処理のほうは種別の切り替わりで取り消しを見て止める。取り消しても送信中の要求は最後まで待つので、処理の終わりを待って完了すると、番組表ファイル 1 本で 2 分待たせることになる。テレビ宛の送信待ちも、同じタスクの中でレコーダーの処理と並べて送る（識別子もモードも増やさない） |
| 通知 | `UNUserNotificationCenter`。自動予約の結果と残容量の警告に使う。許可の取り方は下の「通知の許可」 |

UI で唯一手間がかかるのは番組表の表形式です。時間軸とチャンネル軸の 2 方向スクロール、両方向に残るヘッダー、
ピンチでの時間軸の拡大縮小は SwiftUI でも自前で組む必要があります。PWA 側の `GuideGrid.svelte` が仕様書代わりになります。

## レコーダーの振る舞いチェックリスト

実機（BDZ-FBT4100）で分かったこと。どれもコードにコメントとして残っていますが、移植時に踏みやすい順に並べます。

**通信**
- 同時リクエストは 503。1 台につき 1 本のキューで直列化する（アプリではクライアントが 1 本ずつ持つ）。それでも
  ほかのクライアント（公式アプリ、別の端末、同じアプリの深夜の処理）とはぶつかるので、503 は**キューの中で**
  0.5〜1 秒（ランダム）おいて 2 回まで送り直し、それでも 503 なら「ほかの要求を処理中」として返す。
  どの呼び出し元も 503 を独自に読み違えていた
  （`description.xml` では「ソニー製レコーダーではない」、番組表ファイルでは「まだ作られていない」）。
- XSRS の制御 URL は `/XSRS`、X_PvrControl は `/X_PvrControl`、ContentDirectory は `/DMSContentDirectory`。ポートは 64220。
- SOAP ヘッダは `Content-Type: text/xml; charset="utf-8"`、`SOAPACTION: "<serviceType>#<action>"`、`Accept-Language: ja`。
  本文の形は `port/xsrs.json` の `soap.example`。
- エラーは HTTP 500 + SOAP Fault の `errorCode`。402 は引数の形式違反（例: 時刻のオフセットが `+0900`）、
  804 は存在しない予約 ID、820 は存在しないタイトル ID、831 は受信できないチャンネルの番組を追従予約しようとした、
  880 はレコーダーがネットワークスタンバイ中で再生できない。**errorCode の無い素の HTTP 500 もあります**
  （録画中のタイトルの削除。後述）。
- EPG/ロゴのファイルは別ポート（既定 60151）から `//EPG_TRDEPG_FILE.dat` のように**スラッシュ 2 つ**で取る。ポートは
  DLNA ツリーの最初の `<res>` URL から確認できる。そのチャンネル種別を持っていない場合は 416 が返る。
- **`description.xml` の取得に余計な処理を足さないこと。** 上の配信ポート検出（Browse を最大 8 回）を
  `describe` の中でやっていたため、「2 秒で諦めるはずの生存確認」が数分かかりました。起動待ちのプローブは
  `description.xml` 1 本だけにして、ポート検出は番組表ファイルを取る直前に 1 回だけ行います。
- ネットワークスタンバイ中でも API は答える。電源を入れるのは `X_PowerControl` の `on`（`PowerOn` や `On` は不可）。
- レコーダーが完全に落ちている（電源オフ後しばらく）と何も答えない。Wake-on-LAN で起きる。本体の「ネットワーク待機」が
  切だと、しばらく操作がないだけで LAN から消えるので、これは例外ではなく普通に起きる。
- **レコーダーは自分から起きます。** 12 時間つないだまま 1 分ごとに 64220 を見た記録（2026-09-17、誰も操作していない
  時間帯を含む）:

  | | 回数 | 中央値 | 最短 | 最長 |
  |---|---|---|---|---|
  | 寝ている時間 | 13 | 27 分 | 2 分 | 136 分 |
  | 起きている時間 | 12 | 10 分 | 2 分 | 81 分 |

  応答していたのは全体の **25%**。周期は一定ではなく、2 分で起きることも 2 時間寝ていることもあります。設計上の
  意味は 2 つです。**(1) 「寝ている」は恒久的な状態ではない**ので、溜めた予約を送る機会は放っておいても来ます
  （中央値 27 分待ち）。**(2) 逆に、起きているのは 4 分の 1 の時間だけ**なので、アプリを開いた瞬間につながっている
  ことは期待できず、Wake-on-LAN は例外処理ではなく通常の経路として要ります。
  何のために起きているのかは LAN 側からは見えません（外部サービスとの通信を覗く手段がない）。
- **Wake-on-LAN はレコーダー自身が申告しています。** `description.xml` の `X_WakeupOnLAN` が `1`（取説には記載なし、
  公式クライアントもこの値を読む）。
  宛先の MAC は 2 通りで取れるので、ユーザーに入力させる必要はありません。`X_PvrControl` の `X_GetPrivateIp` が
  `macAddress` と `wirelessMacAddress` を返すのが正攻法で、`description.xml` の `<UDN>` の末尾 12 桁も同じ有線 MAC です
  （`uuid:XXXXXXXX-XXXX-XXXX-XXXX-<MAC>`、実機で ARP と一致）。iOS は ARP を読めないので、起きているうちに控えておくのが
  唯一の手です。有線と無線で MAC が違うので、繋いでいる側を使うこと。
- **Wake-on-LAN は同じサブネットにいるときだけ確実です。** `255.255.255.255` はルーターを越えず、VPN 越しの端末は
  自分のインターフェースから自宅のサブネットを知ることができません。レコーダーのアドレスからそのサブネットの
  ブロードキャストを組み立てて送る手はありますが、ゲートウェイがディレクテッドブロードキャストを転送する設定で
  なければ届きません（UniFi は既定で転送しません）。**レコーダーのアドレス宛のユニキャストでも起きます**（実測:
  ブロードキャストを一切使わず、同じセグメントからアドレス宛にポート 9 と 7 へ送って 6 秒で応答）。
  どちらの実装も、リミテッドブロードキャスト・サブネットのブロードキャスト・レコーダーのアドレスの 3 つへ送ります。
- **VPN 越しにも起きました。** 外出先から VPN でつないだ iPhone のアプリが、寝ていたレコーダーを起こして接続
  できています（寝てから 2 分後、起きるまで 2 分ほど）。届いたのはアドレス宛のユニキャストで、
  ブロードキャストは VPN を越えません。ただし**ゲートウェイがそのアドレスの MAC を覚えている間だけ**のはずで、
  何時間も寝たあとに同じことができるかは未確認です。キャッシュが切れた後は LAN の内側にいる何かに送ってもらう
  しかありません。自宅にサーバーを置いているなら `POST /api/v1/recorder/wake` がその役目を果たします。
- **この機種は ICMP に答えません。** 起きていても ping は通らないので、死活監視には使えません（UPnP のポート
  64220 に繋がるかで見ます）。「ping に答えない＝ネットワークにいない」とは言えない、ということでもあります。
- `X_GetPrivateIp` は `useDhcp` も返します。アドレスが DHCP で動く機体なら、保存した IP に繋ぐだけの実装は取りこぼします。
  サーバー側は UDN で再探索していますが、移植先でも同じ手当てが必要です。
- サービスは 5 つに見えて実質 4 つ。`/XSRSExt`（`X_ScheduledRecordingExt:1`）は `/XSRS` と SCPD が完全に同一で、同じ答えを
  返します。詳細は `upnp/service-sweep.md`。

**予約**
- `X_CreateRecordSchedule` の `<Elements>` は公式アプリの送信内容と同一にする（`port/xsrs.json` の `create_elements[0]`
  は実キャプチャ由来）。要素の順序、`channelType="2"`、`scheduledChannelID` の `0x0428` 形式、時刻の `+09:00`。
- `desiredMatchingID` に `,,0x<service>,0x<event>` を入れると番組追従になり、タイトルはレコーダーが EPG から上書きする。
  時間指定（event なし）の予約は後から event_id が補完されることはない。
- 更新は同じ item に `id` を付けて `X_UpdateRecordSchedule`。画質・毎回録画をその場で変えられる。
- **更新は録画先も書き換えます。** item の `recordDestinationID`（本体の HDD は `HDD`、USB HDD は `USBHDD`）を
  `HDD` の決め打ちで送ると、USB HDD への予約が本体の HDD に黙って移ります（実測）。録画先を変えない変更では、
  読み直した一覧にあるその予約の値をそのまま送ること（`ReservationRequest(changing:)`）。`USBHDD` を書いた更新では
  USB HDD のまま、番組追従も続きます（実測。`LiveRecorderTests.testAChangeKeepsTheUSBDisk`）。録画先を移す変更は
  両向きとも通り、予約の ID も番組追従も変わりません（実測）。
  USB HDD への予約は、作成要求のこの値だけを `USBHDD` に変えれば通ります（時刻指定の予約と番組追従の予約で確認）。
  **USB HDD を外していても通り**、一覧にも `USBHDD` で載ります（時刻指定の予約で一度。外したまま録画の時刻が
  来たときにどこに録画されるかは未確認）。起こした直後の数秒（USB HDD を「無し」と答える間）に作った予約は
  確かめていません。アプリがその間には送らないためです（下の「録画先の選び方」）。
- **録画先の選び方**（アプリ）: 録画できる USB HDD（登録済みで、つながっていて、大きさのあるもの）を知っている
  あいだだけ、番組の画面の新しい予約に「録画先」を出し、本体の HDD（「HDD」、レコーダー自身の呼び名）を先に、
  いつもそれを選んだ状態で始めます（`RecorderDisk.choices`）。起こした直後の「無し」で手放さずにいるディスクも、
  答えたディスクと同じに出します。ただし、レコーダーが最後に答えてから USB HDD が答えていないディスクを当てにして
  は何も送りません。待つのは、知っているディスク（画面のもの、またはキャッシュに残したもの）があるときに、接続を
  始めた時（画面のディスクがあるとき。起きかけのレコーダーに問い合わせている間も）か、接続でレコーダーが答えた時
  から（送信待ちを送る前から）、USB HDD がディスクか「無し」を答えるまでです。接続自身が USB HDD
  を読む間も、30 秒後の読み直しまでの間も、読み直しが無応答か 503 で何も決めずに終わったあとも待ちます
  （`SessionState.usbDiskUnanswered`）。そのあいだ、そのディスクを録画先にした予約、変更（移す先がそれか、その上の
  予約）、条件、重複の確認は、レコーダーを確かめたあと、送る前に USB HDD を 2 秒ごとに最長 10 秒読みます
  （`RecorderDriver.settleTheSlot`。待つ間、画面は「録画先のディスクを確かめています」と出し、ほかの要求の間と同じ
  にボタンを止める。条件の画面は、押した時から「レコーダーに登録中」を出してボタンを止めるので、レコーダーを確かめ
  る間に 2 度押しても条件は 1 つ）。ディスクを答えたら、読み直しと同じにそれを取って 30 秒後の読み直しをやめ、録画
  できるディスクなら送ります。最後まで「無し」なら何も送らず、ディスクも読み直しもそのままにして（待つことも続く）、
  出せなくなった録画先と同じに言い、画面も同じに戻ります。答えたディスクが録画できない（つながっていない）ときも同
  じです。待つ間に無応答なら、ほかの読み取りと同じに接続を失い、予約は何も送っていないので送信待ちに入ります。答え
  たディスクを持っているあいだと、USB HDD の無い家では、何も読み足しません。重複の確認は画面に出ている録画先で尋ね、
  予約の前の確認には録画先を書きます。
  予約の画面は、変えられるあいだ録画先を移せ、移したときだけその録画先を送ります（移さなければ、送る時点で
  レコーダーが持っている録画先のまま）。録画先が出せなくなった USB HDD 上の予約も、本体の HDD へは移せます。
  画面は利用者が選んだ録画先をそのまま渡し、送る直前にそれがもう出せないもの（読み直しで外れた USB HDD）なら、
  何も送らず、送信待ちにもせず、ディスクの名前を挙げて言います。本体の HDD を代わりに送ると、利用者が同意して
  いない予約になるためです。画面にほかの録画先があれば、別の録画先を選ぶよう言い、画面は本体の HDD に戻ります
  （番組の画面では、テレビが番組を受けられれば「予約先」にテレビも出ています）。本体の HDD 上の予約の画面は、
  USB HDD が外れると選ぶ欄ごと無くなり、ほかに選べるものが無いので、移す変更を断ったときは、予約が本体の HDD の
  ままであることを言います（`RecorderDisk.stays`。どちらを言うかは、レコーダーのドライバーが、画面が録画先を
  出すのと同じ規則（`RecorderDisk.choices(keeping:on:with:)`）で決める）。
  番組の画面で、選んだあとに外れた録画先は、値として出たまま、重複の確認を尋ねず（欄には何も出さない）、
  「録画予約する」で確認を出さずにすぐ断ります（確認は、断ると分かっている登録を約束してしまうため）。
  USB HDD への予約や移動をレコーダーが断ったときは、コードだけでなく、そのディスクへの予約を受け付けなかったことを
  ディスクの名前を挙げて言い、別の録画先を選ぶよう言います（`RecorderDisk.turnedDown`。ディスクそのものを断ったとは
  言わない。コードはそこまで言わないため）。理由が別にあるもの（受信できないチャンネルの 831、無いアクションの
  401、該当なしの 501・701、予約のものでなくなった ID の 804）と、本体の HDD への断りは、これまでどおりの文です。
  宅外で作った予約は録画先ごと送信待ちに入り（キューの表の `destination` 列。以前の版の行は本体の HDD）、
  そのまま送って、レコーダーの答えに任せます。ただし、キャッシュに USB HDD を残しているあいだは、`USBHDD` 宛の行を
  送る前に、その回で 1 度だけ同じように USB HDD を待ち、画面と同じに読みます。録画できるディスクを答えれば送り、最
  後まで「無し」か、録画できないディスクを答えたら、`USBHDD` 宛の行には何も送らず、理由を書きます
  （`RecorderDisk.waitingRowNotAnswered`。「録画先のディスクが応答しませんでした。つなぎ直してからもう一度送るか、
  この予約を消して別の録画先で予約し直してください」。ディスクの名前は行の上の段に出ているので入れない）。何も書か
  ずに見送ると、番組が終わるまで送られないことがあるためです。画面の無い処理（深夜とショートカット）は知っているデ
  ィスクを手放さないので、ディスクが本当に外れていれば毎晩黙って見送ることになり、アプリでも、あとでディスクが答え
  たときにその行を送り直すものがありません。理由の付いた行は、断られた行と同じに読み手を待ち、同じに知らせます（帯、
  通知、ショートカットの答えの「…理由は予約タブにあります」。これだけが起きた回でも知らせる）。「もう一度送る」は
  理由を消して、その回でまた USB HDD を待ち、答えれば送ります。消すこともできます。待つ間に無応答なら、何も書かず
  にその回を打ち切ります（ほかの無応答と同じ）。回そのものが取りやめられたときは見送ります。本体の HDD 宛の行は送
  り、待たせるのはその 1 度の間だけです。接続、引き下げ、もう一度送る、深夜の処理、ショートカットのどれから送って
  も同じです。回は画面が読んだことを知らないので、画面がディスクの答えを得たあと（接続中のもう一度送る）でも、1 回
  読み足します。USB HDD を知らなければ読まずに送り、レコーダーの答えに任せます。
  本体の HDD 以外の行を同じ規則のコードで断られたら、行の理由は、この録画先への予約を受け付けなかったことと、
  送信待ちの行は録画先を変えられないので、消して別の録画先で予約し直すことを言います
  （`RecorderDisk.waitingRowTurnedDown`。ディスクの名前は送る側が知らず、行の上の段に出ているので
  入れない）。行の録画先は、レコーダーの行で本体の HDD 以外のときだけ、知っているディスクの名前で（知らなければ
  `USBHDD`）出します（`RecorderDisk.shown`）。テレビの行には出しません。USB HDD の無い家では何も出ず、送る要求も
  以前のままです。
- 毎週の毎回録画（`w1`〜`w7`）は番組の曜日と一致させる。
- 一覧は `X_GetRecordScheduleList`、1 回 200 件まで。ソートは `-scheduledStartDateTime`。返った件数が 200 に
  届いていて、ほかにもあると言われている（`TotalMatches`）ときは、一覧に無いことは、レコーダーに無いことに
  なりません（アプリは頁を送って読みません。そのため「削除されていました」ではなく「一覧に見つかりませんでした」と
  言い、送信待ちの行がレコーダーに無いと決めるのは、返った件数が 200 より少なく、ほかにあると言われていない
  ときだけです。返った件数は、読めた行ではなく、返った `<item>` で数えます）。`TotalMatches` を実機で読んだことは
  まだありません。
- **予約 ID は振り直されます。** レコーダーが自分のおまかせ・まる録で入れた予約は、番組表を読み直したときに
  ブロックごと番号が変わります（実測: 19 件が一斉に変わり、番組自体は同じまま）。数時間前に読んだ ID で削除や
  更新をすると 804 になります。**削除・更新の前に一覧を読み直し、同じ予約を探し直すこと**。アプリは、ID が
  まだ同じ番組（放送の種別、局、番組 ID。時刻で入れた予約は開始）に付いている間だけ、その ID の行を同じ予約とし、
  別の番組に付いていれば何も送らずに「更新されていました」と言います（繰り返しの予約が、同じ ID のまま次の回に
  進んだときもこうなり、利用者は読み直した一覧からもう一度押します）。ID が無くなっていれば、チャンネルと開始
  時刻で探しますが、見つけるのは、同じ作成者が入れた、同じ番組 ID（時刻で入れた予約なら番組 ID の無いもの）の
  行だけです（`[Reservation].target(of:)`）。番号を振り直すのはレコーダーが自分で入れた予約だけだと見ているので、
  アプリが入れた予約（作成者 2200）の ID が無くなっていれば、探さずに無くなったものとします。チャンネルと開始
  時刻だけで探すと、利用者がレコーダー本体の画面で消した予約の代わりに、同じ番組をレコーダーが自分で入れた
  予約を変えたり消したりしていました。本当に無くなっているのは、探して見つからないときだけです。
- `X_GetConflictList` に作成と同じ Elements を渡すと重なる予約が返る。作成と同じ本文を投げるので、**実際に
  作らずに本文の妥当性まで確かめられます**。

**録画タイトル**
- `X_GetTitleList` は、本体の HDD なら SearchCriteria を空で（公式クライアントと同じ）、USB HDD なら
  `recordDestinationID="USBHDD"`（空白なし、引用符つき）で検索し、1 回 200 件まで。`TotalMatches` を見て、各ページが
  返した件数ずつ進めて繰り返す。レコーダーは読めない条件を「全件」と読むので、録画先を指定して読むときは各行の
  `recordDestinationID` で絞り直す。指定しないときは返った行をすべて残す（アプリの録画一覧はこれで、以前と同じ）。
- `lastPlaybackTime` は未再生だと本文が `notplayed`。`resumePoint` 属性が再生位置（秒）。
- `genreID` は ARIB のレベル1×16＋レベル2。
- `X_UpdateTitle` は `<item id>` と変える要素だけを送る（`titleProtectFlag`、`titleNewFlag`、`title`）。
- `X_DeleteTitle` は保護中なら失敗、**存在しない ID には成功を返す**。削除前に `X_GetTitleDetail` で存在を確かめる。
  1 件 3 秒ほどかかる。
- **録画中のタイトルも一覧に出ます。** item の `recordingFlag` が `1`。これを消そうとすると
  **errorCode の無い HTTP 500** が返るので（820 のような手がかりが無い）、削除の前にフラグを見て、画面にも
  「録画中」と出すこと。完了したタイトルが `0` であることは実機で確認済み、`1` の観測は未了（予約一覧の
  同名フラグと同じ意味と解釈）。
- 再生は `X_PlayControlTitle`（`play` / `stop` / `pause`、小文字。`pause` はトグルで再開も同じ）。テレビ側で再生される。
  `Position` を付けても先頭から始まるので、途中まで見た録画のボタンは「最初から再生」にしてある。
- ネットワークスタンバイ中の `play` は 880。アプリはそのときだけ `X_PowerControl` の `on` を送り、
  `X_GetPlayStatus` の `powerstatus` が `PowerOn` になるまで 1 秒ごとに見て（最長 30 秒、経過秒数を画面に出
  す）、もう一度 `play` を送る（ドライバーの `play`。クライアントの公開の要求を同じ順に送り、電源を入れる前と
  2 回目の `play` の前に、そのレコーダーをまだ手放していないか、書き込んでよいかを確かめる）。先に電源状態は確
  かめない: 電源が入っているときに毎回 1 往復増えるうえ、サンプルデータのレコーダーは `powerstatus` を返さな
  い。待っても入らなければ 880 のまま返り、手で電源を入れるボタンが出る。
- 残容量は ContentDirectory の `X_HDLnkGetRecordDestinationInfo`（バイト単位）。`RecordDestinationInfo` 要素の中に
  エスケープされた XML があり、その `totalCapacity` / `availableCapacity` 属性が値。何を渡しても本体の HDD の値。
- **USB HDD は、確かめた経路では `X_PvrControl` の `X_GetMediaInfo(USBHDD)` だけが言いました**（形と、確かめた
  経路は `xsrs-api.md` の「USB HDD」。DLNA のツリーはまだ見ていない）。`remain` / `total` は MB（10^6 バイトと推定）。
  `registeredTime` のある、登録済みのディスクだけを USB HDD とし、断り、読めない答え、`mount` の無い答え、登録時刻の
  無い答えは「無し」にします。ディスクを外したときの答えは、起こした直後の「無し」と同じでした（1 回の読み取りでは
  見分けられない。差し直すと最初の読み取りで、同じ名前と登録時刻のディスクを答えた）。一度も登録していない機体の
  答えは未確認です。
  アプリは接続のたびと深夜の処理でこれを 1 回読みます。接続では送信待ちを送ったあとに読み、遅くても無応答でも
  送信待ちを止めません（無応答なら接続は失敗）。深夜の処理は、ここで無応答なら残容量も番組表も取らずに終わります。
  **起こした直後に読むと、ディスクがつながっていても「無し」と答えました**（時間を測った一度では、レコーダーが答えはじ
  めて 5 秒後の読み取りでディスクを答えた。`xsrs-api.md`）。そこで、知っている USB HDD があるときの「無し」ではディス
  クを手放さず、画面には読んだときのまま見せ、30 秒後にもう一度だけ読みます（レコーダーが答えてから USB HDD が
  答えるまでの間に USB HDD 宛のものを送るときは、先に最長 10 秒待つ。上の「予約」の「録画先の選び方」）。そこでも
  「無し」か断りなら手放し、ディスクを答えればそれを取ります。読み直しの無応答と、送り直しても 503（ほかの要求を
  処理中）のときは何も変えず（USB HDD 宛のものの前に待つことも続く）、答えが返っ
  たときに接続が別のクライアントで進んでいれば、その答えは捨てます。読み直しは 1 回の要求で、接続も送信待ちも待たせず
  、別の機器、機器を忘れたときに取りやめます（`DeviceLink.readLater`）。アプリが背景に回ったときも取りやめ、接続せずに
  戻ったとき（最後の応答から 1 分以内）は、戻ったときからもう一度待ちます。ディスクを答えたとき（同じでも別でも）は、
  すぐにそれを取ります。知っている USB HDD は番組表キャッシュに残し（別のレコーダーに移ると消える）、起動して最初の接
  続でも使います。深夜の処理は「無し」と読んでも手放しません。そのディスクが録画できるものなら、内蔵 HDD の通知には「H
  DD」と名前を付け、番組表を取ったあとにもう一度だけ読んで、ディスクを答えれば USB HDD の通知を出します（そういう夜に 
  1 回増える。USB HDD の無い家では増えない）。USB HDD の無い家でも 1 回増えるのは、確かめた経路にほかの手段が無かった
  ためです。ディスクの見分けは、id と登録時刻と名前がすべて同じかどうか（`RecorderDisk.isSameDisk`。名前を変えたディス
  クは別のディスクと見る）。
- サムネイルは全タイトル共通のダミー画像なので出さない。番組内容は `X_GetTitleDetail`（summary と detail 群）。
- DLNA ツリーにはシリーズ ID がない。「まとめ」はタイトル文字列から `series.py` の規則で作る。公式クライアントも
  同じくクライアント側でタイトル文字列から鍵を作っている。
- レコーダー本体の「おまかせ・まる録」（キーワード自動録画）は `X_GetPrefRecSettingList` で読め、
  `X_CreatePrefRecSetting` / `X_DeletePrefRecSetting` で作成・削除できる。**変更は実装しない**: 一覧には本体で設定した
  対象チャンネルが含まれず、書き戻すとそれが消える（実測）。`Filter` は `*` を渡すこと。録画モードは放送波ごとに
  2 つあり、`ALL`（と知らない放送波）の条件では `desiredQualityMode` と `desiredQualityModeForAdvanced` の両方に
  入れる。片方だけだと 4K 側が DR になる（実測）。形と語彙は `xsrs-api.md`、ベクタは `port/xsrs.json` の `recorder_rules`。
  録画先（`recordDestinationID`）を `USBHDD` にした条件も受け付けられ、一覧にも `USBHDD` で返り、本体の画面には
  「後面ＵＳＢ」と出ます（実測）。アプリは予約と同じ規則で、録画できる USB HDD を知っているあいだだけ条件の追加に
  「録画先」を出し、送る直前に出せなくなっていれば送らずに別の録画先を選ぶよう言い、行には本体の HDD 以外のときだけ
  録画先を出します。条件は変更しないので、録画先を変えるには削除して作り直します。

**番組表**
- 時刻は 1970-01-01 00:00 **JST** 起点の秒（unix 時刻 + 32400）。
- サブチャンネル（例: 総合 2）の「参照」イベントは開始・終了と親の service/event しか持たない。表示時に親の番組を引く。
- ジャンルは 3 スロット（内容ニブル + ユーザーニブル）。
- テキストは UTF-8 だが NUL 詰めと C0 制御文字が混ざる。ARIB の私用領域文字は `codes.json` の `arib_symbols` で
  `[字]` 等に置き換え（ほか と © は文の一部なので括弧なし）、それ以外の私用領域は捨てる。BS4K の一部外字は
  この表で変換する（U+1F19B〜U+1F1AC）。
- 放送日は 04:00〜翌 04:00。0 時〜4 時はまだ前日の放送日なので、番組表の最初の日は「今 − 4 時間」の日付にする
  （PWA の `tvDays()`、アプリの `GuideStore.broadcastDays`）。暦の日付で始めると、深夜に放送中の番組が
  どの日にも入らない。
- ロゴファイルは毎日深夜に作り直される。受信していない局は 1152 バイトのゼロ。PNG が IHDR の終わり（33 バイト）
  より短いものは、その局だけ飛ばす（パレットを差し込む位置が無い）。

## 端末側の設計メモ

- **番組表の扱い**: 放送種別ごと（`codes` にあるのは地デジ・BS・CS・BS4K・CS4K の 5 つ。アプリは CS4K を除く 4 つを
  取ります）に 8 日分をまとめて取り、端末内 DB に置く。受信していない種別はファイルが 416 で返るので、無いものは
  飛ばすだけでよい。全文検索は NFKC + casefold した列で。アプリはこの列に番組名・番組内容・詳細（出演者は
  詳細にしか無いことが多い）を制御文字で区切って入れ、どの欄で見つかったかで「番組名 → 番組内容 → 詳細」、
  その中は放送順に SQL で並べてから件数で切る（時刻順で切ると、番組名に語を含む数日先の番組が落ちる）。
  空白で区切った語はすべてを含むものだけ。LIKE の `%` と `_` はエスケープする。詳細だけで見つかった番組には
  語の前後を 1 行添える。列の作り方を変えたときはスキーマ番号を上げず、`meta` の印を見てその場で作り直す
  （上げるとキャッシュが消え、宅外で番組表が空になる）。サーバーの検索は番組名と番組内容のままにしてある
  （キーワード自動予約が同じ列を使うので、出演者名で予約が増えないように）。
  更新はアプリ起動時（キャッシュが古いときだけ）と手動、
  それに OS のバックグラウンド更新（iOS の `BGProcessingTask` は不定期で、テレビ宛の送信待ちも同じタスクで送る。
  Android の `WorkManager` は最短 15 分）に頼りすぎない。古いかどうかは**種別ごと**に、レコーダーがその種別に
  最後に答えた時刻（ファイルが無いという答えも含む。`meta` の `epg_checked:<種別>`）で決め、最後の作り直しより前の種別だけを取る。いちばん新しい種別で
  決めると、1 種別だけ失敗しても新しいと見なされて翌晩まで欠けたままになり、いちばん古い種別で決めると、その
  レコーダーに無い種別のせいで接続のたびに全種別を取り直すことになる。取得は 1 種別の失敗（作り直し前の 500、
  読めないファイル）では止めずに次の種別へ進み、失敗した種別には印を付けないので次の接続でもう一度取る。
  無応答だけはそこで止める（次の種別も答えず、ファイル 1 本ごとに長いタイムアウトが掛かる）。どの種別で失敗
  したかは種別ごとに 1 行で出し、終わったら結果にかかわらずキャッシュを読み直す。
  初回の取得は全種別とロゴで時間が掛かるので、チュートリアルは番組表を取り終えるのを待たず、
  レコーダーが応答した時点で閉じる（接続の処理は分けず、応答したことを知らせるだけにする。分けると同時接続の
  ガードが外れて、クライアントが 2 つになる）。番組表は種別を 1 つ保存するたびに画面に出す（最初に取る地デジが、
  アプリが最初に開く種別）。取得中の空の番組表には、取得中であることを出す。
  空の番組表は理由を言い分ける（すべての局を非表示にしている、絞り込んだ局にその日の番組が無い、サンプルデータに
  無い種別や日、番組表に対応していない機種、その種別のファイルが無かった、まだ取得していない）。「更新ボタンで
  取得できます」で済ませると、更新しても埋まらない場合に嘘になる。
- **局の非表示と並び順**: 放送種別ごとに端末に持つ（`channel_prefs`。キャッシュとは別の表なので、スキーマ番号を
  上げても消えない）。レコーダーには送らない。番組表・表形式の列・番組の検索が従い、予約と録画の一覧は従わない。
  リストを局で絞っているときにその局を非表示にしたら、または放送種別を変えたら、絞り込みを外す（残すと空の
  一覧になり、メニューにもその局が出ないので戻し方が無い）。
- **予約の重複**: 一覧の `conflictID` が 0 でない予約は、レコーダーが重複と見ているもの。相手は教えてくれない
  ので、予約の画面には時間帯が重なるほかの予約を「時間が重なる予約」として並べる。`X_GetConflictList` の答えも
  同じ言い方にする。チューナーは複数あるので、時間が重なるだけでは録れない理由にならず、「重複」と呼ぶと言い過ぎになる。
- **送信待ちキュー**: 届かなかった予約は端末に保存し、**レコーダーに接続できたときに毎回**順に
  `X_CreateRecordSchedule` する（アプリを前面に戻したとき、深夜の更新のとき、手動の再接続のとき、ショートカットの
  アクションから呼ばれたとき）。送る先は、送信待ちを溜めたときのレコーダー（端末内 DB に控えた UDN の機体）
  だけ。別のレコーダーに切り替わったら理由を付けて止め、利用者が「もう一度送る」を選ぶまで送らない。画面の
  無い処理は、別のレコーダーが答えたら何も送らずに通知する（下の「答えたレコーダーが誰かで決める」）。捨てるのは
  **番組が終わったとき**で、始まっただけのものは送る（レコーダーは残りを録る）。レコーダーが errorCode 付きの
  SOAP fault で断ったもの（未契約の局の 831 など）は理由を付けて残し、**利用者が「もう一度送る」を選ぶまで
  送らない**（同じ答えが返るだけで、以前は接続のたびと毎晩送り直し、毎朝「受け付けませんでした」と通知して
  いた）。503（ほかの要求の処理中。クライアントが 2 回送り直したあとのもの）や errorCode の無い失敗は要求の
  中身とは関係がないので、何も書かずに残して次の機会に送り直す。作成を送ったあとにレコーダーが黙ったら、その
  1 件は届いている場合もあるので、理由を付けて残し、利用者が予約一覧で確かめて「もう一度送る」を選ぶまで送らない
  （下の「書き込みは送り直さない」。何も書かずに残すと、次の接続や深夜の処理が同じ予約をもう一度作る）。残りは
  そのまま次の機会へ。送る前にはレコーダーの予約一覧を 1 回読み、行と同じ番組の予約がもうあれば、その行は送らずに
  「すでにある」として外す（下）。結果は、深夜の処理ではローカル通知
  （新しく断られたものだけを伝える）、アプリが前面で送ったときは画面上部に 1 行で知らせる（前面では通知が表示
  されない）。結果の文は規則と同じ場所にあり（`PendingQueue.Outcome` の `summary` と `says(naming:)`）、
  画面上部の行、通知、ショートカットのアクションの答えが同じ文を使う。レコーダーだけの家では、文に機器の
  名前は入らない。テレビを登録してある家では、どの機器に送ったかを入れる（「送信待ちだった「…」をレコーダーに
  登録しました」）。入れるかどうかはアプリが決め、機器の呼び名を渡す。
  実装は `app/RecorderKit/Sources/RecorderKit/PendingQueue.swift` の 1 か所だけで、画面と深夜の
  処理が同じ規則を使います。ここにあるのは、送る順番、送らない行の扱い（終わった番組は捨て、理由の付いた
  行は残す）、1 件ごとの結果に応じて行をどうするか（消す、理由を書く、そのまま残す、その回を打ち切る）
  だけです。理由は、送ったときの理由（無いか、同意した文）の上にだけ書き、作成が出ている間に別のレコーダーが答え
  て書いた理由は残します（`GuideStore.setPendingProblem(_:_:ifItIs:)`）。1 件をどう送るかは機器の側にあります
  （`QueueTarget`。`DeviceEndpoint.swift`）。送信待ちは機器に 1 件ずつ送らせ、返ってきた結果（作った、
  すでにあった、理由を付けて断った、見送った、この回はここまで）を読みます。上に書いたレコーダーの送り方（作成を
  1 回送り、無応答ならその回を打ち切り、理由の付いた断りは行に書き、それ以外は見送る）は、作成の要求だけを持つ機
  器（`ReservationTarget`）と同じ作成です（`sentByCreating`）。送る前に読んでおくものがある機器のために、その回で
  最初に送る行の直前に 1 回だけ機器を読む口（`openRound`。端末に残したものも渡す）もあります。レコーダーは
  そこで予約一覧を 1 回読み（送る行があるときだけ）、行と同じ放送の種別・局・番組 ID の予約があれば、その行を
  送らずに「すでにある」として返します（`ByProgram.lists`。テレビの回と同じ照合です）。行が頼んだ毎回録画に
  足りない予約（1 回だけの予約、曜日の少ない毎回録画）と、レコーダーがおまかせ・まる録で自分で入れた予約
  （作成者 1100。番組表を読み直すたびに決め直されます）は、行の代わりにしません。理由の付いた行も、一覧にあれば
  外します。別のレコーダーに切り替わったために止めた行だけは、利用者が送り直すまでいまのレコーダーのものでは
  ないので、見ません。一覧が全部かどうか（上の、1 回 200 件までの一覧の項）も、回が覚えます。一覧の読み込みが無応答なら回は
  そこで止まり、何も送りません。ほかの理由で読めなければ（ほかの要求の処理中、不具合、読めない答え）、何も
  見つけずに回を始め、行はいままでどおり送ります。キャッシュに残した USB HDD も読み、`USBHDD` 宛の行に来たときに
  その回で 1 度だけ USB HDD を待ち、答えなければ行に理由を書きます（上の「録画先の選び方」。`RecorderClient` の回）。
  送信には、送る行を 1 件に絞る口（`only`）と、利用者の同意を渡す口（`consenting`）もあります。同意は、
  行の id と、同意した文の組です。テレビは、録れなくなる予約を名指しした行に使います（下の「テレビに予約を
  入れる、送り直す」）。レコーダーは、作成が無応答だった行を利用者が送り直すときに使い、その行は、回の初めの
  一覧が全部で、その中に無いときだけ送ります（下の「書き込みは送り直さない」）。1 件に絞る口は、どちらの機器も、
  予約を入れるときと送り直すときに使います。
  送信は端末の中で**一度に 1 つだけ**にし、2 つ目は 1 つ目が終わってから送信待ちを
  読み直す（画面と深夜の処理はクライアントも接続も別なので、同時に読むと同じ予約を 2 回作る）。
  送信待ちの各行は、**どの機器宛か**を持つ（`PendingReservation.target`。画面が作るのは、いまはレコーダー宛だけ）。
  レコーダーへの送信は、レコーダー宛の行だけを送る。別の機器宛の行には触らず、別のレコーダーに切り替わったときに
  止めるのもレコーダー宛の行だけ。どの機器宛の行を送るかは、呼ぶ側ではなく送る先の機器の型が言う
  （`QueueTarget.slot`。レコーダーのクライアントは `.recorder`）。レコーダーへの送信は、テレビと同じく、ひとりでに
  送られるレコーダー宛の行（理由が無く、番組の終わっていない行。`PendingQueue.hasSomethingToSend`）が無ければ、
  レコーダーに何も聞かず、進行中の行も出さない（理由の付いた行は利用者を待つので、出すと、その行が残っている間、
  接続のたびに行が点く）。番組の終わった行があれば、何も聞かずに捨てる。テレビ宛の行は、テレビの側が送る
  （下の「テレビ宛の送信待ちをいつ送るか」）。
  宛先の列は、あとから足した（`ALTER TABLE`）。画面と画面の無い処理は同じファイルを
  別々に開くので、列があるかは鍵を取らずに見て、無いときだけ書き込みの鍵を取り、中でもう一度見てから足す。
  送信待ちの予約は番組表（リストと表形式）、検索結果、番組の画面にも「送信待ち」と出し、番組の画面は予約の
  入力をもう一度出さない。端末への保存に失敗したときは予約できたように閉じず、エラーを出す。
  帰宅しただけでは送られない（iOS はネットワークが来たことでアプリを起こさない）。そのためショートカットの
  アクション「送信待ちの予約を送る」を用意し、自宅の Wi-Fi に接続したときのオートメーション（iOS 17 以降は
  確認なしで実行できる）から呼べるようにする。バックグラウンドで動き、送るものがないときはレコーダーに
  何も送らない（帰宅のたびに起こさないため）。送るものがあれば起こして `PendingQueue` で送り、結果を通知する。
- **LAN の判定**: 保存した UDN の `description.xml` が保存ホストで取れるか、駄目なら探索し直す（`services/session.py`
  の `resolve_recorder` と同じ順序）。iOS アプリも、つながったレコーダーの UDN を端末内 DB の `meta`
  （`recorder_udn`）に控えますが、使うのは「答えたのがどのレコーダーか」を見分けるためです（下の「答えた
  レコーダーが誰かで決める」）。移ったレコーダーの探し直しは、起こすために控えている有線 MAC で照合します。
  UDN の末尾 12 桁と同じなので、UDN を控える前のインストールでも移行なしで探せます。
  - 探すのは、保存アドレスがマジックパケットの起動待ちのあとも黙っていたときに、**同じ接続の中で 1 回だけ**です
    （接続の途中でネットワークが変わってやり直したときは、そのやり直しでもう 1 回）。
    UDN の末尾がその MAC の機体が見つかった時点で残りのアドレスは打ち切り、そのアドレスに移って接続します。
    見つからなければ下の「諦めたら諦めたままにする」のとおり諦め、繰り返しません。走査は /24 で数秒、起動待ちの
    30 秒のあとに足されます。
  - 走査するのは、保存アドレスが属する Wi-Fi のサブネットだけです。DHCP が動かすのはそのサブネットの中なので、
    保存アドレスが今の Wi-Fi のサブネットに無いとき（外出先、よその Wi-Fi、VPN 越し）は走査しません。
  - MAC を読んだときのアドレスも控えておきます。利用者が別の機体のアドレスを入れた直後は、MAC はまだ前の機体の
    もので、そのマジックパケットで起きた前の機体を見つけて黙って元に戻ってしまうからです。控えたアドレスが
    保存アドレスと違う間は照合しません（控えが無いときは照合します。以前の版は控えていないためです）。
    別のレコーダーが説明を返し、その UDN の末尾が控えている MAC でなければ、MAC も忘れます（新しい機体の MAC は
    同じ接続の中で読みます）。それまでは前の機体の MAC が残るので、新しいアドレスが黙っている間のマジック
    パケットは前の機体に届きます。
  - ローカルネットワークの許可は、起こす前に保存アドレス（同じサブネット）で確かめています。拒否されていれば
    そこで許可を待つので、走査が確認ダイアログの裏で空振りすることはない、という作りです。確かめ方は、下の
    「ローカルネットワークの許可」にあります。
    バックグラウンドとサンプルデータのモードでは走査しません。
  - 接続できないときの画面（番組表・予約・録画）には、再接続の下に控えめな「レコーダーを探す」を置き、
    チュートリアルの検索に戻れるようにしています。照合できないとき（一度もつながっていない、1 桁違いの
    アドレスを入れた）や、見つからなかったときの逃げ道です。
  - テレビも同じく探し直します（`TVDriver.findElsewhere`、`TVDiscovery.find`）。照合に使うのは、登録のときに
    読んで保存した Wake-on-LAN の MAC で、各アドレスに登録の要らない `getSystemSupportedFunction` を 1 回ずつ
    聞きます（48 アドレスずつ、1 アドレス 1.2 秒、cookie も PIN も付けない）。テレビは起こさないので、探すのは、
    接続の最初の確認が無応答だったときと、保存したテレビではない機器が答えたときです。別のテレビは MAC で、
    テレビではない機器は、登録の要らない最初の確認にテレビの返さない答え（401・403・503 以外の HTTP の状態、
    読めない答え、知らないエラー番号）を返したことで見分けます。ルーターやプリンターのポート 80 の画面など、
    DHCP がアドレスを別の機器に渡したときのふつうの形です。その機器には cookie の付いたものを送らず、接続は
    無応答と同じに扱って、許可の確認のあとに探します。見つかればそのアドレスに移り、MAC を聞いてから接続します。
    見つからなければ、何が答えたかを行に出して諦めます。MAC を保存してあれば、最初の確認への 401（PIN の要求）も
    同じく扱って探します。最初の確認は登録の要らない要求で、テレビが 401 を返すのを見たのは画面を点けて登録を
    求めたときだけ、ルーターやカメラのログインは 401 を返すからです。別のアドレスで見つかればそこに移り、
    401 を返したアドレスで見つかったときと見つからなかったときは、MAC を保存していないときと同じく登録が要る
    ことにして、諦めません。403 では探しません。探すのは接続の 1 回の試みにつき 1 回で、接続の途中で
    ネットワークが変わったときは、その接続が新しいネットワークで試し直すので、ネットワークごとに 1 回ずつ、
    合わせて 2 回まで探します。同じネットワークで
    見つからなかったら、テレビが答えるまで（またはアプリを起動し直すまで）そのネットワークでは探しません
    （ドライバーが覚えます）。待機中に黙るテレビで、起動・復帰・引き下げのたびにサブネット全体に要求を
    送らないためです。探す間は帯に「テレビを探しています」を出します。走査するサブネットと、背景・
    サンプルデータのモードで走査しないことはレコーダーと同じで、操作の前の確認、深夜の処理、ショートカットの
    アクションからは探しません。
  - 操作の前の確認でも、どのテレビが答えるかを聞きます（`TVDriver.check`）。接続したままの間にアドレスが
    別の機器に渡ったり、同じサブネットの別の Wi-Fi に移ったりすると、利用者の操作が cookie を付けてその機器に
    届いてしまうからです。聞くのは接続の最初と同じ `getSystemSupportedFunction` 1 回だけで、以前の
    `getPowerStatus` の代わりです（確認が読んでいたのは答えがあるかどうかだけで、これも登録が要らず、待機中も
    答えます）。**cookie の付いたものは、保存したテレビが MAC でそのテレビだと答えてからしか送りません。**
    別の MAC のテレビが答えたら、操作は行わず、テレビの行に「登録したテレビとは別の機器が応答しました。…」と
    出し、接続していない状態にします。それからは登録の要るものを何も聞かないので、そのテレビには cookie の
    付いたものが届きません。答えはあったので諦めず、次の接続がもう一度聞いて、その先を探します。確認からは
    探しません。無応答でも別のテレビでもない答えは、どの機器が答えたのかを何も言わないので、それを根拠に
    cookie の付いたものは送りません（`DeviceLink.heardInstead`。レコーダーも同じものを読みます）。401・403 は、MAC を保存していない接続と同じく、登録が
    要ることにします（MAC を保存した接続は、401 なら先に探します。確認からは探しません）。
    ほかの断りや不具合（503、40005、HTTP 500 や 404 の画面、読めない答え）は、接続が出すのと同じその答えの文を
    行に出し、別の機器とは言いません。テレビ自身の一時的な不具合を別の機器と言うと、利用者を「テレビを外す」と
    登録のやり直しに向かわせてしまうからです。どちらも諦めず、別の機器とも扱わず、次の操作は最後の応答からの
    時間によらずもう一度確認して、そのテレビだと聞けてから送ります。MAC の分からないテレビ（MAC を保存して
    いないテレビ、MAC を言わないテレビ）は、接続と同じく、保存したテレビとして扱います。
  - この確認は、どの操作の前にもするわけではありません。テレビの最後の応答から 90 秒たたないうちは
    （`LinkRules.dozeAfter`）、接続中で処理中でないときにネットワークが変わったと分かった場合のほかは、
    レコーダーと同じく確認せずに操作を送ります。テレビの処理中にネットワークが変わったときや、同じアドレスと
    ネットマスクを配る別の Wi-Fi に移ったときは、変わったと分かりません。その間にアドレスが別の機器に渡れば、
    その操作は cookie を付けてそこに届きます。この隙間は残しています。閉じるには、すべての操作の前に要求を
    1 回足すか、ネットワークが変わるたびに確認することになり、後者はリンクの規則なので、レコーダーにも
    ネットワークが変わるたびにプローブを送ることになるからです。その間に接続が始まっても、接続が作った新しい
    クライアントには、その接続がどのテレビか聞き終えるまで、確認を済ませた一覧の読み込みも送りません。接続が
    クライアントを作る前に始まった読み込みは、前の接続が確かめたクライアントで送ります。
- **別のアドレスを選んだら、前のレコーダーのことは忘れる**: 利用者がレコーダーを選び直したとき（探して選ぶ、
  アドレスを入力する。`AppModel.adopt`）、今のアドレスと違うアドレスなら、**接続を試す前に**、前のレコーダーが
  言ったことを端末のメモリから消します。機種・ファームウェア・残容量・USB HDD・電源が要るという印
  （`SessionState.forgotTheDevice`）、予約、録画、おまかせ・まる録の一覧、重複の組とそのチェック、
  読んだ番組内容、終わった一括処理の結果、画面に出ていたエラーと送信待ちの結果の行です。一覧の絞り込み
  （ジャンル、視聴状態、予約の種類）も元に戻します。
  接続は試みのたびに、そのときのアドレスで新しいクライアントを作るので、消さないと、前の機体の一覧が、新しい
  アドレスに向いたクライアントの上に残ります。録画一覧は「読み込み済み」のままで読み直されず、そこから削除や保護を
  押すと、前の機体の ID が新しいアドレスに送られていました。新しいアドレスが説明を返さなかったとき（ほかの要求の
  処理中で 503、レコーダーではない機器）は前の機体の説明も残り、前の機体に接続中と見えたまま、要求だけが
  新しいアドレスに行っていました。
  - 同じアドレスを選び直したときは何も消さず、再接続と同じ動きをします。入力を整えたうえで、大文字と小文字を
    区別せずに比べます（`RecorderAddress.same`）。比べるのはアドレスだけです。同じ機体が別のアドレスに移った
    だけのときも、消して読み直します。探して見つけた行は、UDN が同じなら「使用中」と出ますが、選ぶときには
    見ていません。消さないのは、アプリが自分で探し直して移ったとき（上の「LAN の判定」）だけです。
  - 消えるのは一覧だけではありません。重複の組と、利用者が付け外ししたチェック、終わった一括処理の結果、
    絞り込みも消えます。アドレスを打ち間違えて直したときも同じで、重複の検出はやり直しになります（番組内容は
    端末に残っているのでレコーダーには聞き直しませんが、チェックは付け直しです）。別の機体の録画が画面に
    残るよりは軽い、という判断です。
  - 選んだ時点で消すのはメモリの中だけです。端末内のデータベース（番組表、録画の番組内容、送信待ち、
    チャンネルの設定）、MAC、並び順と放送波の選択は、新しいアドレスで何かが説明を返すまで残します。アドレスを
    打ち間違えても、黙っているかレコーダーでない機器が答えるだけなら、端末の中は何も変わりません。説明が
    返ったあとは、答えたのがどのレコーダーかで決めます（下の「答えたレコーダーが誰かで決める」）。サンプル
    データのモードの出入りでも同じものを消しますが、こちらはデータベースごと切り替わります。
  - 送信待ちは利用者のものなので残します。次に説明を返したレコーダーが、送信待ちを溜めたときのレコーダー
    （UDN が同じ）なら、その接続が送ります。別のレコーダーなら理由を付けて止め、利用者が「もう一度送る」を
    選ぶまで送りません（下の「答えたレコーダーが誰かで決める」）。503 だけを返した機器や、レコーダーではない
    機器は、応答はしているので画面は無応答として扱いませんが、どの機体かを言っていないので送りません。この
    状態は、選び直さなくても起きます（接続のときに、レコーダーがほかのアプリの相手をしていて 503 を返した）。
    そこで、予約一覧の引き下げ更新と、送信待ちの「もう一度送る」は、**書き込めるレコーダーでなければ接続し直します**
    （`RecorderDriver.refreshReservations`、`resend`。書き込めるのは、どのレコーダーかを言った接続のクライアントが
    手元にあり、接続済みのとき。`canBeAsked`）。説明が返れば、その接続が送信待ちを送ります。書き込めるなら、
    引き下げ更新は、テレビと同じく、送信待ちを送ってから一覧を 1 回読みます。以前の引き下げ更新は、無応答で
    なければ一覧を読んでから送信待ちを送っていたので、説明を返していない機器にも届いていました。
    予約の登録、変更、削除も、書き込めるレコーダーにだけ送ります。接続の途中（新しいクライアントは、どの機体が
    答えるかをまだ聞いていない）や、接続に 503 で答えた間は、予約は確かめずに端末に残し、変更と削除は送らずに
    「レコーダーに接続していません。…」と言います。503 で答えた接続のあとは、接続済みのまま諦めてもいないので
    「再接続」が出ません。引き下げ更新と「もう一度送る」が接続し直します。
  - 操作の前の確認（下の「操作の前に起こす」）の最中は、選び直しも、サンプルデータの開始・終了も受け付けません。
    確認は始めたときのクライアントで続くので、起きた前の機体が、新しいアドレスの機体として接続されてしまう
    からです。
  - 選び直したときに、前の機体への要求がまだ返っていないことがあります。帯に行を出さない要求（録画の番組内容、
    予約の重複の確認）は、選び直しを止めないからです。あとから届いた無応答やエラーは前の機体のものなので、
    今の機体の無応答としては扱わず、画面にも出しません（要求を出したクライアントが今のものかで見分けます）。
    以前は、選んだばかりの機体が「接続していません」になっていました。接続し直しただけのときも同じです。
    予約一覧の読み込みと予約の手順（予約、変更、削除、送信待ちの送信）は、クライアントではなく、リンクが数える
    「手放した回数」で見分けます（`DeviceLink.generation`）。別の機体が説明を返したとき、選び直したとき、
    キャッシュを引き継げずに手放したときに増え、同じ機体へのつなぎ直し（別のアドレスで見つかったときも）、
    無応答、説明を言わない答えでは増えません。同じ機体につなぎ直すと新しいクライアントができますが、何も
    手放していないからです。操作は始めたときの回数を控え、変わっていれば、新しい機体には何も送らず、
    読んだ一覧も渡さず、帯の下の行も書き換えません（前の機体に届いた変更や削除も、帯の下の行を消しません）。
    予約、変更、削除、送り直しは、結果で「別のレコーダーが応答したため、この操作は行っていません。…」
    と言います（キャッシュを引き継げずに手放したときは、そのとき帯の下の行に出た文）。無応答も新しい機体のもの
    としては扱いません。送ったもの（変更、削除、予約や送り直しの作成）の無応答だけは、届いている場合もあるの
    で、帯の下の行と結果で「送信の途中でレコーダーの応答がなくなりました。…」と言いますが
    （`RecorderDriver.mayHaveArrived`）、誰も諦めません。予約の送信待ちの行はそのときも消し（別のレコーダーが
    答えたときは何も残しません）、送り直した送信待ちの行は止めたまま残します。操作の前の確認（下の「操作の前に
    起こす」）が、その間に黙ったときも同じで、前の機体を起こさず、許可も確かめません。
- **答えたレコーダーが誰かで決める**: アドレスは叩く場所にすぎません。どのレコーダーかは、`description.xml` が
  返した UDN で決めます（`Recognition`: 初めて・同じ・別。大文字と小文字は区別しません）。控えは 2 つです。
  メモリの一覧をどの機体から読んだか（`SessionState.device`。無応答の間も残り、選び直しの `forgotTheDevice` で
  消える）と、端末内 DB がどの機体のものか（`meta` の `recorder_udn`。`GuideStore.owner`）。説明が返るたび
  （`RecorderDriver.attach`）に、一覧を読んだり送信待ちを送ったりする前に、この 2 つと比べます。
  - 同じ UDN なら、どのアドレスで答えても端末のものは何も消しません。番組内容、番組表とその取得の印、残容量の
    通知の印、MAC はそのままで、送信待ちもそのまま送ります。DB には何も書きません（読むだけで分かるので、
    深夜の更新などほかの書き込みを待たされません）。
  - 別の UDN なら、前の機体のものは渡しません。メモリでは、説明が届いたのと同じターンで一覧を消し
    （`forgetWhatTheRecorderSaid`。選び直しのときに消すものから、説明とクライアント、画面に出ていたエラーを
    除いたもの。エラーは、その接続が最後まで進んだときに消えます）、接続済みの
    ままだったときは、読んであった録画とおまかせ・まる録の一覧をその接続の中で読み直します
    （`readAgainWhatWasUp`。画面は「接続済みになった」ことをきっかけに読むので、接続済みのままだと誰も
    読み直さない）。端末内 DB では 1 つのトランザクションで（`GuideStore.claim`）、録画の番組内容、番組表（局・
    番組・ロゴ）と `epg_refreshed:` / `epg_checked:` の印を消し、レコーダー宛の送信待ちの各行に理由を書いて止め、持ち主の
    UDN を書き換えます。`UserDefaults` の残容量の通知の印と最終自動更新の時刻も消します。番組表は空になり、
    同じ接続の `refreshGuideIfStale` が全種別を取り直します（その機体に無い種別は、前の機体の番組を残さず
    空のまま）。MAC は、新しい UDN の末尾がそれでなければ忘れ、同じ接続の中で新しい機体のものを読みます。
  - DB を書き換えられなかったとき（ほかの書き込みが長く続いている、空き容量が無い）は、その機体には接続
    しません。接続すると、前の機体の番組表や番組内容の上で動いてしまうからです。理由を画面に出し、次の接続で
    やり直します。クライアントも手放します（選び直しの直後と同じ、誰にも聞けない状態）。残すと「応答は
    あるが接続していない」機器として扱われ、画面に残っている前の機体の番組表から予約すると、その機体に
    送られていました。手放したあとの予約は送信待ちに入り、持ち主が替わった時点でほかの行と同じく止まります。
  - 止めた送信待ちは、各行に理由を出し、帯に「別のレコーダーに切り替わったため、送信待ちの予約 N 件は送らずに
    残しています」と出します。止まっている行がある間は、送信待ちを送るたびに出します（止めた接続が最後まで
    進まなかったときも次の接続で伝わるように、行から数えます）。「もう一度送る」でいまの機体に送れます。黙って
    別の機体に入れるのも黙って捨てるのも違う、という判断です。以前に別の理由で断られていた行も、同じ理由に
    書き換わります。
  - 操作の前の確認（下の「操作の前に起こす」）でも比べます。プローブに別の機体が答えたら、その操作は行わず
    （画面には「別のレコーダーが応答したため、この操作は行っていません」）、一覧を消して、新しい機体は別の
    接続で取り込みます。起動待ちの末に別の機体につながったときも同じです。予約の登録も、このときは送信待ちに
    入れません（入れると、前の機体のための予約として止まるか、新しい機体に送られます）。実行中の一括処理や
    重複の検出は次の 1 件に進む前に止め、接続はそれが終わってから始めます。前面で動いている一括処理も、
    確認が出ている間は次の 1 件を始めずに結果を待ちます（`readyForNextStep`）。確認の問い合わせは実行中の
    1 件の後ろに並ぶので、待たないと、結果が届く前に次の 1 件が別の機体に届きます。すでに送った 1 件は
    止められません。
  - メモリの一覧を消したことは、画面にも伝えます（`AppModel.timesForgotten`）。開いたままの録画や予約の画面、
    削除の確認に選んだ行は前の機体のものなので、閉じます。閉じないと、空になった一覧の上に残った画面の
    ボタンが、前の機体の ID を新しい機体に送ります。機体の行を持つ画面（録画 1 件、番組ごとの録画、予約
    1 件）は、どこから開かれたかに依らないように、自分で閉じます。番組の画面は放送のものなので残しますが、
    削除の確認に選んだ予約と、前の機体が答えた「時間が重なる予約」は捨て、次の機体につながったら聞き直します。
    検索の画面は、予約と録画の一覧を「接続済みになった」ときにも読みます（一覧を消された画面が前面に
    あると、ほかに読み直すきっかけがありません）。
    一覧を消す前に読み始めていたレコーダーの予約一覧が、消したあとに返ってきても、画面には置きません。新しい
    機体の一覧は、その機体の接続が読みます。予約一覧を読む入口（画面の読み込みと引き下げ、接続、送信待ちの送信と
    「もう一度送る」、予約の登録、変更、削除）は、始めたときの `timesForgotten` を控え、読んだ一覧はその数が
    変わっていないときだけ持ちます（`AppModel.keepReservations`）。削除した行を画面の一覧から外すのも同じです。
    テレビのホストも同じ規則で、一覧はそれを読んだホストと一緒に手放します。変更と削除は、持つかどうかに
    依らず、いま読み直した一覧から行を探し、読めなかったときは何も送らず、読めなかったわけを言います（テレビと
    同じです。以前は画面の一覧から行を探して送っていました）。
  - 利用者が選んでいないのに別の機体が答えたとき（一覧を持ったままの接続、操作の前の確認）は、帯にも出します
    （`AppModel.anotherTookOver`。「別のレコーダーが応答したため、一覧を読み直しました。操作の途中だった場合は、
    確かめてからやり直してください」）。操作を行わなかったことはエラーの行でも伝えますが、その行は続く接続で
    消え、操作を始めた画面が上のとおり閉じると、その中のアラートも一緒に閉じます。帯はどの画面でも読めるので、
    利用者が閉じるか、アプリを離れるか、レコーダーを選び直すまで残します。出すのは接続している間だけです
    （新しい機体がすぐ黙ったときは、読み直していないので、再接続の帯を先に出します）。
  - 画面の無い処理（深夜の更新、ショートカットのアクション）は、端末内 DB の持ち主と違う機体が答えたら、何も
    送らず、取らず、消しません（`RecorderDriver.isTheOneKnown`）。持ち主を読めなかったときも同じです。送るものが
    待っていたときだけ、別のレコーダーが応答したので送っていないと通知します。取り込むのは画面のある接続
    だけです。
  - UDN を返さない機器は見分けようがないので、控えている機体と同じとみなします（答えるたびに忘れる方が害が
    大きい）。
  - 持ち主の UDN を控える前のキャッシュ（以前の版）は、誰のものかを言いません。推測はせず、最初に説明を
    返した機体を持ち主として控え、中身はそのままにします。起こすために控えている MAC を UDN の末尾と比べれば
    見分けられる場合もありますが、末尾が MAC だと確かめたのは 1 機種だけで、MAC は利用者が手で入れることも
    あります。外れると、レコーダーが 1 台しかない家で、更新した日に番組内容が消え、送信待ちが止まります。
    ただし、メモリの一覧を別の機体から読んでいたと分かっているとき（`SessionState.device`）は、持ち主が
    書かれていなくても別の機体のものとして引き継ぎます（`claim` の `knownToBeAnother`。最初の機体の UDN を
    書き込めないまま、次に別の機体が答えた場合です）。
  - サンプルデータのモードでは比べません（キャッシュが別で、終了時に消える）。実機のキャッシュの持ち主、
    番組内容、通知の印は、サンプルの出入りで変わりません。
  - 残っていること。同じアドレスで別の機体が答えたら、利用者が選んでいなくても取り込みます（機体の入れ替え、
    DHCP の割り当て直しのほか、よその家の同じアドレスのレコーダーでも同じです）。2 台を行き来すると、その
    たびに番組内容と番組表を消して取り直し、送信待ちは止まったままになります（どの機体のための行かは控えて
    いません）。同じ機体がディスクの初期化などで録画の ID を振り直すと、古い番組内容が残ります。新しい
    アドレスを選んでから最初の説明が返るまでに溜めた送信待ちも、新しい機体のための予約なのに止まります。
    同じアドレスの機体が入れ替わったあと、画面の無い処理は、アプリが開かれるまで送信待ちを送りません（通知で
    知らせます）。深夜の更新の最中に画面で別の機体を取り込むと、深夜の更新が前の機体の番組表を新しい
    キャッシュに書くことがあります（次の夜に直ります）。接続の途中、説明が返るまでの一瞬に確定した操作は、
    照合の前に送られます。確認や接続の問い合わせに、機器が説明ではなく 503 などで答えたときは、誰が答えたか
    分からないまま、それまでの機体として扱います（以前からの動作で、直後の操作は照合なしで送られます）。
    以前の版で 2 台を使い分けていた端末は、更新した時点のキャッシュに別の機体の番組内容が混ざっていても、
    最初に答えた機体のものになります（次に機体を切り替えたときに消えます）。
- **諦めたら諦めたままにする**: レコーダーが沈黙したときの再試行は、**この端末が持っているアドレスが変わったとき**
  （別の Wi-Fi、VPN の上がり下がり、セルラーへの切り替え）と、利用者が明示的に頼んだとき（再接続・レコーダーを
  探す・引き下げ更新）だけにします。同じネットワークでは答えは同じで、1 回の試行にタイムアウト（マジックパケット →
  5 秒の確認 → 無応答なら最大 30 秒の起動待ち。待つ間は、2 秒で打ち切る確認を 1 秒おいて繰り返す）が掛かるうえ、
  クライアントは要求を直列化するので、画面ごとに読み込みを始めると数分間スピナーが回り続けます。
  `NWPathMonitor` はもっと細かい理由でも発火するので、
  判断はインターフェースのアドレス一覧で行います。セルラー（`pdp_ip`）のアドレスは一覧に入れません。キャリアは
  自宅の Wi-Fi にいる間も勝手に付け替えるので、数えるとそのたびに 35 秒の起動待ちが走ります。Wi-Fi が
  切れれば Wi-Fi の側が変わるので、セルラーへの切り替えはそれで分かります。接続していないことは画面に出し、
  再試行の入口を添えます。諦めるのは無応答のときだけで、503 や SOAP の Fault のように答えがあったときは
  諦めません（レコーダーはそこにいて、何が悪いかはもう画面に出ています）。接続の途中でネットワークが変わった
  とき（家に着いて Wi-Fi につながった、VPN が上がった）は、接続の最後にアドレス一覧を比べ、変わっていれば
  **同じ接続の中で 1 回だけ**やり直します。接続中は変化の通知を受けても何もしないので、やり直さないと、来た
  ばかりのネットワークで諦めたままになります。
  変化の通知は、アドレスが揃う前に来ます。IPv6 もあるネットワークでは IPv4 のアドレスが付く前に経路が
  使えるようになって通知が来て、アドレスが付いたときには何も来ません。通知の瞬間だけ比べると変化が見えず、
  Wi-Fi に戻っても諦めたままでした。そこで通知のあと 30 秒ほど何度か見直し、試行を 1 回始めたらやめます。
  処理中に来た通知も捨てず、「前回の試行のあとに別のネットワークにいた」ことを通知の時点で覚えておきます。
  要求の途中で Wi-Fi が切れて戻ると、前後のアドレスは同じでも、無応答は家の外で受けたものだからです。
  無応答で諦めるときに、試したネットワークを終わった時点のものに書き換えないのも同じ理由です。
  アプリに戻ったときの再接続は、実際にバックグラウンドに回ったあとだけにします。コントロールセンター、通知センター、アプリスイッチャー、
  システムのアラートでもアプリは非アクティブになりますが、どこにも行っていないので数えません。
  接続していて、最後の応答から 1 分以内なら、戻っても接続し直しません（少し別のアプリを見て戻るたびにマジック
  パケットを送らないため）。処理の途中や、操作の前の確認の最中は、2 つめのクライアントを作らないよう、接続は
  せずにネットワークを見直すだけにします（`LinkRules.onReturn`）。
- **表示するだけの値で接続の成否を決めない**: 接続できたかどうかは `description.xml` だけで決めます。
  続けて読むファームウェア（`X_GetFirmwareVersion`）、MAC（`X_GetPrivateIp`）、残容量、USB HDD
  （`X_GetMediaInfo(USBHDD)`）は、BDZ-FBT4100 は答えますがシリーズのほかの機種が同じように答えるとは限りません。
  断られたり形の違う答えが返ったりしたら値を「不明」にして接続を続け（設定の行を出さない）、無応答のときだけ
  接続の失敗にします（`RecorderError.silenceOnly`）。以前はこれで接続全体が失敗し、レコーダーが答えているのに
  エラーが出て、送信待ちも予約一覧も番組表も取りませんでした。
  残容量は、数値が 2 つとも読めなければ 0 とせずエラーにします（0 と読むと「残り 0.0 GB」と出て、容量不足の
  通知まで出ていました）。合計が 0 のときも不明として扱い、通知は出しません。削除のあとに読み直す残容量が
  読めなくても、削除は成功として扱います。
  接続済みになるのは `description.xml` が読めた時点ですが、それまでの無応答の印は、続き（ファームウェア・MAC・
  残容量）を読み終えるまで残します。そこで、画面が一覧を読み込むきっかけは「接続済みで、無応答の印も無い」に
  します。接続済みだけをきっかけにすると、起こした直後に読みに行って空振りし、そのあと読み直すきっかけが
  ありません（起動待ちの間に録画の画面を開いていると、起きたあとも一覧が空のままでした）。予約の画面も同じ
  きっかけにしています。予約一覧は接続そのものも読むので空にはなりませんが、操作の前の確認で起こしたあとは、
  送信待ちを送ったときと、操作そのものが読むとき（予約の変更・削除）を除いて、誰も読み直さず、眠る前の一覧が
  出たままでした。
- **使っている最中に眠る**: レコーダーは何もしないと 15 分ほどで LAN から消えるので、アプリを開いたままでも
  眠ります。そのままにすると、番組を開けば重複の確認で 30 秒、予約で 30 秒待たされ、家にいるのに送信待ちに
  なります。
  - **無応答は 1 か所で受ける。** どの要求（一覧の読み込み、重複の確認、予約の作成・変更・削除、録画の操作、
    一括処理、重複の検出、送信待ちの送信）でも、無応答を受けたら接続に失敗したときと同じ状態（未接続・諦めた）
    にします。そうしないと、アプリはつながっているつもりのまま画面ごとに同じタイムアウトを待ち、再接続の入口も
    出ません。一括処理と重複の検出は最初の無応答で止めます。
  - **書き込みは送り直さない。** 無応答でも、要求はレコーダーに届いていることがあります。削除と変更は送り直さず、
    届いている場合もあると言います。予約は、テレビと同じく先に端末の送信待ちに書き、その 1 行を送信待ちに
    送らせるので（下の「レコーダーの予約の手順」）、作成のあとの無応答は、送信待ちを送っている途中の無応答と
    同じに扱います。そのとき送っていた 1 件には、「予約の登録中にレコーダーの応答がなくなりました。届いている
    場合もあるため、自動では送り直しません。予約一覧で確かめ、届いていなければ「もう一度送る」を選んでください。」
    という理由を書いて残し（`RecorderDriver.heldAfterSilence`。帯の下の行にも同じ文を出します）、次の接続も、
    引き下げ更新も、深夜の処理もショートカットのアクションも送りません。何も書かずに残すと、それらが同じ予約を
    もう一度作ります。利用者が「もう一度送る」を選んだときだけ、その回の初めに読んだ一覧が全部で、その中に
    無いと分かったときに送ります。一覧にあれば「すでにある」として外し、200 件あった、ほかにもあると言われた、
    読めなかった、のどれかなら送らず、理由も残して、どちらだったかを言います（`notKnownThere`、
    `notKnownThereUnread`）。レコーダーの一覧は 1 回で 200 件までなので、テレビのように、次の回が一覧で探して
    から自分で送ることはしません。残りの行は、何も書かずに次の機会に送ります。何も送らないうちに分かった
    無応答（回の初めの一覧、USB HDD の待ち）では、理由の無い行は理由なしのまま残り、ひとりでに送られます
    （利用者が送り直した、作成が無応答だった行は、理由を残したまま、接続していないと答えます）。
    この理由の文は端末の行に残り、1 字ずつ比べて読みます。言い方を変えるときは、前の版が書いた文も読めるように
    残します（`heldAfterSilence(matches:)`）。それより前の版が理由を書かずに残した行は、前のとおり、ひとりでに
    送られます（いまは回が一覧で探してから送ります）。別のレコーダーが答えたあとの作成の無応答は、誰も諦めず、
    行には切り替わったときに書いた理由が残ります。送信待ちをまとめて送る回では、何も言いません。予約と
    「もう一度送る」の 1 行の回では、その 1 件が前の機体に届いている場合もあるので、変更や削除の無応答と同じに、
    行と結果で `mayHaveArrived` を言います（予約の行は、何も残さない決まりで消します）。
  - **操作の前に起こす。** クライアントは最後に応答を受けた時刻を持ちます（SOAP の Fault も応答に数えます）。
    利用者の操作の前に 90 秒以上空いていたら、**今のクライアントのまま**マジックパケットと 5 秒のプローブを
    送り、黙っていれば接続時と同じ起動待ちに入ります。起きていればミリ秒で終わります。ここで接続し直すと
    クライアントが 2 つになり、2 本のキューがレコーダーに同時に話しかけて 503 になるので使いません。接続中に
    端末のネットワークが変わったときも、最後の応答はもう当てにならないので、同じ確認をします。
    確認に、どの機体かを言わない答え（ほかの要求の処理中の 503 をクライアントが 2 回送り直したあと、不具合、
    読めない答え）が返ったときは、テレビと同じく、その答えをリンクに覚えます（`DeviceLink.heardInstead`）。
    それを根拠に、予約の登録、変更、削除、送信待ちの送信と送り直しは何も書き込まず（予約は端末に残します）、
    予約一覧の読み込みもその答えで失敗して、帯の下の行にその答えの文を出します。次の操作は、最後の応答からの
    時間によらずもう一度確かめ、レコーダーが説明を返せば送ります。確認そのものは行に書きません。時間の重なる
    予約の問い合わせ（テレビには無い要求）は、これを読まずに続け、行にも触らないためです。録画とおまかせ・
    まる録の操作は、まだこれを読みません。
- **一括処理**: 削除・保護はキューで 1 件ずつ、進捗と「中止」を出す（中止は次の 1 件から止める）。アプリが
  バックグラウンドに回ると OS がまもなく止めるので、その旨（離れると一時停止し、戻ると再開する）を表示する。
  止められた途中の要求は失敗として返り、削除が届いたかどうか分からないまま処理が止まるので、処理中の 1 件だけは
  バックグラウンドタスク（iOS の `beginBackgroundTask`）で終わらせ、次の 1 件の前で待ちます。前面に戻ったら、
  離れていた間に眠ったかもしれないレコーダーを確かめてから続けます。処理中は接続し直しません（クライアントが
  2 つになり、2 本目への 503 を「レコーダーではない」と読んで諦めていた）。
- **重複の削除**: チェックを付けたものが消え、チェックの無いものが残る。「残す」の札は提案した 1 本ではなく
  チェックの無い行に付け、全部にチェックが付いた組があれば、その組の名前を出して削除しない。自動で
  チェックを付けるのは番組内容まで一致した組（`high`）だけ。毎回同じ説明文を載せる番組（毎朝の短い番組、
  ミニアニメ）は別の回でも説明文が一致するので、説明文が 20 字未満（`summary_key` で数える）か、番組表の
  キャッシュに同じタイトル・同じ説明文が別々の放送日（4 時区切り）に 2 回以上あれば `boilerplate` とし、
  チェックを付けない（`fixed_blurbs`）。同じ日の 2 回は数えない。1 週間以内の同じ回の再放送も定型文と
  見なされるが、チェックが付かない側に倒れるだけなので許す。番組表は重複の検出のたびに読み直す。
  組を作り直したとき（1 件ずつの削除・保護、一括処理、一覧の再読み込みのあと）は、前と同じ録画でできていて
  確度も同じ組だけ利用者のチェックをそのまま残し、処理中はチェックを変えさせない。番組内容は**読めたものだけ**を
  保存する（空の本文も答えのうち）。820 はレコーダーから消えたものなので一覧から外し、それ以外の失敗は保存せず、
  組にも入れない。`port/titles.json` のベクタは要約の無いものを空として扱う（サーバーと同じ）ので、この絞り込みは
  その手前で行う（RecorderKit では `Duplicates.readSets`。削除を持ちかける画面は `Duplicates.sets` を直接呼ばず、
  これを使う）。一括削除で 820 が返った録画は「すでに削除されています」として飛ばし、一覧からも外す
  （`ItemOutcome.gone`。理由の文言の比較で見分けない）。サーバーの `services/titles.py` は今も失敗を空として保存します。iOS アプリは、以前の版が
  失敗を空として保存した行を一度だけ消します（`meta` の `blank_summaries_cleared`）。
- **iOS の権限**: LAN への平文 HTTP は `NSAppTransportSecurity` の `NSAllowsLocalNetworking` で許可する。LAN
  アクセスの説明文 `NSLocalNetworkUsageDescription` も必須。SSDP のマルチキャスト送信には
  `com.apple.developer.networking.multicast` エンタイトルメントが要り、Apple への申請が必要。**TCP スキャンだけなら
  不要**なので、まずはスキャンで作る。
- **ローカルネットワークの許可**: iOS は、アプリが初めて LAN に触れたときに利用者へ確認を出します。確認の裏で走査す
  ると空振りし、「見つかりません」と出て、許可したあとにもう一度押させることになります（実機で起きたことです）。走査
  は許可を待たず、押すとすぐに 1 回走査します。その要求の大半が確認の裏で拒否されていたら、結果を言わずに許可の案内
  を出し、拒否されたアドレスに 1 秒ごとに尋ね直して、外へ出たら走査し直します（下の「走査は待たない」と「拒否された
  走査」）。許可の待ち（`LocalNetwork.waitForAccess`）は、今は接続側の見張りだけが使います。どれも Apple のテックノ
  ート TN3179 "Understanding local network privacy" に沿っています（2026-10-06 に読んだ版）。システムが何をするかを
  述べた文には、出典を添えるか、1 台の実機で 2026-10-06 に見たと書くか、まだ見ていないと書きます。フォーラムの投稿は
  引いていません。
  - **Apple の文書が言っていること。**
    - 許可の状態を返す API はありません。"There's no general API that returns whether the current process has
      local network access (FB8711182)." 確認のボタンが押されたことを知らせるイベントも、テックノートは挙げて
      いません。挙げているのは、待っている接続をシステムがやり直すこと（下）です。
    - 確認が出ている間の操作は、答えを待たずに拒否されることがあります。"If the system presents a local network
      alert in response to one of your local network operations, it may deny the operation immediately, before the
      user has responded to the alert. To handle this smoothly, use an API that supports waiting for connectivity,
      like `Network` framework [...] or URL Loading System with `waitsForConnectivity` enabled. If you can't use one
      of these preferred APIs, add appropriate retry logic."
    - 許可がないことは、接続の状態で分かります。"If your goal is to make a TCP connection to a local network
      address, manage that connection with NWConnection. If your program doesn't have local network access, the
      connection enters the NWConnection.State.waiting(_:) state and the current path lists an unsatisfied
      reason of NWPath.UnsatisfiedReason.localNetworkDenied."
    - 許可されたことも、同じ接続で分かります。"If the user subsequently changes the Local Network privilege to
      grant your program local network access, the system automatically retries the connection."
    - 確認が出ている間の接続について述べた文は、WWDC20 のセッション 10110 "Support local network privacy in your
      app" の 1 文だけです（ページの書き起こしで読みました）。"Local connections that use NWConnection will stay
      in the waiting state until your app gets permission." その間の接続の経路が何であるか、TCP のハンドシェイク
      の時計が進むのかは、読んだどの文書にも書かれていません。
    - 接続の状態について、SDK のヘッダー `Network/connection.h`（iOS 27.0 の SDK）は、`waiting` を "The
      connection is waiting for a usable network before re-attempting"、`failed` を "The connection has
      irrecoverably closed or failed" と書き、"Connections in the waiting state will normally re-attempt on
      network changes" とも書いています。経路が `unsatisfied` の理由については、同じ SDK の `Network/path.h` に
      "In many cases, the path may be unsatisfied with no reason available." とあり、そのとき理由は
      `notAvailable` です。待ちが読む理由の方は、同じヘッダーに "The user has disabled local network access"
      と定義されています（`nw_path_unsatisfied_reason_local_network_denied`）。書かれているとおりに読めば、利
      用者が「許可しない」と答えた（または設定でオフにした）あとの状態です。確認が出ていて答えがまだの間に、経
      路が何を言うのかは、この定義からは分からず、実機でもまだ見ていません。
    - シミュレータでは試せません。"The simulator doesn't support local network privacy. Test your local network
      privacy behavior on a real device."
    - 許可がなくても通る宛先があります。テックノートの "Local network operations" の節は、例外として "If your
      device's DNS server is on a local network, traffic to it doesn't require local network access." と "If your
      device uses a network proxy and that proxy is on a local network, traffic to it doesn't require local network
      access." を挙げています。ルーターが自分を DNS サーバーとして配る家では、ルーターがこの宛先にあたります。
  - **アプリが間違えていたこと。** 0.3 で入れた待ちも `NWConnection` を使っていましたが、経路を**最初に読めた時
    点**で答えにしていました。接続は、何も試さないうちに最初の経路を渡されます（Mac のループバックで見ると、状態
    がまだ `setup` のうちに `satisfied` が届きます）。Wi-Fi につながった iPhone でも、許可の有無にかかわらずそこ
    で `satisfied` が届き、待ちはそれを「許可あり」と読んで終わったと考えています。ただしこれは、ループバックで
    見たことと実機での結果からの推測で、実機で経路を見たわけではありません。どちらにしても、走査は確認の裏で走
    り、要求はすぐに拒否されて、確認がまだ出ている間に「レコーダーが見つかりませんでした」と出ていました（実機
    で、確認の裏にこの文が出ているところを確認しています。全アドレスを回り終えるより前です）。そのあとで許可して
    も、何も走りません。
    - 同じ結果になる読み方がもう 1 つあります。古い待ちが経路を許可以外の理由で `unsatisfied` と読み、「許可と関
      係なく経路がない」と答えた場合です。走査はそのとき Wi-Fi が無いときにしか止まらなかったので、やはり確認の
      裏で走りました。どちらだったのかは、その版が実機に残したログを読むまで分かりません。
    - テックノートのしるしは「`waiting` の状態で、理由が `localNetworkDenied`」です。経路が `satisfied` であるこ
      とは、許可のしるしではありません。
    - そのあとに足した手当て（誰も見つからなかった結果を 1 秒持つ。押してからアプリが前面を外れて戻っていれば 1
      回やり直す）は、文書ではなく推測の上に作ったもので、実機では働きませんでした。取り除いています。
  - **実機のログが示したこと（2026-10-06、1 台の iPhone）。** アプリを入れ直して最初に「レコーダーを探す」を押したと

    のアドレスは、確認なしで通る宛先（DNS サーバーやプロキシ）ではありません。
    - `ready`: つながった。届きます。
    - `waiting` か `failed` で、理由が `localNetworkDenied`: 許可がありません。画面にそう出して、**その接続のま
      ま**待ちます。許可されるとシステムがその接続をやり直す（テックノート）ので、次に決まった状態が答えになりま
      す。待つ時間に上限はありません（確認を読むのに何分かけても、設定アプリへ行って戻っても構いません）。待って
      いる接続は何も送りません。以前のように数秒ごとに張り直すことはしません。
    - `waiting` か `failed` で、経路が `satisfied`: 相手が接続を断ったか、ハンドシェイクが時間切れになったかです（ポ
      ート 9 を断る機器なら一瞬、黙る機器なら 2 秒で）。断られたのは LAN からの答えなので、届いています。時間切れの
      方は、誰もいないアドレスと見分けがつかないので、届いたと**みなして**います。確認の裏でシステムが接続を止めてお
      いて時間切れにすることがあるのかは、まだ誰も見ていません（下の「実機でしか分からないこと」）。
    - `waiting` か `failed` で、経路が別の理由で `unsatisfied`: 許可とは関係なく経路がありません（Wi-Fi が切れた、な
      ど）。待ちを終え、見張りはリンクに、許可は来なかったと伝えます。
    - `setup` と `preparing`: まだ何も分かりません。経路は読みません（以前はここで読んでいました）。
    - ただし、接続を張ってから 4 秒（ハンドシェイクの 2 秒に 2 秒を足したもの。
      `LocalNetwork.secondsToComeToSomething`）たっても、上のどれにも 1 度もならなければ、その接続について 1 度だけ
      「許可が邪魔をしている」と知らせ（`blocked`）、ログに 1 行書きます。待ちは終わらず、同じ接続を見続けるので、そ
      のあと接続が何になったかが答えです。許可が邪魔をしていると分かっているわけではありません。確認が出ている間の接
      続がどうなるかは読んだどの文書にも書かれておらず、そうして止められた接続を見た人もいません。この知らせは、走査
      がこの待ちを使っていた頃に、画面が「検索中 0 / 253」のまま止まらないように書いたものです。今の使い手の見張りは
      `blocked` に何もさせないので、残るのはログの行です。
    - 誰もいないアドレスは黙るだけなので、ハンドシェイクに 2 秒の上限を付けます
      （`NWProtocolTCP.Options.connectionTimeout`。"The number of seconds that TCP waits before timing out its
      handshake"）。付けないと、接続は `preparing` のまま進みません（ループバックの誰もいないアドレス
      `127.0.0.2` で、6 秒待っても変わりませんでした）。上限を付けると 2 秒で `waiting`（posix 60）になることを
      同じアドレスで確認し、テストにしています。許可済みの利用者にとっての待ちは、相手が断るまでの一瞬か、長くて
      も 2 秒ほど（Mac で測った値）です。
    - 待ちの接続はモバイル通信を使いません（`NWParameters.prohibitedInterfaceTypes` に `.cellular`。"A list of
      interface types that connections, listeners, and browsers will not use"）。使えるままだと、Wi-Fi が切れたとき
      に機器のアドレスをモバイル通信で試しかねません。そこにはローカルネットワークがなく（テックノートの "Such
      interfaces include Wi-Fi and Ethernet, but not cellular (WWAN) or VPN"）、時間切れを「届いた」と読んでしまいま
      す。使えなくしておけば経路がなくなり、待ちは「許可と関係なく経路がない」と答える、と考えています。どちらも実機
      では見ていません。
    - `failed` になった接続は、システムがやり直しません（`connection.h` の "irrecoverably closed or failed"）。
      許可がないまま `failed` になったときだけ、1 秒おいて張り直します。テックノートが待てない API に勧める
      "appropriate retry logic" にならった、アプリ自身の張り直しです。許可がないために接続が `failed` になると書
      いた文書はありません。張り直しは合わせて 120 本まで（約 2 分）で、それでも許可がなければ、待ちは「塞がった
      まま諦めた」と答えて終わります。待っているだけの接続は、どれだけ長く待っても 1 本です。
    - 待ちの答えは 3 つです（`LocalNetwork.Access`）。届く。許可とは別の理由で経路がない（待ちが中止されたときも
      これ）。塞がったまま諦めた。

    られた**接続も「接続性を待っている」ものとして扱いました。タスクのデリゲートに
    `urlSession(_:taskIsWaitingForConnectivity:)` が届き、要求は終わりません（待たないセッションなら -1004 です
    ぐ終わります）。待っている間の時間切れについては、Command Line Tools の macOS 15.4 と 26.5 の SDK の
    `NSURLSession.h` に "When waiting for connectivity, the timeoutIntervalForRequest property does not apply,
    but the timeoutIntervalForResource property does." とあります（iOS 27.0 の SDK のヘッダーと Web のリファレン
    スにはこの文はありません）。ポート 9 を断るルーターでは、許可済みの利用者でも待ちが終わらず、届いた通知が許
    可のせいなのか断られたせいなのかも区別できません。走査の要求そのものをこのセッションに通すこともしません。断
    るアドレスのたびに待ってしまうからです。
    - 見たのは 2026-10-06、macOS 26.6 の Mac のループバック（ポート 9 では誰も待ち受けていない）です。以前はこれ
      をテストにしていましたが、アプリのコードではなく macOS のふるまいを固定の 0.5 秒で確かめるもので、アーカイ
      ブ前のテスト（`ci_scripts/ci_pre_xcodebuild.sh`）をアプリと関係のない理由で止めかねないので外しました。終
      わらないことは、次の 5 行を `swift ファイル名` で動かすと、もう一度見られます（ループバックだけを使い、外
      には何も出ません）。

      let t = URLSession(configuration: c).dataTask(with: URL(string: "http://127.0.0.1:9/")!) { print($2 ?? "応答") }
      t.resume(); RunLoop.main.run(until: Date(timeIntervalSinceNow: 8))
      print(t.state == .running ? "8 秒たっても終わっていない" : "終わった")

  - **レコーダーとテレビを一度に探す。** ボタンは 1 つ（「レコーダーとテレビを探す」。チュートリアルと設定）で、
    各アドレスに 2 つのことを同時に尋ねます（`DeviceSearch.scan`）。レコーダーの `GET /description.xml`（64220 番）
    と、テレビの `POST /sony/system` の `getInterfaceInformation` 1.0（80 番。登録が要らず、cookie も PIN も付けず、
    待機中のテレビも画面をそのままに答えた要求）です。テレビかどうかは `productCategory` が `tv` かで決めます
    （`TVInterface.isTelevision`）。誰もいないアドレスではどちらも 1.2 秒の時間切れになるので、順に尋ねると走査は倍
    かかります。同時に尋ねれば、1 アドレスは遅い方の時間で済み、走査はレコーダーだけのときとほぼ同じです。見つかっ
    たものは、その要求が答えた時点で一覧に出ます（アドレスのもう 1 つの要求を待ちません）。レコーダーだけの家が新
    たに送るのは、走査ごとに各アドレスへ 80 番の POST（約 80 バイト）が 1 件ずつで、自分のレコーダーの 80 番にも
    届きます。BDZ の 80 番に尋ねたことはこれまでなく、何を返すか、ネットワーク待機のレコーダーがそのままでいるか
    は、実機で読みます。ルーターやプリンター、NAS の 80 番の画面は答えて、何でもないと読まれます。走査のセッション
    は、テレビへの要求がみな通るもの（`URLSessionTransport.withoutCookies`）で、cookie を持たずリダイレクトに従いま
    せん。3xx も答えのひとつで、走査が選んでいないアドレスやポートには何も送りません。
    - 一覧はレコーダー（「見つかったレコーダー」）とテレビ（「見つかったテレビ」）に分けます。レコーダーは今までど
      おり選び（走査は止まり、チュートリアルはそのレコーダーが答えたところで閉じます）、テレビは、まだ保存していな
      い間だけ押せます。押すと登録のシートが開いて、そのまま「テレビに接続」に進み（点いていれば画面に番号が出ま
      す）、走査は裏で続きます。チュートリアルは閉じず、テレビを保存したあとはボタンが「閉じる」になります。テレビ
      を保存してあると、見つかったテレビは並ぶだけで押せず、保存したものに「使用中」が付き、別のテレビは「テレビを
      外す」のあとで足すと下に書きます。レコーダーを選んでも、見つかったテレビは一覧に残ります（チュートリアルで見
      つけたテレビを、閉じたあと設定から登録できるように）。設定の「テレビ」欄は、テレビが無いとき「アドレスを入力し
      て追加」だけを出します（走査で見つからなかったときの入口）。
    - サンプルデータの表示中は、架空の 2 つのアドレスだけに 2 つのポートで尋ね、答えるのは、レコーダーのポートの架空の
      レコーダーと、ポート 80 の架空のテレビだけです（`DemoDevices`）。Wi-Fi の一覧も走査のセッションもテレビへの
      口も使わないので、LAN には何も出ず、ローカルネットワークの確認も出ません。架空のレコーダーは「使用中」で、選ん
      でもサンプルは終わりません。架空のテレビは押せば登録に進みます（下の「サンプルデータのモード」）。実際の機器は、
      サンプルを終えてから探します。
  - **走査は待たない。** 押すとすぐ、そのときの Wi-Fi のアドレスを 1 回だけ回り、見つかったものをすぐに言います
    （`AppModel.scanForDevices`）。その前には何も尋ねません。許可の待ちも、決まったアドレスへの確かめもしません。
    走査の要求そのものが確かめで、待てない要求にテックノートが勧めるとおりに読みます（"add appropriate retry
    logic"）。走査の要求は待てる API にできません（上の「`URLSession` の `waitsForConnectivity` は使いません」）。
    Wi-Fi が無ければ「Wi-Fi に接続されていません」と言い、誰にも尋ねません。許可済みの利用者には、これまでの待ちのハ
    ンドシェイク（断られるまでの一瞬か、黙るアドレスで 2 秒ほど）なしに走査が始まります。チュートリアルを閉じる、レ
    コーダーを選ぶ、サンプルデータに入る（どれも `stopScanning`）で、どこにいても終わります。テレビを押しても終わり
    ません。
  - **拒否された走査。** 走査の要求の大半がシステムに拒否されたら、結果を言いません
    （`ScanTally.Counts.mostTurnedAway`）。システムに拒否された要求とは、システムのコードで失敗し、そのコードが外へ
    出た要求の返り方のどれでもないものです。返り方は、答え（HTTP の状態は問わない）、時間切れ（-1001）、取り消し
    （-999）、相手が断った（-1004）、相手が切った（-1005）です。システムに拒否された要求が、それ以外の要求（答えたも
    のを含む）を合わせた数より多ければ、その走査は拒否されたとみなします。数えるのは、レコーダーとテレビの両方の要
    求を合わせた 1 つの数です。許可はポートではなくアプリのもので（テックノートの "If your program has local network
    access, the system allows the operation. If not, the system blocks it."）、両方の要求が一緒に拒否されるか一緒に
    外へ出るので、2 つに分けて数えても同じことを 2 回読むだけです。ただし、レコーダーかテレビが見つかった走査は、数に
    かかわらず結果を言います。何かは外へ出ています。走査の途中で許可されたときにはそうなるはずです（まだ見ていま
    せん）。そのとき、探す機器への要求が許可の前に拒否されていて、拒否されたものが少数なら、「レコーダーもテレビも
    見つかりませんでした」と言います。もう一度押せば見つかります。
    - 全部ではなく大半で決めるのは、確認なしで通る宛先（上の例外）が、許可があるときと同じに返るからです。2026-10-06
      の実機では、その宛先が断りました（252 件が -1009、1 件が -1004）。ポートを黙って捨てる宛先なら時間切れになり、
      そういう宛先が 2 つある家もありえます。規則の表のテストに、どれも行があります。
    - 許可があれば、システムは要求を拒否しません（テックノートの "If your program has local network access, the
      system allows the operation."）。2026-10-06 の実機でも、許可したあとの走査に、システムに拒否された要求はありま
      せんでした。誰もいないアドレスへの要求は時間切れで返ります。走査はアドレスごとに 1.2 秒を与え、それを過ぎても
      終わらない要求は `Discovery.probe` が 2.2 秒で取り消すので、-1001 か -999 になります（ループバックの誰もいない
      アドレスで、本物のセッションを通して確かめ、テストにしています）。ですから、どのアドレスもすぐに断るサブネット
      も、大半が外へ出て数件だけ拒否された走査も、拒否された走査にはならず、結果をすぐに言います。
    - 拒否に付くコードを 1 つに決めず、外へ出た返り方のコードでないものを拒否と読むのは、Apple が待たないセッション
      の失敗を "fails immediately with an error, such as `NSURLErrorNotConnectedToInternet`"（-1009。
      `waitsForConnectivity` のページ）と例として挙げているだけだからです。確認の裏で拒否された要求に付いたコード
      は、2026-10-06 の実機では -1009 でした。ほかの iOS のバージョンや機種で何が付くかは、まだ見ていません。
    - 拒否されたら、許可の案内を出し、その走査で**レコーダーの要求が拒否された**アドレスのうち最初に返ったもの
      （`ScanTally.turnedAwayAt`。`ScanTally(_:keepingAddressFrom: Upnp.port)` で、64220 番の要求からだけ控えます）
      に、レコーダーの要求を 1 秒に 1 件送ります（`Discovery.turnedAway`）。拒否されたものと同じ要求を、同じアドレス
      とポートに尋ね直すことになります。断ったアドレスにも、前もって決めたアドレスにも送りません。確認なしで通る宛先な
      ら、許可がなくても外へ出てしまうからです。80 番の要求だけが拒否されたアドレスにも送りません。確認なしで通る宛先
      は 80 番にも尋ねられ、そこで拒否と読むコードで失敗することがあるからです（読めない答えや、リダイレクトに従ってい
      れば証明書の失敗 -1202）。そこを控えると、64220 番で断られた 1 件が外へ出たと読まれ、許可がないまま案内が下りて、
      走査し直しが 120 回まで続きます。拒否されたアドレスは確認なしで通る宛先ではないので、許可がないうちは拒否され、
      許可が出れば外へ出ます。テックノートがどの操作についても "If your program has local network access, the system allows the operation. If
      not, the system blocks it." と書いているとおりですが、尋ね直した 1 件でそうなるところは、実機ではまだ見ていま
      せん。その 1 件も同じ規則で読みます。1 件なので、システムに拒否されたかどうかがそのまま答えで、断られたこと、
      時間切れ、答えは、外へ出たしるしです。アドレスはメモリにだけ、その走査と、そのあとに続く 1 件ずつの要求の間
      （次の走査か、押した操作が終わるまで）持ち、ログにも件数の行にも書きません。
    - 1 件が外へ出たら、案内を下ろして走査し直し、その結果も同じ規則で読みます。走査し直しが拒否されれば、その走査で
      拒否されたアドレスに尋ね直します。
    - 1 件ずつの要求の前と、そのあとの走査の前に、Wi-Fi を読み直します。無ければ「Wi-Fi に接続されていません」と言
      い、もう誰にも尋ねません。別のサブネットに移っていれば（尋ね直すアドレスが、今の Wi-Fi で回るアドレスに無けれ
      ば）、古いサブネットには何も送らず、その周の要求の代わりに、新しいサブネットですぐに走査し直します。案内は出し
      たままで、その走査の結果を同じ規則で読みます。
    - 1 件ずつの要求は、1 回押すごとに合わせて 120 件までです（`AppModel.singleRequestsAllowed`）。使い切ったら、案
      内はそのまま、何も言わず、ボタンは押せます。
    - 網にかからないものがあります。確認の裏でシステムが要求を止めておいて、時間切れにした場合です。時間切れは誰もい
      ない家と見分けがつかないので、「見つかりませんでした」と出ます。まだ見ていません。
    - 逆に、許可があるのに拒否された走査と読むことがあります。Apple は、待たないセッションがすぐに失敗するわけの例に
      "the device might require a VPN connection but none is available"（`waitsForConnectivity` のページ）も挙げて
      います。VPN を通さないと届かない構成で VPN が上がっていなければ、どの要求もすぐに失敗し、許可の案内が出たまま、
      1 件ずつの要求が 120 件まで続き、そのあとも案内が残ります（押し直しても同じ）。VPN が上がるか Wi-Fi が無くなれ
      ば、そのとき結果を言います。まだ見ていません。
    - 許可済みの家では、走査は 1 回で、結果はすぐに出ます。システムが要求を拒否しないので拒否された走査にはならず、1
      件ずつの要求も、間を置くことも起きません。
  - **際限なく繰り返すものはありません。** 走査の 1 件ずつの要求は `singleRequestsAllowed`（120）についての `for`
    で、1 周で要求を多くて 1 件と、走査を多くて 1 回します（別のサブネットに移っていれば、要求の代わりに走査を 1
    回）。周を戻すものはないので、1 回押すごとに、最初の走査のあとは要求が 120 件まで、走査が 120 回までです。接続側
    の待ちは `turnsAllowed` についての `for` で、1 周で接続を 1 本張り、その接続が答えのないまま消えたときにだけ次の
    周へ行くので、張る接続は 120 本までです。
  - **画面に出るもの。** 許可済みなら、押したあと走査が終わったところで（約 6 秒）結果が出ます。初めて押して確認が出
    たときは、押してからの順に:
    1. 押した直後: ボタンは押せず、横に小さなくるくる。「検索中 n / 253」。
    2. 走査が拒否されたら（2026-10-06 の実機では押してから 0.2 秒ほど）: 赤い文は出ず、許可の案内と「設定を開く」。
       「検索中」は消え、ボタンは押せます（くるくるは無し）。システムの確認はその上に出ています。
    3. 1 秒に 1 件の要求の間: 2 のまま、何も変わりません。
    4. 「許可」のあと、次の 1 件が外へ出たら（多くて 1 秒の間と、その 1 件の時間。黙っているアドレスなら 1.2 秒ほ
       ど）: 案内が消え、「検索中 0 / 253」から走査し直します。ボタンは押せません。
    5. その走査で見つかれば、見つかったものの文（「レコーダーが n 台見つかりました」「テレビが n 台見つかりました」
       「レコーダーが n 台、テレビが m 台見つかりました」）と一覧、誰もいなければ赤い「レコーダーもテレビも見つかりま
       せんでした」と、考えられる原因 5 つ。また拒否されれば 2 に戻ります。
    6. 120 件を使い切ったら: 2 のまま、要求はもう出ません。もう一度押すと最初からやり直します。
  - **ボタン。** 「レコーダーとテレビを探す」が押せず、横にくるくるが出るのは、走査が進行中で、しかも許可の案内が出てい

  試みも `RecorderDriver.reachWithNoScreen` にあり、マジックパケットの送り方だけをアプリから受け取ります
  （`NoScreenReachTests` は偽のパケットで確かめます）。テレビ（ソニーの BRAVIA）は同じ `DeviceLink` に
  `TVDriver.swift` を載せ、レコーダーのリンクとは別に動きます。テレビとの通信（Scalar の JSON-RPC、PIN での登録と
  cookie）は `ScalarClient.swift` にあります。テレビは起こさず、接続の最初にも操作の前の確認にも、待機中も
  答える `getSystemSupportedFunction` で、どのテレビが答えるかを聞きます。
  どのテレビかは保存した Wake-on-LAN の MAC で見分け（起動して最初の応答から）、cookie の更新はアプリが前面に
  あるときだけ行います。アドレスが変わったテレビの探し直しと、操作の前の確認でそのテレビだと聞けなかったとき
  のことは、上の「LAN の判定」にあります。テレビが 1 台
  保存してあるとき、別の MAC を言うテレビの登録は、登録の要求を送る前に断ります（`ScalarClient.enrol(expecting:)`。
  画面に番号は出ません）。別のテレビを使うのは「テレビを外す」のあとです。MAC を言わないテレビは、接続と同じく、
  保存したテレビとして受け入れます。テレビの録画予約の一覧、変更、削除も `TVDriver.swift` の手順で、結果ごとの文もそこに
  あります。一覧の 1 行の読みと、変える前と消す前に同じ予約かを確かめる規則（番号と番組の両方が合うこと）は
  `TVSchedule.swift` です。
  テレビに予約を入れるための要求は 3 つで、どれも `ScalarClient.swift` にあります。局の一覧
  （`avContent.getContentList` 1.0、50 局ずつ）、その予約を入れると録れなくなる予約の問い合わせ
  （`recording.getConflictScheduleList` 1.0）、作成（`recording.addSchedule` 1.1）です。送る中身のテレビ側の綴りは
  `TVReservation.swift` にあり、測って分かった規則もそこに書いてあります。局の uri は一覧で返ったものをそのまま送り、
  組み立て直しません。番組の局（放送の種別とサービス ID）と違う局には、本文を作りません（番組 ID はその局の中でしか
  意味を持たないため）。開始の時刻はレコーダーの `+09:00` ではなく `+0900`、番組 ID は 10 進の文字列、長さは数で、
  録画モードは送りません。番組名での繰り返しは `title` です。毎週の繰り返しは番組の曜日（日本時間）のものだけを送り、
  月−金は土日の番組に、月−土は日曜の番組に送りません。午前 4 時より前に始まる番組には、曜日の入る繰り返しを
  どれも送りません（放送の 1 日と暦の 1 日がずれる時間帯で、測っていないため）。局の一覧は、どの頁で失敗しても
  読めなかったことにします（途中までを返すと、その先の局が「テレビに無い」ことになるため）。問い合わせの答えが
  読めないときも、「何も録れなくならない」とは読みません。作成の応答が言うのは `annotation` という数だけで
  （測った限りは 0）、そのまま返します。テレビへ送る本文は、鍵を並べて書きます（`.sortedKeys`）。
  辞書には順序が無く、そのままでは同じ要求のバイト列が起動のたびに変わり、実機で確かめたものと出荷するものが
  同じになりません。この 3 つの要求を使うのは、下に書く「送信待ちの 1 件をテレビに送る手順」だけです。
  アプリがその手順を呼ぶのは、テレビ宛の送信待ちを送るとき（その下の「テレビ宛の送信待ちをいつ
  送るか」）と、テレビに予約を入れるとき、送信待ちの行を送り直すとき（さらに下の「テレビに予約を入れる、
  送り直す」）です。テレビ宛の行は、番組の画面でテレビに予約を入れたときにできます（その下の「番組の
  画面」）。
  アプリ自身のクライアントから実機に送って分かったこと: 局の一覧は、終わりの先の頁を聞くと空の頁が返ります。
  作成は受け付けられると `annotation` 0 を返し、一覧には送った項目がそのまま（録画モードは DR で）載りますが、
  題名はテレビが番組表から付け直します。同じ番組の 2 回目は 41222 で、何も作られません。契約していない局への
  作成と、番組の曜日と合わない毎週の作成は、どちらもエラー 7 で断られます。毎日・月−金・月−土は、テレビの
  予約一覧にそのとおりの言い方で出ます。同じ時刻に 3 件目を入れると、問い合わせはいちばん先に作った 1 件を名指しし、
  作成は通って、その 1 件が録れない状態（`fullyOverlapped`）になります。視聴予約は名指しされませんが、作成のあと
  一部重なり（`partlyOverlapped`）に変わることがあります。受け付けられない cookie での作成は 403 で、何も
  作られません。
  送信待ちの 1 件をテレビに送る手順も `ScalarClient.swift` にあり、送信待ちが機器に頼む形（`QueueTarget` の
  `openRound` と `send`）で書いてあります。レコーダーは作成の要求 1 つで済みますが、テレビは作成に、何を
  作ったかも、何を録れなくしたかも答えません。そこで前後に読みます。規則は次のとおりで、実機の答えで確かめた
  ものに（測）、確かめていないものに（未測）と書きます。
  回の初めに、録画用のディスクと予約の一覧を読みます。ディスクが無ければ、何も送らずにその回をやめ、行には何も
  書きません（ディスクが戻れば、そのまま送られます）。一覧に、行と同じ局で同じ番組 ID の録画予約があれば、その行は
  送らずに「すでにある」として送信待ちから外します。題名でも開始の時刻でも探しません。題名はテレビが付け直し
  （測）、番組を追う予約は開始が動いてもその番組のものだからです。視聴予約は録画しないので数えません。ただし、
  毎回録画を頼んだ行に対して、テレビにある予約がそれに足りないときは、外しません。外すと、残りの回の番組が
  予約されないまま、何も言わずに送信待ちから消えるからです。足りないのは、テレビにあるのが 1 回だけの予約
  （`repeatType` が `1` か、書かれていない）のときと、テレビにある毎回録画の曜日が、頼んだ毎回録画の曜日の
  一部でしかないときです。毎日を頼んだ行には、毎週・月−金・月−土のどれも足りません。月−土を頼んだ行には、
  月−金と、月曜から土曜までの毎週が足りません。月−金を頼んだ行には、月曜から金曜までの毎週が足りません
  （毎日・月−金・月−土は、テレビ自身の予約一覧がそう言い表します。毎週は、月曜・木曜・日曜の符号を番組の
  曜日で確かめました。測）。その行は、何も聞かずに、テレビの予約の毎回録画を変更してから「もう一度送る」を
  選ぶよう書いた理由を付けて、保留にします（テレビの予約の毎回録画は、予約の画面で変更できます。予約を
  削除してから送り直す道は、そのあいだ番組が予約されないままになり、送り直しが通らなければそのままなので、
  勧めません）。頼んだ毎回録画に足りる設定に変更してから送り直すと、その行は「すでにある」になります。理由の
  文は、1 回だけの予約のときと、曜日の少ない毎回録画のときとで別です。ほかの組み合わせは「すでにある」の
  ままです。1 回を頼んだ行にテレビの毎回録画があるとき、同じ毎回録画があるとき、頼んだ曜日をすべて含む毎回録画があるときは、
  失うものがありません。番組名での毎回録画（`title`）は、頼んだ側でもテレビにある側でも、1 回だけの予約としか
  比べません。名前で追うもので、曜日で決まる毎回録画と比べてどちらが広いかは分かりません（未測）。曜日が
  1 日も重ならない毎回録画どうしも比べません（片方は番組の曜日に合わないもので、毎週ならテレビが断り、
  月−金と月−土は送っていません）。頼んだ毎回録画は行の符号そのもので比べるので、テレビに送らない繰り返しを
  頼んだ行も同じに比べます。足りなければ外さず、その行は「送らない繰り返し」の理由で保留になります
  （送る手順では、その確認のほうが先のため）。番組 ID の無い予約と、テレビに送らない繰り返しの予約も、
  何も聞かずに、理由を書いて保留にします。
  放送が始まっていて、まだ終わっていない番組の行は、ほかの行と同じに送ります。レコーダーに送るのと
  同じです（終わった番組の行は、回の前に送信待ちが捨てます）。局の一覧、問い合わせ、作成、一覧の順も、
  同意の扱いも、テレビにある予約が頼んだ毎回録画に足りないときの保留も、ほかの行と変わりません。
  本物のテレビがそういう作成に何と答えるかは、まだ測っていません（下の「測っていないこと」）。回は、番組の
  開始も終了も時計と比べません。クライアントは時計を持たず、いまの時刻を読むのは送信待ちだけです
  （`PendingQueue.flush` の `now`。終わった番組を捨てるのに使います）。回のテストと、席の確認のリハーサルは、
  決まった日時の行を送るとき、自分の決めた時刻をそこに渡すので、走らせる日によって結果が変わりません。
  局の一覧は、放送の種別ごとに、その回で 1 度だけ読みます。読めた一覧にその局が無ければ、理由を書いて
  保留にします。読めなければ、行に何も書かずに見送ります（次の機会に送り、下の「何も言わない答え」には
  数えません）。最初の頁がその要求自身のエラーで答えられたら、「その種別の局は無い」と読み（未測）、局が無いときと
  同じに保留にします。ただし、テレビの状態を言う符号は「局が無い」とは読まず、読めなかったときと同じに見送ります
  （行に何も書かず、数えず、その回ではその種別をもう聞きません）。保留にすると、いずれ変わる状態のために、
  その種別の行がどれも自分からは送られなくなるからです。その符号は 40005 と 7 です。40005 は、
  このクライアントがどの要求でも「電源が入っていない」と読む符号で、待機中のテレビがほかの要求に返しました（測）。
  7 は「いまの状態では受けられない」の符号で、局の一覧に返ったことはありません（作成に返る 7 とは別の意味です）。
  局の一覧そのものは、待機中のテレビから読めています（測。別の道具で 5 種別とも、このクライアントでは電源を
  切って約 1 分後に地上波を読み、どちらも局が返りました）。局の一覧に 40005 や 7 が返ったことも、テレビが持たない
  種別を聞いたこともまだ無く、2 つの読みはどちらも未測です。
  その予約を入れると録れなくなる予約は、毎回問い合わせます。1 件でも名指しされたら、録画でも視聴予約でも、
  それぞれを題名と局の名前と開始の月日・時刻で書いた理由を付けて保留にし、作成は送りません。局の名前は、その行の
  uri の `&srvName=` から後ろを、テレビの書いたまま使います（問い合わせが名指しする行には `channelName` が
  無いため）。利用者が「もう一度送る」を選んだ行（録れなくなる予約があっても入れる、という同意）でも
  問い合わせ直し、行に書いてある理由が、今の答えから作った理由と一字も違わないときだけ作成を送ります。同意は、
  その文が名指しした予約に対するもので、一覧はそのあと変わっているかもしれないからです。局の名前まで
  書くのもそのためです。同じ題名で同じ時刻の予約が 2 つの局にあるとき（同時に放送される番組）、片方を失うことへの
  同意が、もう片方を失うことへの同意にならないようにします。答えが読めないときは、何も
  名指しされなかったことにしません。理由の頭の文（「この予約を入れると、次の予約は録画されません」）は、保留の
  行をそれで見分けるので変えません。視聴予約が名指しされると「録画されません」は合わない言い方になりますが、
  テレビが視聴予約を名指ししたことはありません。
  作成を送ったら、一覧を読みます。一覧に（局と番組 ID で）あって初めて「作った」です。受け付けたと答えて一覧に
  無ければ、理由を書いて保留にします。41222 は何も作らないので（測）、一覧にあれば「すでにある」、無ければ
  保留です。41222 は繰り返しが違っても返るので（測）、一覧にある予約が、行の頼んだ毎回録画に足りないときは、
  「すでにある」にせず、回の初めと同じ規則で、同じ理由を書いて保留にします。エラー 7 は、その予約そのものが
  断られた符号なので（契約していない局、番組の曜日と合わない毎週。どちらも測）、理由を書いて保留にし、同じものは
  送り直しません。作成の前と後の一覧を比べ、作った行が重なりの印を持つとき、名指しされなかった行が新しく印を
  持ったとき（視聴予約が `partlyOverlapped` になる。測）は、その文を「作った」に添えます
  （`RowSent.made(saying:)`）。新しく印を持った行は、録画予約と視聴予約を別の文で言います。録画予約には
  「録画されないことがあります」と言い（`fullyOverlapped` は、録れない側になった録画予約に付いた印です。測）、
  視聴予約には「重なりました」とだけ言います。視聴予約は録画しないので、印の付いた視聴予約を「録画されない」
  とは言いません。送信待ちはそれを結果の `remarks` に入れ、「登録しました」の文のすぐ後ろで言います。
  レコーダーは何も添えず、文は前と一字も変わりません。
  どの段でも、無応答と、受け付けられない cookie（403。作成でも何も作られない。測）は、その回を止めます。作成が
  無応答なら、一覧も読みません。作られているかもしれないので、次の回の初めの一覧が教えます（あれば「すでにある」、
  無ければ送る）。問い合わせや作成への答えが、行について何も言わないとき（知らない符号、読めない答え）は、行に何も
  書かずに見送り、そういう行が 2 件続いたらその回を止めます。おかしいのは行ではなくテレビのほう、と読むためです。
  41222 のあとの一覧が読めないときも、同じに数えます（何も作られていないので、回の持っている一覧はそのまま
  使えます）。受け付けられた作成のあとの一覧が読めないときは、数に関係なく、そこで回を止めます。回が拠っている
  一覧が無くなり、続ければ、次の行が「作ったことで何を変えたか」を、この作成より前の一覧と比べて言うことに
  なるからです。その行には何も書かず、見送った行としても伝えません（その一覧が無応答だったときと同じです）。
  見送った行は「送れなかったため、次の機会にもう一度送ります」と伝えられますが、テレビは作成を受け付けたと
  答えていて、作られていれば、次の回は初めの一覧で見つけて「すでにある」と伝え、送り直さないからです。
  「2 件続いたら」の数を初めから数え直すのは、テレビがその行について何か答えたときだけです。問い合わせで
  名指しされて保留、符号で断られて保留、一覧に無くて保留、41222 のあとの一覧にあった予約が頼んだ毎回録画に
  足りなくて保留、作った、すでにあった、の 6 つです。何も聞かずに保留にした行（番組 ID が無い、送らない
  繰り返し、回の一覧にある予約が頼んだ毎回録画に足りない、局が一覧に無い）と、局の
  一覧が読めずに見送った行は、数えもせず、数え直しもしません。テレビが答えるかどうかを、何も
  示さないからです。
  残してあること: 作成が無応答だった行と、受け付けられた作成のあとの一覧が読めなかった行は、次の回の初めの一覧で
  見つかり、「すでにある」と伝えられます。その作成がほかの予約に重なりの印を付けていても、それはどこでも
  言われません（回の初めに返るのは、どの行がすでにあるかだけです）。
  この規則は `TVRoundTests` が偽のテレビ（`DemoTV`）で確かめます。偽のテレビは、実機が答えたとおりに答えます。
  題名を付け直す、3 件目の問い合わせには先に作った 1 件を名指しして作成は通す、視聴予約を一部重なりにする、
  契約していない局と曜日の合わない毎週はエラー 7、同じ番組の 2 回目は 41222、受け付けない cookie は 403 です。
  実機で見ていないことを答える箇所には、そう書いてあります。
  テレビ宛の送信待ちをいつ送るかは、ドライバーの手順です（`TVDriver.sendWhatWaits`。`TVDriverTests` が確かめます）。
  送るのは 2 つのときです。1 つは、テレビへの接続が、登録の要る読み取り（ディスク）まで通ったときです。接続は、
  起動、アプリに戻ったとき（最後の応答から 1 分以上たっていれば）、未接続のときのネットワークの変化、再接続、
  登録の直後、サンプルデータの終了、ローカルネットワークの許可が下りたときに起きます。バックグラウンドで起きた
  接続でも送ります（前面に限るのは cookie の更新だけです）。接続の中では、ホストに「届いた」と伝える前に送り、
  答えたばかりのテレビを確かめ直す要求は送りません。もう 1 つは、予約一覧の引き下げ更新です。送ってから一覧を
  読むので、作った予約がその一覧に入ります。聞けるテレビには接続しません。聞けないとき（未接続、登録が要る）は
  接続し直し、その接続が送ります。
  送る前に見るのは端末の送信待ちで、テレビではありません。テレビ宛の行が無ければ、何も聞かず、進行中の行も
  出しません。理由の付いた行しか無いときも同じです（出すと、その行が残っている間、接続のたびに行が点きます）。
  番組の終わった行があれば、テレビには何も聞かずに捨て、そう伝えます。同意は渡しません。録れなくなる予約が
  あるために保留にした行は、利用者が選ぶまで送りません。テレビに聞けないとき（未接続、登録が要る、リンクが
  無い）は、何も読まず、何も送らず、何も書きません。次に接続できたときに送ります。聞けるかどうかは、
  送信待ちを読んだあと、クライアントを取るところでもう一度確かめます。読んでいる間に接続が始まっていれば、
  リンクにあるのは新しいクライアントで、どのテレビが答えるのかをまだ聞いていないからです。送っている間は、
  テレビの行に「テレビに送信待ちの予約を登録中」と出します。止まるのはテレビのボタンだけで、レコーダーの
  ボタンは止まりません。接続の外では、ほかの操作と同じ確認を先に通します（最後の応答が古いか、前の確認で
  そのテレビだと聞けなかったときは、`getSystemSupportedFunction` で、どのテレビが答えるかを聞きます）。
  回が止まったときに何を残し、何を言うかは、止まり方で決まります。どの場合も、行に理由は書きません。
  ディスクが無いとき: テレビのエラーの行には何も出さず、接続は成立したことにします。失敗ではないので、
  エラーとしては言いません（どこで言うかは、下の「ディスクの状態」）。作成より前の無応答: 読み込みの

  消えます）。保留、見送り、止まった回のあとは、何も読みません。
  戸口（何も送る前に、ドライバーが自分で断る所）で何を言うかは、操作が何を返すかで決めてあります。
  ドライバーがアプリに渡す操作すべての規則で、`Reserved` の説明に書いてあります。文の入った結果を返す
  操作（テレビに予約を入れる、行を送り直す、テレビの予約を変更する）は、断ったことをその結果で言い、機器の
  エラーの行には触りません。何も送っておらず、前の操作が残した文は、この操作が上書きするものではないからです
  （送り直しと変更の結果は、言うことが無いとき、つまりほかの機器の行と、もう待っていない行では、空です）。
  レコーダーに予約を入れる操作、レコーダーの予約を変更する操作、両方の機器の予約の削除（`Altered` を返します）も
  同じです。断ったことは結果で言い、エラーの行は前の操作が残したままにします。確認や読み込みがエラーの行に
  書いたもの、送って失敗したもの（無応答、機器の断り）は、行に出たうえで、結果も同じ文を言います。いま読んだ
  一覧で、行が無かった、別の番組に付いていた、機器が「その予約は無い」と答えた（読み直しが通ったとき）、は
  結果だけで言います（その読み込みが行を消しているので）。画面は結果の文をアラートで言い、
  「〈機器〉がエラーを返しました」のような、行が空のときの代わりの文はありません。画面に言うことを何も返さない
  操作（送信待ちの送信、一覧の読み込み）は、戸口では何も言いません。送ったものの失敗は、どの操作でもリンクが
  エラーの行に書き（`DeviceLink.say`）、操作の前の確認が書くものは、確認のものです（レコーダーの確認は、
  どの機体かを言わない答えを行に書かず、それで止まった操作が書きます。上の「操作の前に起こす」）。
  送り直すとき（`resend`）は、テレビ宛でない行を戸口で断ります。何も読まず、送らず、書かず、言いません
  （削除が、ほかの機器の予約を断るのと同じです）。リンクかデータベースが無いときも同じです。行は、id で
  送信待ちから読み直します。渡された行は、画面が描いたときのものだからです。もう無ければ、何もしません。
  理由をどうするかは、送信待ちにいま書いてある理由で決めます。録れなくなる予約を名指しした理由は、行に
  残します。その文が、利用者の同意する相手だからです。ただし、利用者が押した行の理由と一字も
  違わないときだけで、違っていれば、何も送らず、何も変えません（利用者は、変わったあとの文を見ていません。
  ホストが送信待ちを読み直すので、画面には出ます）。ほかの理由は消します。行は、これからはほかの行と一緒に、
  自分から送られます。この行に同意は渡しません。
  テレビに聞けないときは、接続します（利用者が頼んだことなので。予約を入れるときは接続しません）。その接続が
  送信待ちを送るので、理由を消した行はそこで送られ、送り直しは接続で終わります。レコーダーの送り直しと
  同じです。名指しの理由で保留の行は、接続では送られません。接続のあとテレビに聞けるようになっていれば続けて
  送り、聞けなければ保留のままです。聞けるときは、「テレビに送信待ちの予約を登録中」の行を出し、確認を
  通してから、その 1 行の回を走らせます。そのあと一覧を読むのは、予約を入れるときと同じ場合です。
  同意は、文に対するものです。送信待ちには、行の id と、利用者が押した行に書いてあった文を組にして渡します
  （`flush` の `consenting`）。送信待ちは、その行を送る番が来たときに、行にいま書いてある理由がその文と
  同じときだけ、同意のある行として送ります。同じ行が 2 回続けて押されても、1 回目の回が別の予約を名指しして
  理由を書き換えれば、2 回目は理由の付いたふつうの行として保留になり、利用者の見ていない予約を録れなくする
  作成は出ません。テレビの側の半分は上の規則のままで、同意のある行でも問い合わせ直し、行の理由が今の答えから
  作った理由と同じときだけ作成を送ります。同意は、その 1 回の回のものです。同意を付けて送った行が、
  見送られたか、回が途中で止まったときは、行の理由を消します。残すと、その行は次からの送信で送られないのに、
  そういう行について言う文は「自分から送られる」と言うからです（作成の無応答なら「次にテレビが答えたときに
  一覧で確かめ、届いていなければ送ります」）。次の送信では、同意なしで聞き直されます。回が新しい理由を書いた
  行と、番が来たときに同意が成り立たなかった行は、その理由のままです。
  送り直しは、その行がどうなったかも返します（`resend` の 3 つ目の値。予約を入れたときと
  同じ `Reserved` で、頼んだ画面が言います）。行は、いま待っているとおりに返します。送り直しが理由を
  消していれば、回の前でも後でも、消えた形です。回が走ったときは、予約を入れたときと同じに読みます。回が
  走らなかったときは、次のとおりです。戸口で断ったときと、行がもう送信待ちに無いときは、何も返しません。
  送信待ちの理由が、押した文から変わっていたときは、「録れなくなる予約がある」を、送信待ちにいまある行で
  返します（画面が、いまの名前で聞き直せるように）。理由を消して接続に任せたときは、接続が終わってから
  送信待ちを 1 回読み、行を id で探します。もう無ければ、何も返しません（作った、すでにあった、番組が
  終わっていた、のどれかで、接続の送信が帯で言います。送信待ちが読めなかったときも、何も返しません）。
  名指しの理由が付いていれば「録れなくなる予約がある」、ほかの理由が付いていれば、その理由で「端末に
  残した」です。理由が無く、テレビにまだ聞けなければ、予約を入れたときと同じ「テレビに
  接続していないため」の文（登録が要るなら、その文）で「端末に残した」です。ただし、その接続が送信待ちの
  送信まで進み、作成が無応答だったときは、作成の無応答の文で返します。行はテレビに届いているかも
  しれず、「接続していないため…予約タブで削除できます」と答えれば、送っていない行のように言うことになる
  からです（エラーの行にも、同じ無応答の文が出ています）。見分けるのは 2 つを合わせてで、リンクの
  クライアントが登録の確認まで進んだものであることと、エラーの行がその文であることです。行の文だけでは、
  前の作成が残した文の下で、接続が初めから無応答だったときと区別できません（そのときは、行はどこにも
  送っていないので、「接続していないため」の文です）。理由が無く、テレビに
  聞けるなら、接続は通ったのに、その送信が行を残しています。ディスクが無いと分かっていればディスクの文、
  そうでなければ答えが読めないときの文で返し、接続していないとは言いません。
  名指しの理由で保留の行が送られなかったとき（接続のあともテレビに聞けない、操作の前の確認が通らない）は、
  行を理由ごと返します。文は、削除が戸口で言うのと同じ 2 つのどちらかです（「テレビに接続していません。
  テレビの電源とネットワーク接続を確認してください。」、登録が要るなら「テレビへの登録が必要です。設定の
  「テレビ」から登録してください」）。理由の付いた行は、テレビが次に何をしても利用者を待つので、「自分から
  送られる」とは言いません。理由の無い行が同じように送られなかったときは、予約を入れたときと同じ「テレビに
  接続していないため」の文です。回が空だったとき（送信待ちを読めなかった回は、そう見えます）は、送信待ちを
  読み直します。行がまだあれば、理由が無ければ答えが読めないときの文で、同意した理由が残っていれば、
  送られなかった行と同じに返します。
  行そのものを出している画面は、行が言っていないことだけを言います（`Reserved.besideItsRow`。予約タブが
  使います）。「作った」は、何も言いません。行は送信待ちから予約の一覧へ移り、送信の文は帯が言います。
  「録れなくなる予約がある」は、行の理由を全部言います。予約タブでこの答えが返るのは、利用者が押したのとは
  別の予約が名指しされたときだけで、もう一度送れば、それへの同意になるからです。「端末に残した」は、文が
  行の理由と同じなら何も言わず、違えばその文（送られなかったわけ、自分から送られること）を言います。
  「していない」は、その文を言います。
  アプリの側では、テレビのホストが頼み、返ってきたものを持ちます（`TVHost.reserve`、`TVHost.resend`）。読んだ
  一覧が返れば持ち、画面の送信待ちは、どちらの操作のあとでも、結果が何でも読み直します（回が走らなかった
  送り直しでも、行の理由が消えていることがあります）。入れた予約の結果は、頼んだ側にそのまま返し、帯には
  出しません。帯の文は「送信待ちだった「…」をテレビに登録しました」で、待っていなかった予約には
  合わないからです。送り直した行は、待っていた行なので、回の結果を送信待ちの送信と同じに帯に出し
  （言うことが無ければ前の文を残します）、行がどうなったかは、その横で、頼んだ側に返します。帯は、前の
  送信がその行について言った文（「登録できませんでした。理由は予約タブにあります」）を出したままかもしれず、
  送り直して作られたなら、帯がその続きを言わなければ、古い文だけが残るからです。「もう一度送る」は、行の
  機器へ最初に振り分けます（`AppModel.resend`）。テレビ宛の行のために、レコーダーを確かめることも、
  レコーダーの送信の番を取ることもありません。レコーダー宛の行は、レコーダーのドライバーの送り直しへ渡します
  （下の「レコーダーの予約の手順」）。画面は、その隣の入口（`AppModel.sendAgain`）を呼び、どちらの機器の行も、
  ドライバーが返した結果を受け取ります。帯は、どちらの機器でも、回が送ったものを言います。
  予約タブは、送信待ちの行がどの機器宛かを、行の 2 行目の先頭で言います（「テレビ · 10/6(火) 21:00 · …」）。
  言うのは、テレビを登録してある家と、レコーダー宛でない行だけです（`AppModel.deviceSaid`）。送信待ちの下の
  説明は、登録してある機器ではなく、行が待っている機器で決めます（`AppModel.whatWaitsSays`）。レコーダー宛の
  行だけなら、テレビを登録していても、前のとおりの文です。テレビ宛だけなら「テレビにまだ届いていない
  予約です。次にテレビにつながったときに登録します。」、両方なら「レコーダーやテレビにまだ届いていない
  予約です。それぞれ、次につながったときに登録します。」で、理由の付いた行があれば、どれにも前のとおり、
  送り直し方の文が続きます。テレビ宛の行の「もう一度送る」と「削除」は、テレビが作業中の間は押せません
  （出ている送信が、その行を手に持っているかもしれません）。レコーダーの作業では止まりません。レコーダー宛の
  行も同じく、レコーダーが作業中の間は押せません（`AppModel.isBusy(for:)`。帯にレコーダーの行が出ている間で、
  番組表の取得や録画の操作も含みます）。「もう一度送る」の結果は、行が言っていないことがあるときだけ、
  「送信待ちの予約」という題のアラートで言います。言うことの無い結果は、出ているアラートを消しません
  （レコーダー宛の行の送り直しは、レコーダーを起こす間は終わりません。その間に送り直したテレビ宛の行の答えが
  先に出ていても、読まれる前に消えないようにです）。削除の確認は、行の機器の名前で
  言います（「この端末から削除し、テレビには送りません。」）。確認が出ている間にテレビの作業が始まることが
  あるので、確認の「削除する」も、行の機器が作業中なら何もしません（`AppModel.deleteWaiting`。行は残ります。
  テレビを外す操作と同じです）。削除は、どちらの機器の行も、送信待ちの番の中で行い（レコーダーは
  `RecorderDriver.deleteWaiting`、テレビは `TVDriver.deleteWaiting`）、番を待つ間に送信がその行を作っていれば、
  消したとは言わず、帯が送った行に言う文（「送信待ちだった「…」を登録しました」）を言います。番の中で
  機器の一覧を読み、その番組の予約があれば、行がまだ待っていても同じです（下の「画面の無い処理」）。
  番組の画面: テレビに予約を入れるのは、番組の画面です（`ProgramSheet`）。テレビを登録してある家では、新しい
  予約の欄（「録画予約」）の最初の行が「予約先」で、その番組をまだ入れられる機器を出します
  （`AppModel.destinations(for:)`）。入れられるのは、登録してある機器のうち、その番組の予約を持っておらず、
  その番組の送信待ちも無い機器です（もう 1 つ入れても、同じ予約か、待っている行の
  置き換えにしかなりません）。両方に入れられれば選べて、開いたときはいつもレコーダーです（選んだ機器は
  覚えません）。片方だけなら、その機器を 1 行で出します。レコーダーがもう持っている番組は
  「予約先 テレビ」で開き、テレビだけが持っている番組は「予約先 レコーダー」で開きます。放送が始まった
  番組も、終わるまでは、どちらの機器にも入れられます（上の「測っていないこと」）。どちらにも入れられなければ、
  欄そのものがありません。機器が 1 つの家に、予約先の行はありません。テレビだけを登録した家には、番組表を開く
  入口がまだ無いので、番組の画面も開けません（規則は同じで、入れられるのはテレビだけです。
  テストはこの形も確かめます）。
  予約先の下は、その機器が受けるものです。レコーダーは前のとおりです（録画モード、毎回録画の 6 つ、時間の
  重なる予約、ボタン）。テレビは、録画モードが 1 行（DR）、毎回録画はその番組にテレビへ送るものだけで
  （`TVDriver.repeats(for:)`。戸口が断る繰り返しは、画面に出ません）、時間の重なる予約の行はありません。
  画面を開いても、テレビを選んでも、テレビには何も送りません。その予約を入れると録れなくなる予約は、
  利用者が予約したときに聞きます（すぐ下）。先に聞いて画面に出す形にしなかったのは、テレビに予約が作られる
  道を 1 つのままにするためと、先に聞いた答えは「予約する」が押されるまでに古くなり、回がどのみち
  聞き直すためです。欄がテレビのものになったら、毎回録画は「しない」に戻します。利用者が選んだときも、
  レコーダーがその番組を持っていると分かって変わったときも同じです（レコーダーのために選んだ
  繰り返しを、テレビに持ち越しません）。テレビの「録画予約する」が押せないのは、テレビが作業中の間と、この
  画面のほかの要求がまだ返っていない間です（下の「テレビへの要求が出ている間は」）。レコーダーの
  作業そのものでは止まりません。レコーダーに時間の重なる予約を聞くのは、欄がレコーダーのものの間だけです。
  確認の文は、ボタンが押されたときに欄が出していた機器を持ちます。文も「予約する」も、その機器だけを
  使います。確認が出ている間に一覧が読み直されて、入れられる機器が変わっても（レコーダーを起こしている
  間に開いた番組を、レコーダーがもう持っていたとき）、確認が名指ししなかった機器には入りません。テレビの
  確認の題は「この番組を録画予約しますか？」で、文の最後は「テレビに予約を登録します。テレビが
  応答しないときは端末に保存し、次に応答したときに登録します。」です（`TVDriver.confirming`）。機器が 2 つの
  家では、欄がどの機器のものかも、予約の途中（確認、要求、答えのアラートが出ている間）は読み直しません。
  テレビに入れた予約は、行が待つか、作られるかして、テレビを入れられない機器にします。そこで欄が
  レコーダーに戻ると、アラートの下で欄が変わり、テレビの予約のために、レコーダーが時間の重なる予約を
  聞かれるからです。読み直すのは、答えが閉じられて画面が残ったときです。
  入口は、機器によらず 1 つです（`AppModel.reserve(_:on:quality:repeating:)`）。名指しされた機器にだけ入れ、
  どちらの機器の答えも同じ `Reserved` です。テレビの予約は、最初にホストへ渡します。レコーダーには何も
  聞かず（時間の重なる予約も）、レコーダーのエラーの行にも触りません。録画モードは読みません。テレビが
  いなければ（架空のテレビを足す前のサンプルデータのモード）、何も控えず、何も送らず、「していない」です。
  レコーダーの予約は、そのドライバーの予約（`RecorderDriver.reserve`）に渡し、その結果を返します。
  作った、端末に残した（理由が付いていれば、利用者を待ちます）、していない、のどれかで、文は結果が持ちます
  （下の「レコーダーの予約の手順」）。
  この画面の要求が機器に出ている間は、画面のどこも押せず、画面を閉じられません（一覧ごと無効にし、閉じる
  ボタンも、引き下げて閉じることも止めます）。テレビへの予約と送り直し、レコーダーへの予約、レコーダー宛の行の
  「もう一度送る」、どちらの機器の予約の削除も同じです。答えはこの画面のアラートで言うので、画面が先に閉じると、
  どこにも出ないからです。押せるままだと、レコーダーの予約の削除で画面が閉じて、録れなくなる
  予約があるという問いが聞かれないまま行が保留で残ったり、予約先をレコーダーに替えて予約して、両方に
  入ったりします。レコーダーへの要求は、起こす間と USB HDD を待つ間も含めて、40 秒ほど画面を止めることが
  あります（予約は、送信待ちの番を、ほかの送信が終わるまで待つこともあります）。レコーダーが離れていると
  分かっていて端末に残すだけの予約は、すぐ答えます。
  送信待ちの行の削除だけは、送信待ちの番を待つ間、要求の行を出しません。そこで画面は、出ている削除の数を
  数えます（`ProgramSheet` の `others`。出すときに足し、返ったときに引きます）。0 でない間は、閉じるボタンと
  引き下げて閉じることを止め、どちらの機器の「録画予約する」、「もう一度送る」と「予約を変更する」、
  レコーダーの「予約を削除」が押せません（レコーダーへの予約は、削除と同じ送信待ちの番を待つので、先に返る
  削除が画面を閉じてしまいます）。
  要求の行（「テレビに予約を登録中」。送り直しと「それでも予約」では「テレビに送信待ちの
  予約を登録中」。レコーダーへの要求では、帯と同じ「予約を登録中」「送信待ちの予約を登録中」「予約を削除中」）は、
  「録画予約」の欄の中ではなく、それだけの欄として出します。送り直しのときは、行が待っているので、その機器の

  あれば、通知は、前に言った行でまだ待っているものも合わせた、そういう行のすべてについて言います。通知は
  前のものに代わるので、新しい行だけを言うと、先に言った行の知らせが消えるからです。その通知は、言った行が
  どれも待たなくなった次の処理で取り下げます。アプリ自身の送信や削除が、言った行をどれも待たないものにした
  ときも、その場で取り下げ、その行のことは忘れます（`TVTold.afterTheScreensSent`。次の画面の無い処理は、番組が
  始まってからかもしれないので）。言った停止は残します。テレビを登録し直したときと外したときは、言ったことを
  すべて忘れ、その通知もその場で取り下げます。最後に言った停止が「登録が必要」なら、送信待ちがどうなったかの
  通知も取り下げます（登録が要ると言う通知が、登録のあとまで残らないように）。
  テレビが答えないことは、それだけでは通知しません。深夜の処理は、
  レコーダーが答えないことも言いませんし、夜に答えないのは、たいてい端末が家の外にあるときです。言うのは、
  上の通知の終わりと、ショートカットのアクションの答えだけです。アクションの答えは、レコーダーの文のあとに
  テレビの文を続け、どちらにも言うことが無ければ「送信待ちの予約はありません。」を 1 回だけ言います。
  端末に登録が残っていない（別の端末のバックアップから戻したなど。キーチェーンの項目は端末の外に出ません。上の表の
  「テレビの登録の保存」）と、
  MAC だけを聞いて回が止まり、画面と同じく「テレビへの登録が必要です」と言います。再起動のあと一度もロックを
  解いていないときは、番組表キャッシュのファイルが開けず、キーチェーンまで行かずに何もせず終わります
  （Apple の既定のファイル保護による。見ていません）。ローカルネットワークの許可が切られていると、テレビが
  答えないのと同じに言います（どちらも何も答えないので、偽りではありません。画面の側は、アプリを開けば許可の
  ことを言います）。タスクの時間が切れたあとに戻った処理は、送信待ちの行がどうなったかだけを、途中で応答が
  なくなったという文を除いて言い、何も覚えません。中断された要求は、処理が戻ったときに通信の失敗として返り、
  クライアントはそれを無応答と読む、と考えるからです。これは推測で、見ていません。Apple の `BGProcessingTask`
  のページが言うのは、システムがプロセスを中断することがある、までです。アーカイブされた TN2277「Networking
  and Multitasking」は BSD ソケットと、`URLSession` より前にその上に作られたものの話で、中断されたアプリの
  ソケットの資源はカーネルに回収されることがあり、そのあとはそのソケットへの操作がすべて失敗する、と言います。
  `URLSession` の要求がそのときどうなるかは、読んだページにはありません。処理の途中でテレビを外されたら、
  何も言わず、何も覚えません。予約タブの「削除する」と設定の「外す」は、テレビ宛の行について、画面の無い
  処理の送信も含めて、進んでいる送信が終わるのを待ちます（`PendingQueue.betweenFlushes`。待つのは 1 回の回の
  長さです。番はすべての機器で 1 つなので、レコーダーの回も含みます）。ショートカットのアクションがアプリと
  同じプロセスで動き、この番を分け合うことは、推測で、見ていません（アクションはアプリ自身のターゲットに
  あります。Apple の記事「Creating your first app intent」が言うのは、App Extension に置いたものは別の
  プロセスで動かせる、までです）。「削除する」は、その番の中で、何かを消す前にテレビの予約一覧を読み直します。
  一覧にその番組があれば、行がまだ待っていても（作成をテレビが受け取り、答えが失われたとき）、帯が送った行に
  言う文（「送信待ちだった「…」をテレビに登録しました」）を言い、行は作ったものとして送信待ちから外します。
  待つ間に送信が行を持ち去っていて、番組がまだ終わっていなければ、一覧が読めなくても同じ文を言います（テレビが
  あるあいだ、終わっていない行が送信待ちから消えるのは、回が作ったか、すでにあると見つけたときと、アプリ自身の
  削除だけです。削除は 1 行に 1 つずつで、先の削除が番を待つあいだに同じ行をもう一度削除すると、何も言わずに
  すぐ戻ります）。どちらも、消したとは言いません。言えないこと: 作成をテレビが受け取り、答えが失われた行を、
  アプリのリンクが一覧を読めないときは、何も言わずに送らないまま消し、テレビには予約が残ります（アクションに
  答えなかったテレビは、たいていアプリにも答えないので、起こりやすい場合です）。
  テレビ宛の行を端末に残したときは、レコーダー宛のときと同じく、通知の許可を聞きます。
  テレビだけの家に残すこと: そういう家には開く番組表が無いので、まだテレビ宛の行を作れません。通知の仮の
  許可を取るのは、レコーダーに接続したときだけです。設定の通知と「帰宅したときに送る」の説明は、テレビが
  あると両方の機器のことを言い、レコーダーの残り容量のことも言います。どれもテレビだけの家の入口と一緒に、
  公開の前の段で揃えます。テレビだけの家の入口も、公開の前の段です（サンプルデータのテレビと、それを使う画面の
  テストは入りました。下の「サンプルデータのモード」）。保存してあるテレビの代わりに別のテレビを登録したときに行を保留にすることは、やめました。別の
  テレビの登録を MAC で断るので（上の「LAN の判定」の下）、行が別のテレビに向かうことがありません。
  テレビだけの家でも、起動のたびにチュートリアルを出すことはしません（`AppModel.welcomes`。何も保存して
  いないときだけ出します）。
  開発する人への注意: 送信待ちの行に宛先の機器を持たせる前の版（タグの付いた版は、v0.3.1
  までどれもそうです）を、テレビ宛の行のある端末で動かすと、その行をレコーダーに送ります。開発中の端末を古い
  版に戻すときは、先にテレビ宛の送信待ちを消します。
  ドライバーは自分のリンクを持つので、アプリは操作のたびにリンクを渡しません。アプリの側では、テレビのホスト
  （`TVHost`）が読んだ一覧を持ち、テレビを外せば一覧もホストごと無くなります。予約の変更と削除は、行を持っている
  機器へ最初に振り分けます（変更は `AppModel.change`、削除は `AppModel.cancel`）。レコーダーの予約の探し直し（`current`）も、ほかの機器の行は見つけません。
  レコーダーの予約の手順: レコーダーの予約一覧の読み込み、予約、変更、削除、送信待ちの送信、送り直し、
  送信待ちの行の削除、時間の重なる予約の問い合わせは、どれもドライバーの手順です（`RecorderDriver.reservations`、
  `refreshReservations`、`reserve`、`update`、`cancel`、`sendWhatWaits`、`resend`、`deleteWaiting`、`conflicts`）。
  どれもテレビの決まりに揃えてあり、揃えずに残した違いは、この段落の終わりにまとめます。アプリ（`AppModel`）は
  機器に振り分けて頼み、返った一覧を上の「答えたレコーダーが誰かで決める」の規則で持ち、結果を画面に渡します。
  ほかの機器の行は、どの手順も何も読まず、送らず、言わずに断ります（`RecorderDriverTests`）。送信待ちを書いた
  ことはホストに伝わり（`LinkHost.queueWritten`）、アプリは画面の送信待ちを読み直します。行に書く理由の文のうち、
  止めた行の理由（`RecorderDriver.heldForAnotherRecorder`）と、作成が無応答だった行の理由（`heldAfterSilence`）は
  端末に残り、1 字ずつ比べて読むので、言い方を変えるときは、前の版が書いた文も読めるようにします。
  書き込むのは、書けるレコーダーにだけです（`canBeAsked`、上の「別のアドレスを選んだら」）。操作の前の確認が、
  どの機体かを言わない答えを聞いたあとも、書き込みません（`DeviceLink.mayBeSent`、上の「操作の前に起こす」）。
  どちらのときも、予約は端末に残し、変更と削除は送らずに、なぜかを結果で言います。操作は始めたときに、リンクが
  数える手放した回数を控え、その間にレコーダーを手放していれば、新しい機体には何も送りません（上の「答えたレコーダーが
  誰かで決める」）。
  一覧の読み込み（`reservations`）は、テレビと同じく、1 度に 1 つです。読み込みが出ている間に頼まれた読み込みは、
  同じ手放した回数のまま、リンクが同じクライアントを持っている間なら、出ているものの答えを受け取り、2 つ目の
  要求は送りません（書き込みが通ったあとまで出ていた読み込みは、クライアントが要求を 1 つずつ送るので、その
  書き込みのあとに送られたものです）。進行中の行は、操作ごとに 1 つです。削除なら「予約を削除中」を、確かめる
  前から最後の読み込みまで出し、途中の読み込みは行を出しません（「予約一覧を取得中」は、一覧を読むだけのとき
  だけです）。読み込みの無応答は、レコーダーがもう離れていると分かっている間は言わず、もう一度失いません。
  そのため、書き込みの無応答の文（届いている場合もある）は、その後ろで待っていた読み込みにも、そのあとの
  起こしにも上書きされず、接続が通るまで残ります。レコーダーに聞けない間（諦めた、未接続、503 で答えた
  接続のあと）は、予約タブに最後に読んだ一覧を残し、いつ読んだものかを言います（「レコーダーの予約は
  〈N 分前〉に読んだものです」。`AppModel.reservationsStaleSince`。テレビと同じです）。
  削除と変更（`cancel`、`update`）は、一覧を読み直して行を探し（`[Reservation].target(of:)`。上の「予約 ID は
  振り直されます」）、要求を 1 回送り、一覧を読み直して、読んだ一覧を返します。前の読み込みが失敗したら何も
  送らず、その読み込みの文を言います。行が一覧に無ければ「この予約はレコーダーの予約一覧に見つかりません
  でした。一覧を更新しました。」、ID が別の番組に付いていれば「レコーダー側で予約が更新されていました。…」で、
  どちらも何も送りません。804 か 820（その予約は無い）が返れば一覧を読み直し、読めれば「更新されていました」、
  読めなければその読み込みの文です。変更は、録画中の予約と放送の終わった予約を戸口で断り
  （`whyNot(changing:)`。「録画中の予約は変更できません。」「放送が終わった予約は変更できません。」。読み直した
  行にもう一度当てます）、受け付けられたら、あとの一覧で行を探し直して、録画モードと録画先が送ったとおりかを
  見ます。違えば「変更がレコーダーの予約一覧に反映されていません。一覧を更新しました。」、行が無ければ
  「レコーダーは変更を受け付けたと答えましたが、この予約が一覧に見つかりません。…」です。毎回録画は比べません
  （変更のすぐあとの一覧に毎回録画の変更が出るかを、まだ測っていないため）。あとの一覧が読めなければ、前の一覧の
  行を送った値にして返します。削除は `Altered` を返し、変更と同じく、断ったことは結果で言います（上の、戸口で
  何を言うかの規則）。削除した行は、あとの読み込みが返るまで一覧に残るので、予約タブの削除のスワイプは、
  テレビと同じく、レコーダーの作業中（帯にレコーダーの行が出ている間）は押せません。
  予約（`reserve`）は、テレビと同じく、先に行を端末の送信待ちに書き、その 1 行を送信待ちに送らせます
  （`PendingQueue.flush` の `only`）。戸口で断るもの（録画先がもう出せない、表に無い録画モードや毎回録画、
  リンクが無い）は、何も残しません。レコーダーが離れていると分かっているとき（クライアントが無い、前の問いが
  無応答だった）と、書けるレコーダーでないときは、確かめず、行も出さずに端末に残します。そうでなければ
  「予約を登録中」の行を出して確かめ（`DeviceLink.check`）、USB HDD に入れるときはつなぎ口を待ってから
  （`withholds`。待つ間の無応答は端末に残します）、行を書いて送らせます。書けたかどうかは書いたことだけで決め、
  送信待ちを読み直しません。回はレコーダーの一覧を読んでから作成を送り、つなぎ口はもう待ちません（予約が
  待ったので）。結果は `Reserved` で、送り直した行と同じに読みます（`came`）。作った。一覧にもうあった（作成は
  送らず、「レコーダーにはこの番組の予約がすでにありました。」）。理由付きで断られた（831、本体の HDD への
  402）なら、その理由で端末に残し、利用者を待ちます（帯の下の行には出さず、行の赤い理由が言います）。ほかの
  操作中かスタンバイ中（503 を 2 回送り直したあと、880）や、何も言わない答えなら、理由なしで残し、ひとりでに
  送られます（「レコーダーがほかの操作中かスタンバイ中で受け付けなかったため、予約を端末に保存しました。…」）。
  作成の無応答は、上の理由で残します（上の「書き込みは送り直さない」）。作成より前の無応答（回の初めの一覧）は、
  理由なしで残します（「レコーダーに届かなかったので、予約を端末に保存しました。…」、`keptUnsent`）。回の番が
  来たときに番組が終わっていれば、捨てて「この番組は放送が終わっているため、予約していません。」。ほかの送信が
  先に行を取ったときは、あとで読んだ一覧で、作った、または「予約を登録できたか確かめられませんでした。…」です。
  USB HDD への予約が、ディスクのせいかもしれない理由で断られたときは、何も残さず、行を消して、別の録画先を選ぶ
  よう言います（画面が録画先を出しているので）。行を書く間、回の番を待つ間、回が出ている間にレコーダーを手放し
  たら、回が作っていない限り、行を消して「していない」です（残すと、前の機体のための行として止まるか、
  次に答えた機体に送られます）。回がその行を見なかったとき（ほかの送信が先に取ったとき）は、行を消し、
  その送信が前の機体に作ったかもしれないので、手放さなかったときと同じく「予約を登録できたか確かめられませんで
  した。…」です（一覧は読みません）。作成が無応答だったときも行は消しますが、届いている場合もあるので、
  帯の下の行と結果で `mayHaveArrived` を言い、誰も諦めません。確かめのあとに端末に残すだけの行（確かめが送れな
  いと言った、どの機体かを言わない答えを聞いた、USB HDD の待ちが無応答だった）も、書く間に手放せば消して「して
  いない」です。回の番は端末のすべての送信が分け合うので、ほかの送信（テレビの回、画面の無い処理）
  が出ていれば、「予約を登録中」のまま待ちます。番の中ではリンクの確認を通しません（確認は行を書く前に済ませ、
  あとの一覧は番が終わってから読みます）。通知の許可は、アプリが、予約の行が下りてから、理由の付いていない行に
  ついてだけ聞きます（上の「通知の許可」）。
  送信待ちの送信（`sendWhatWaits`）は、ひとりでに送られる行があるときだけ、「送信待ちの予約を登録中」の行を
  出して確かめてから（接続の中や、起こしたあとの接続ではすぐ通ります。眠ったレコーダーに作成を送って無応答で
  失うより、先に起こします）、回を走らせます。回が止まったわけは、テレビと同じくリンクで言います。止めた行の
  数と回の結果は、アプリが帯に書きます（上の、帯の文の規則）。一覧は、そのあと引き下げ更新か接続が 1 回読みます
  （確認が起こしたときの、接続の外の送信だけは、自分で読み直します）。
  送り直し（`resend`）は、その 1 行だけを送ります。ほかの行は、次の送信で送られます。行の理由は、確かめが済んで
  から消します（確かめが起こしたときの接続が、ほかの行と一緒にその行を送らないように。その行は、その送信の
  あとに自分の回で送り、何になったかを返します）。作成が無応答だった行の理由は消さず、同意として渡します
  （上の「書き込みは送り直さない」）。レコーダーが離れていれば接続し、接続がほかの行と一緒に送ります（理由の
  残る行は、接続のあとここから送ります）。結果は `Reserved` で返し、回がその行を見なかったとき（ほかの送信が先
  に取った、利用者が消した）は、あとで読んだ一覧で、作った、確かめられなかった、のどちらかを言います。
  確かめの間に別のレコーダーが答えたら、行は止めたまま、何も送りません。回が出ている間に答えたときも、
  どの行も切り替わったときの理由のまま止め、回が作っていない限り「していない」で、回がその行を見なかったとき
  は、手放さなかったときと同じく確かめられなかったと言い（その行を取った送信が前の機体に作ったかもしれませ
  ん）、作成が無応答なら、届いている場合もあると帯の下の行と結果で言います。理由を消すのは、読んだときの理由の
  ままのときだけです。
  送信待ちの行の削除（`deleteWaiting`）は、送信待ちの番の中で行い、番を待つ間に送信がその行を持ち去っていれば
  （番組が終わっていなければ）、作ったと言います。確かめの要らないとき（書けるレコーダーで、最後の応答が
  新しく、ほかの確かめが出ておらず、どの機体かを言わない答えも聞いていない）だけ、番の中で、手元のクライアントで
  一覧を読み、その番組の予約があれば、行がまだ待っていても作ったと言います。別のレコーダーに切り替わったために
  止めた行は別で、その一覧は新しい機体のもので行を送っていないので、作ったとは言いません。予約が自分の行を消す
  のは、レコーダーの行が出ている間で、画面はその間、送信待ちの行の削除を止めています。番の中ではリンクの確認を
  通しません。確認がレコーダーを起こすと、起きたあとの接続が送信待ちを送ろうとして同じ番を待ち、どちらも進まな
  くなるからです（`PendingQueue.betweenFlushes` の説明）。
  予約の画面が出す録画モードと毎回録画（`RecorderDriver.recordsIn`、`repeats(startingAt:)`）、変更のボタンの
  下の文、おまかせ・まる録の文、USB HDD のつなぎ口を待って何を送らないかを決めること（`withholds`。
  ディスクが使えなかったことは `SessionState.diskNotHad` に置き、画面はそれを読みます）も、ドライバーが
  持ちます。重なりの問い合わせは、作成と同じ中身で聞き、自分の行は出しません。リンクがもう使っていない
  クライアントの失敗は言いません（同じレコーダーにつなぎ直しても何も手放さないので、こちらはクライアントで
  見分けます）。操作の前の確認がどの機体かを言わない答えを聞いても、それを読まずに続け、行にも触りません。
  番組の画面が出すレコーダーの録画モードと毎回録画、予約する前の確認の最後の 1 文と、レコーダーが離れている
  ときの題（`confirming(away:)`、`keepingTitle`）、重なる予約が無いときの文（`noClashes`）も、ドライバーが
  持ちます。どの機器に入れられるかと、機器によらない入口は、アプリにあります。
  テレビと揃えずに残した違い: 作成が無応答だった行を、レコーダーはひとりでには送らず、利用者を待ちます（テレビは
  次の回が一覧で探してから送ります。レコーダーの一覧は 1 回で 200 件までで、見落とすことがあるため）。おまかせ・
  まる録の予約は、送信待ちの行の代わりになりません（テレビには無い予約です）。書き込みの途中で別のレコーダーが
  答えたら、レコーダーは新しい機体に何も送りません（テレビの削除は、始めたリンクで最後まで送り、ホストごと
  手放されます）。確認がレコーダーを起こすことがあり、起きたあとの接続が送信待ちを送ります（テレビは確認で
  起こしません）。そのため、確認の起こしたあとの送信は一覧を読み直し、送り直しは理由を確認のあとで消し、送信
  待ちの行の削除は確認を通りません。レコーダーの読み込みは、どの機体かを言っていないレコーダーにも送り、
  読み込みの無応答は、接続済みかではなく、もう離れていると分かっているかで受けます。確認が聞いた答えは、確認
  ではなく、それで止まった操作が行に書きます。変更のあとの比較は、録画モードと録画先だけです（テレビは毎回録画
  しか変えず、それを比べます）。予約の画面は、録画先を出せないために送らなかった変更のあとだけ、閉じずに
  残ります。録画とおまかせ・まる録の条件の操作、再生と電源も、そのあとこの決まりに揃えました（下の段落）。
  ドライバーの予約・変更・削除を実機で通す確かめ（`LiveRecorderTests.testTheDriverMakesChangesAndDeletesAReservation`）
  は、まだ走らせていません。作る前の一覧に無く、選んだ局と開始にあり、アプリが作った行を自分の行としますが、
  レコーダーが同じ番組に自分で入れた行にもアプリの印が付くことがあるので、そういう行が 2 つ以上あれば、何も
  書かずに終わり、予約が残っているかもしれないと時刻を添えて言います。作成が無応答だった予約も、届いている
  かもしれないものとして後片付けで待ちます。架空のレコーダーで先に通す確かめ（`DriverCheckRehearsalTests`）が、
  どれも `swift test` で走ります。
  録画（一覧と残容量、詳細、保護、削除、再生・一時停止・停止、電源）と、おまかせ・まる録の条件（読み込み、追
  加、削除）も、ドライバーの手順です（`RecorderRecordings.swift`、`RecorderConditions.swift`）。予約と同じ決ま
  りに揃えてあります。書き込み（録画の保護と削除、再生と電源、条件の追加と削除）は、どのレコーダーかを言った接
  続のクライアントにだけ送り（`canBeAsked`）、確認が断りや不具合を聞いたあとは送らず（一覧も読みません）、操作
  を始めてから別のレコーダーが答えたら、クライアントに渡す前なら何も送りません。電源を入れて待つ再生は、電源を
  入れる前と 2 回目の再生の前にも、それを確かめます。入口で断ったことは結果だけで言い、帯の下の行は前の操作が
  残したままにします。送って失敗したことは、行にも結果にも出て、画面の通知は結果の文を出します。録画中の録画と
  保護された録画の削除は、1 つの関数（`whyNot(deleting:)`）が断り、画面もそれを読んで、出さないボタンを決めま
  す。録画と条件の一覧は、読んだときのレコーダーのものとしてだけ持ちます（予約と同じく `timesForgotten` で）。
  別のレコーダーが答えたら、その接続が、出ていた一覧と読んでいた一覧（条件の追加と削除の途中なら、条件の一覧
  も）を読み直します。前のクライアントで同じ一覧を読んでいれば、それが返ってから読みます（書き込みそのもの
  は待ちません。下の違い）。同じ一覧の読み込みは 1 度に 1 つで、その間に頼んだ人は答えを分けてもらいます。条件
  の追加と削除のあとの読み込みもその 1 つですが、始めたときに出ていた読み込みの答えは受け取らず（書き込みが答
  えられる前に頼んだもので、それを映していないことがあるため）、それが返ってから読みます。条件の追加と削除は、
  押してから、あとの一覧の読み込みが終わるまで、行を 1 つ出します。あとの読み込みは、通った追加と、レコーダー
  が答えた削除（通っても断られても）のあとだけで、断られた削除のあとも読むのは、本体の画面で編集すると条件の番
  号が変わるためです。その読み込みが通れば行は消え、断りは結果で言います。条件が読めなかった理由は、読み込み自
  身が言います。残容量の無応答は、ほかの読み込みと同じく 1 度だけ行で言います。録画一覧を読み直す印は、送って
  無応答だった保護と削除のあとだけ付けます。引き下げは、書き込めないときは接続し、接続済みのままの接続なら一覧
  も 1 度読みます（その接続に別のレコーダーが答えたら、まだ読んでいない一覧でも、読むのはその接続です）。録画
  と条件のシートは、自分の要求が出ている間は閉じられず、その間はシートのボタンとスワイプも止まります。スワイプ
  と確かめのボタンは、どの画面でもレコーダーの作業中は止まり、テレビの作業では止まりません。
  テレビと揃えずに残した違い: 録画の詳細は、重なりの問い合わせと同じく行を出さず、確認が断りを聞いたあとも送
  り、無応答も黙ってレコーダーを諦めます。録画の削除と保護が「その録画は無い」（820）と答えられても一覧を読み
  直しません（予約の削除と変更は読み直します。レコーダーは知らない番号の削除に成功を返すと書かれていて、変更に
  何を答えるかは測っていません）。断られた条件の削除は、どの断りのあとも一覧を読み直します（知らない番号に何を
  答えるかを測っていないため。予約の削除は「その予約は無い」のあとだけ）。条件の削除の前には一覧を読まず、録画
  の削除の前にもその録画があるかを確かめません。再生と電源の無応答は、読み込みの無応答の文で言います。読み込み
  は、どのレコーダーかを言っていない相手にも送ります（予約と同じ）。クライアントの順番待ちにもう渡した書き込み
  は、そのあと別のレコーダーが答えても送られ、答えは手放したあとのものとして受けます。予約の書き込みも同じで、
  機器の違いではなくリンクの限界です。そうして前のクライアントに出ている書き込み（条件の登録や削除そのものも）
  を、新しいレコーダーの接続の読み込みは待たず、その横で送ります。これも同じクライアントの順番待ちのことで、あ
  との段で、クライアントの順番待ちの中で閉じます。一括の削除と保護、重複の検出は、まだアプリにあり、始めたとき
  のクライアントに確かめるだけで送るので、1 件ずつの書き込みとは別の決まりのままです。
  1 つの操作を作る部品も、機器に共通のものをリンクが持ちます（`LinkOperation.swift`）。操作の前の確認
  （`DeviceLink.check`）は、機器に送れないときに、なぜかを返します。未接続、許可待ち、別の機器が答えた、
  起こしたが接続を断られた、確かめている間にその機器を手放した、無応答の 6 つです（`ensureUp` は同じ確認を
  真偽で返します）。確認に断りや不具合が答えたとき、リンクは確認を通しますが、聞いたものを覚え
  （`DeviceLink.heardInstead`）、どちらの機器のドライバーも、それを根拠に何も書き込みません（`mayBeSent`。上の
  「LAN の判定」と「操作の前に起こす」）。どの機器が答えたかを言った接続のクライアントも、リンクが覚えます
  （`attachedClient`。`clientIsAttached` は、手元のクライアントがそれかどうか）。送ったものがどう
  失敗したかは `OperationFailure` が種類と文をまとめて持ちます。何も送っていない、機器が断った、書き込みの
  あとの無応答、読み込みの無応答、返ってきたがその間に機器を手放していた、の 5 つです（最後のものは、
  操作が始めたときの手放した回数を `run` に渡したときだけで、値は返さず、行にも触りません）。`DeviceLink.say` がそれを画面の行に書き、無応答なら上の
  「無応答は 1 か所で受ける」の状態にします。断られただけなら機器は「いる」ので文を出すだけ、何も送って
  いないときは何も書きません（確認がもう伝えています）。書き込みのあとの無応答に出す文は、操作ごとに渡します
  （あとで何を確かめるかが操作によって違うため）。読み込みの無応答を受けるかどうかだけは機器によって違い、
  ドライバーが答えます（`takesSilenceOnARead`）。テレビは接続済みの間だけ、レコーダーは、もう離れていると
  分かっていない間だけ受けます（レコーダーは、どの機体かを言っていない間も読むので、接続済みかでは決めません）。
  無応答になった要求の後ろで順番を待っていた読み込みが、先の要求の文（削除が届いているかもしれない）を
  上書きしないためです。`DeviceLink.run` は、要求が 1 つの操作の順番（進行中の行を出す、確認する、送る、
  うまくいけば前の失敗の行を消し、失敗なら伝える）をまとめたもので、手で頼んだ番組表の取得の入口
  （`AppModel.run`）と 2 つの機器の予約一覧の読み込みがこれを通ります。失敗の行を消すのはうまくいったときだけ
  で、入口では消しません（前の要求の失敗が、読まれる前に次の要求で消えるため）。部品は、偽の外界を渡す
  `LinkPartsTests` が確かめます。レコーダーの操作のうち、入口（`AppModel.run`）を通るのは、手で頼んだ番組表の
  取得だけです。一括の削除と保護、重複の検出もまだアプリにありますが、入口は通りません。録画と条件の操作は、
  `run` を通さず、その部品の上に書いてあります。一覧や削除のあとの残容量の読み込みは、操作が行を消したあとに同
  じ行の下で読み、その無応答を行に残すためです。レコーダーの送信待ちの送信は、進行中の行を部品（`underALine`）
  で出し、回が止まったわけを `say` で伝えます（作成の無応答は、行に書いた理由の文で。作成より前の無応答は、読
  み込みの無応答の文で）。レコーダーの予約の削除と変更は、進行中の行を部品で出し、送信の無応答を `say` で伝え
  ます（届いている場合もある、の文）。予約は、送信待ちの 1 行の回なので、送信と同じです。
  要求がいくつもある操作（テレビの予約の変更と削除）は `run` を通りません。同じ確認（`ensureUp`）を使い、
  途中の一覧の読み込みは `run` を通ります。変更は、進行中の行と送信の失敗を部品（`underALine`、`say`）で
  出しますが、削除は、進行中の行と、送信の無応答や「その予約は無い」と答えられたときの文を、
  まだ自分で書いています。
  HTTP のクライアントは、1 つの要求を 1 回だけ送ること。`URLSession` は、401 に Basic の認証の問いが付いていると、
  同じ要求を別の接続でもう 1 回送ってから 401 を返します（デリゲートが何と答えても、問いを取り消さない限り）。
  テレビの登録の要求（`actRegister`）は、未登録なら必ずこの 401 で答えられます。アプリから登録したとき、テレビの
  画面の PIN は出てすぐ消えました（同じ要求を 1 回だけ送ると、読める間は残ります）。`Http.swift` は問いを取り消して
  401 の答えをそのまま返し、`URLSessionTransportTests` がループバックのサーバーで、送ったのが 1 回であることを
  確かめます。差し替えの通信では見えない規則なので、移植先でも本物の HTTP クライアントで確かめてください。
  テレビへの要求と、移ったテレビを探す走査は、リダイレクトを追いません。3xx はそのまま答えとして返します
  （`URLSessionTransport.withoutCookies()` のセッション）。ポート 80 にはルーターやプリンターの画面が答える
  ことがあり、https のページや LAN の外の名前へのリダイレクトを追うと、アプリが選んでいない宛先とポートに
  送ることになるためです。テレビの接続は、そういう 3xx を、テレビではない機器が答えたものとして読みます。
  レコーダーの通信は今までどおりです。これも `URLSessionTransportTests` がループバックで確かめます。
  テレビの挙動を測るときも、別の道具ではなく、アプリが送るのと同じクライアントと通信で送ります
  （`TV_HOST=<アドレス> swift test --filter LiveTVTests/<テスト名>`。変数は毎回コマンドの行に書き、テストは 1 つずつ名指しします。
  登録の手順はファイルの先頭にあります）。
  予約を入れる 3 つの要求を実機に初めて送る確認も同じファイルにあり、持ち主がテレビの前にいる席で、1 つずつ
  走らせます（順番と、そのつど見るものはファイルの先頭）。テレビに書き込む確認の決まりは `TVSitting` に
  書いてあります。書き込みを名指しで許されたとき（`TV_WRITE` が、走らせるそのテストの名前のとき）だけ、テレビの
  電源が入っているときだけ作る。作成の前には毎回、録れなくなる予約をテレビに問い合わせ、自分の作った行のほかが
  挙がれば作らない。作成の前と後に一覧を読み、送った局に新しく増えた番号の録画だけを自分のものとして消す（番組や
  時刻や番組名では消さない）。自分の行の番号が、あとで読んだ一覧で別の局や別の番組の予約に付いていたら、その行は
  もう自分のものとせず、削除を送らず、台帳に線を引かずに終わる。作る前に台帳のファイルに書き、削除に応答があり、
  消えたのを一覧で見てから線を引く。線の引かれていない記入が残っていれば、その後の確認は何も作らずに失敗する。
  作成が無応答でも送り直さない（一覧を 1 回読み、自分の行があれば消し、消えたことをもう一度一覧で見る）。前後
  3 時間に予約の無い、20 時間以上先の番組にだけ作る。確認に使う視聴予約は、持ち主が開始の時刻で名指しする
  （`TV_REMINDER`）。番組名・局名・テレビの付けた番号は表示しない。同じ確認を、その前に偽のテレビ（`DemoTV`）で
  通します（`TVSittingTests`）。持ち主の予約を、確認の使う枠のすぐ外と、確認が予約する番組そのものに置いておき、
  行が残る、作っていない行を消す、作成を 2 回送る、問い合わせずに作成を送る、番組名を表示する、のどれかがあれば、
  実機に送る前にそこで落ちます。
  電源を切ったテレビ（待機と答えるテレビ）への確認が 1 つあります（`testAWaitingRowSentInStandby`。手順は
  ファイルの先頭）。この確認だけは、ほかと逆に、テレビが待機と答えたときにだけ作ります。送信待ちの 1 件を、
  確認だけのためにメモリ上に作ったデータベースに入れ（ディスクには何も置かない）、出荷するのと同じ手順
  （`PendingQueue.flush` と、上のテレビの回）で送ります。続けて同じ 1 件をもう一度入れて送り（一覧で見つかるので、
  作成は送られない）、行を消します。確かめるのは、出荷する手順が、電源を切った実機に、アプリ自身の
  クライアントと通信でそのまま通るかどうかと、そのあいだの画面・本体のランプ・ディスクです。電源を切ってからの
  長さは問いません。テレビは、電源を切って数分後にも（別の道具で、予約の作成と削除、局の一覧）、5 時間以上
  あとにも（このクライアントで、登録の要らない読み取り、ディスクと予約の一覧の読み取り、登録の更新）同じ
  ように答え、アプリは電源を切ったテレビの予約を削除できています（どれも測）。そのため、時刻を選ばない短い
  1 回の席で済みます。実機では、リモコンで電源を切って約 1 分後に通りました（測）。1 回目は、ディスク、一覧、
  局の一覧、問い合わせ、作成、一覧のどれにも応答があり、行が 1 つでき、読み返すと送ったとおりでした。2 回目は
  ディスクと一覧だけで、行は一覧で見つかり、作成は送られませんでした。行を消したあとの一覧は確認の前と同じで、
  テレビは終わりにも待機と答え、画面にもランプにもディスクにも変化は見えませんでした。回が行を保留にする
  場合と回を止める場合は、実機では通していません（偽のテレビで確かめています）。
  0 時から 5 時までに始まる番組は選びません。局が放送を休んでいることのある時間帯で、その枠への
  作成にテレビが何と答えるかは見ていないためです。作成を送るのが確認ではなく回なので、台帳は送信待ちを送る前に
  書き、送る前と後に一覧を読みます。台帳にいつ線を引くかは、ほかの確認と同じ 1 か所の規則を通ります。自分の行と
  するものは、ほかの確認より狭くしてあります。送った局に新しく増えた録画のうち、入れた番組の番組 ID を持つもの
  だけです。作成が送られていないとき、送られても受け付けられなかったと分かるとき（すでにあった、符号で
  断られた）は、1 行も自分のものとしません。作成が送られたかどうかは、送信待ちの結果ではなく、下の通信の控えで
  見ます（「見送った」行は、作成の応答が読めなかったときも、問い合わせにエラーの符号が返って作成まで進まなかった
  ときも、同じ結果になるため）。それ以外に増えた録画は持ち主のものとして触らず、台帳に線を引かずに失敗します。
  作成の前の問い合わせは回が行い、1 件でも名指しされれば作成を送りません。作成が送られていて、回が
  「受け付けられたが一覧に無い」「見送った」と言ったとき、作成が無応答だったときは、一覧に何も増えていなくても
  台帳に線を引きません。
  回が何を送ったかは、送信待ちの結果からは分かりません（一覧で見つかった行は、作成を送ったあとで見つかっても
  同じ結果になる）。そこで確認のクライアントは、要求ごとにメソッド名と応答の種類（応答あり、エラーの符号、
  HTTP の状態、無応答）だけを控える通信（`TVLine`）の上に作り、送るたびに何を送ったかを表示します。2 回目に
  作成が含まれていれば失敗します。終わりに、テレビが自分の状態を何と答えるかをもう一度聞いて表示します
  （何と答えても失敗にはせず、無応答のあとは聞かない）。ほかに表示するのは、送信待ちの結果の件数と、回が
  止まった理由の種類だけです（行に書かれた理由の文には、持ち主の予約の題名が入るため）。テレビの電源を切って
  から確認が終わるまでは、この確認のコマンドのほかにも、レコーダーやテレビに問い合わせるもの（番組表を取りに
  行くサーバー、スマホのアプリ）を止めておきます。
- **サンプルデータのモード**: レコーダーの応答を偽のものに差し替えるだけで、画面は本物のパーサを通ります。
  審査にも、レコーダーを持っていない人の下見にも、ストア用のスクリーンショットにも同じものが使えます。
  キャッシュは**別のデータベースに書く**こと（終了時にファイルごと消せる）。実装は `app/BDBridge/DemoData.swift`。
  サンプル中に実機を選んだとき（探して選ぶ・アドレスを入力する）は、**サンプルを終了してから**そのレコーダーに
  つなぐこと。サンプルのままつなぐと偽の応答で「つながった」ように見え、あとで終了すると元の設定に戻って、選んだ
  レコーダーが消えます。元の設定に戻すのは「終了」だけで、選んだときは戻しません（`AppModel.adopt`）。サンプルの
  開始・終了と切り替えは、接続・読み込み・一括処理・操作の前の確認の最中は受け付けないこと。途中の応答が
  切り替えたあとの画面に入ります。答えたレコーダーの照合（上の「答えたレコーダーが誰かで決める」）は、
  サンプルでは行わないこと。サンプルのキャッシュは自分のもので終了時に消え、実機のキャッシュ（持ち主の UDN、
  録画の番組内容、残容量の通知の印）はサンプルの出入りで変えません。
  サンプルにはテレビもあります。始めたときには無く（だから、ふだんのサンプルとスクリーンショットはレコーダーだけの
  家の画面のまま）、サンプルの検索で見つかる架空のテレビ（`DemoData.television()`、パッケージの `DemoTV`）を押すと、
  実機と同じに番号で登録します。番号は画面に出ないので、シートが言います。架空のテレビは電源が入っていて、
  サンプルの番組表のすべての局を受け、予約したものを番組表の題名で並べ、リモコンで入れたような録画予約を 1 件
  持っています。それ以降、サンプルはレコーダーとテレビのある家になり、テレビへの予約、毎回録画の変更、削除、
  「テレビを外す」が実際に動きます。架空のテレビと、その登録と、足したアドレスは、サンプルの間だけメモリに置き
  （`demoTV`、`demoTVCredentials`、`demoTVHost`）、**実機のテレビのアドレス、MAC、キーチェーンの登録と鍵のファイル、
  画面の無い処理が知らせたことの控えは、読みも書きもしないこと**。サンプルの間、テレビへの要求はすべてモデルの
  `televisionTransport` を通し、架空のテレビのアドレスだけが答え、ほかのどこにも出しません。架空の
  テレビのアドレスは、サンプルが終わったあとも LAN に出さず、黙らせます（終わる前に作ったリンクに、まだ出す要求が
  残っていても）。サンプルを終えるときは、先に架空のテレビのリンクを手放してから（残すと、実機のテレビのリンクが
  作られません）、テレビと登録を捨て、テレビ宛の送信待ちはサンプルのキャッシュと一緒に消えます。実機のテレビは、
  保存してあるものからリンクを作り直して、番号を聞かずにつながります。サンプルのまま起動し直したときはテレビが
  無く、サンプルのキャッシュを開くときにテレビ宛の送信待ちを消します（`DemoData.seed`）。`DemoTelevisionTests` と
  UI テスト 1 本（`testTheDemosTelevisionIsFoundReservedAndGoesWithTheDemo`）が確かめます。

## App Store 申請の要点

- **審査担当者はレコーダーを持っていません。** 起動しても何も見つからず、機能を評価できないという理由で返される
  可能性があります。これが最大のリスクです。**対策として、チュートリアルの最後と設定画面から入れるサンプル
  データのモードを入れました**（`app/BDBridge/DemoData.swift`）。架空の番組表・録画一覧・予約一覧で、予約の作成・
  変更・削除まで実際に動きます。テレビも、サンプルの検索で見つかる架空のテレビ（`KJ-SAMPLE`）を番号 1234 で
  登録して試せます。審査メモには入り方を書き、機種要件とデモ動画のリンクも添えます。
- **アプリ名は独自の名前にします。** 他社の商標は名前にもサブタイトルにも入れず（Apple のガイドライン）、
  対応機種は**説明文の本文**で伝えます。ロゴ、製品写真、本家アプリに似た配色やアイコンは使いません。
- **Info.plist** には `NSLocalNetworkUsageDescription` と `NSAllowsLocalNetworking` を入れます。用途は正直に書きます。
- **プライバシー**: ポリシーの URL は全アプリ必須なので、何も収集しない旨のページを用意します（`privacy.md`）。
  App Privacy の質問票は収集項目なしで答えられます。外部ライブラリは使っていませんが、`UserDefaults` は
  「理由の宣言が必要な API」なので、理由コード（`CA92.1`）を書いたプライバシーマニフェストが要ります（無いと
  ITMS-91053 で止められます）。iOS アプリでは `app/BDBridge/PrivacyInfo.xcprivacy` がそれで、収集も追跡も
  しないことと、この 1 つの理由を宣言しています。マニフェストにはコメントを書かないこと。`--` を含むコメントは
  整形式の XML にならず、ITMS-91056 でビルドが差し戻されます（`plutil -lint` はそれを通してしまいます）。
- **費用と手続き**: 個人登録で足ります。無料アプリなら銀行口座と税務情報の登録は不要です。iPhone のみにすると
  iPad 用のスクリーンショットと動作保証が不要になり、面倒が減ります。
- スクリーンショットの要求サイズは変わります。申請時に App Store Connect の最新の要件を確認してください。
  撮り方（サンプルデータで撮る手順、寸法とシミュレータの対応、はまりどころ）は
  `app/scripts/screenshots/README.md`。

Android を配布する人向けの注意も一つ書いておきます。Play ストアを使わず APK を直接配る形は、Play Protect の警告、
自動更新の欠如、そして認証済み端末へのサイドロードに開発者の本人確認を求める動きがあるため、一般利用者向けには
向きません。配布前に最新の要件を確認してください。

## 検証ベクタ（`docs/port/`）

`uv run python -m bdzbridge.tools.portkit` が Python 実装から生成します（テストが鮮度を確認するので、手で直さないこと）。
移植側では次のようなテストを書きます。

- `codes.json` — 定数の一致（コード表、ファイル名、ARIB 記号表、ロゴの共通カラーテーブル、名前空間、制御 URL）。
- `xsrs.json` —
  - `create_elements[*].input` から Elements 文字列を組み立て、`elements` と**完全一致**させる。
  - `update_elements` / `title_update_elements` も同様。
  - `parse_reservation.item` / `parse_title[*].item` を解析して `expected` と一致させる（`notplayed` の扱いを含む）。
  - `soap.example.body` と同じ本文を作れること。
- `description.json` — `description_xml` を解析して `expected` の各値（機種名、UDN、EPG 対応）を得ること。他社機や
  レコーダー以外のソニー機を弾くこと（製造者が Sony Corporation かつ XSRS サービスを持つもの）。
- `epg-sample.dat` → `epg-sample.json` — 復号結果が一致すること（時刻は ISO 8601 の `+09:00`、参照イベント、ジャンル、
  コピー制御、視聴年齢、記号置換）。実機ファイルでの検証は `server/tests/test_epg.py` の要領で自分のレコーダーから取る。
- `logo-sample.dat` → `logo-sample.json` — チャンネル番号と service_id の対応、ロゴのない局のスキップ、PLTE/tRNS 挿入後の
  PNG が `png_base64` と一致すること。
- `series.json` — `series_name` / `series_key` / `same_title_key` / `summary_key` の各値の一致。
- `titles.json` — 視聴状態（未視聴／途中／視聴済み）、番組ごとの「まとめ」（件数・容量・未視聴数・保護数）、
  重複の検出（候補の作り方、内容による分割、残す 1 本とその理由、`guide` から求める `fixed_blurbs` と定型文の組
  `boilerplate`）。**録画中のものは残す側に固定**され、削除候補には入りません。

## 他のプラットフォームに移植するときの順番

上の表と同じ順序で積むのがいちばん楽でした。

1. プロトコル層: `description.xml` の解析 → SOAP → 予約一覧の取得（読み取りだけ）。`xsrs.json` と `description.json` を通す。
2. EPG: ファイル取得と復号、端末内 DB、日別・チャンネル別の表示。`epg-sample` を通し、実機ファイルで Python と突き合わせる。
3. **サンプルデータのモード**: ここで作っておくと、実機がなくても UI を進められて、申請にもスクリーンショットにも
   そのまま使えます。
4. 予約: 作成・更新・削除と番組追従。テスト用の予約名を決めて作成→削除で確認する（録画の削除はテストに使わない）。
5. 録画: 一覧、詳細、保護、削除、テレビ再生、まとめ、重複。`series.json` と `titles.json` を通す。
6. 宅外: 送信待ちキュー、Wake-on-LAN、諦め方。
7. 仕上げ: おまかせ・まる録、ロゴ、残容量の警告、定期更新、通知。
